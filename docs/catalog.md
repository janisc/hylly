# The catalog (`hylly catalog`) and the server (`hylly serve`)

**Goal:** find and browse everything you own, across books, comics, manuals and collections, from any source. Built into `hylly` rather than adopting a ready-made server, for what Hylly wanted of one:
- **Your files left as they are:** the catalog reads the folders the shops' downloads and your own books are in, and never copies, renames or rewrites a book; what it finds is kept apart (*Program, metadata and content stay separate*, below).
- **One tool from the shop to the reader:** the downloads, the catalog, the lookups and the server are one package, installed once, with one set of settings, so a title is the same title at every step.
- **A page that needs nothing installed on the device:** a current browser ([those Hylly is made for](../README.md#built-on)) browses, searches and reads the library, and the reading apps take the same catalog over OPDS.

## Use cases it must serve
1. "Show me every Marshal Kane / Rust Orchard volume I have": series grouping, in volume order, across bundles and sources.
2. "Find *The Long Dust* by Marlow Ellery", even with the title half remembered: prefix and fuzzy search over title, author, series, publisher and bundle.
3. "Browse sci-fi novels": genre facets, plus kind, source and device filters.
4. On a tablet: browse, search and download in a reading app such as Panels, over OPDS.

## Requirements
- **Kept current by a script.** `hylly catalog` is incremental.
- **Program, metadata and content stay separate:**
  ```
  <this repository>              program
  <library>\catalog\             what can be made again: data.js (the titles, for the server), covers\, cache\ (safe to delete)
  <library>\state\               what can't: the shops' records, snapshots, and the lookups' answers and budgets (lookups\)
  the database (hylly.db)          the titles and their files as the last build kept them, when each title first came,
                                   and your own changes (docs/database.md); data.js is written from it
  <library>\<content>\           the shops' folders (humble\, storybundle\, drivethrurpg\, itchio\) and your own: never written by the catalog
  ```
  `hylly catalog --rebuild` regenerates everything, from the files and `state\`, so nothing is looked up again; `hylly catalog --page` makes data.js again from the database alone.
- **Files are written whole, and record files survive being cut** (`storage.py`). One build at a time, on any computer sharing the library (`runs.py`, with a lock in `state\locks\`).
- **A build won't quietly lose a folder.** Your folders are walked folder by folder, each listed once (`os.scandir`; a link to a folder isn't followed, as `os.walk` follows none), past the systems' own folders (`System Volume Information`, `$RECYCLE.BIN`, `lost+found` and the like: `paths.CLUTTER_FOLDERS`, the list `hylly copy` passes by, at the top of the library too) and, at any depth, the folders tools keep beside your books, which `hylly copy` does copy: version control's (`.git`, `.svn`, `.hg`), trash (`.Trash`, `.Trash-<uid>`, Calibre's `.caltrash`) and sync tools' (`.stversions`, `.stfolder`, `.sync`, `.dropbox.cache`) (`paths.TOOLS_FOLDERS`, `catalog.USERS_TRASH`); one rule, `catalog.systems_own`, for the build, `hylly doctor`'s `catalog.unlisted` and `shrunk`. Any other folder starting with a dot is read, and a shop's title whose folder starts with one comes from the shop's records. One of your folders that can't be listed, or a folder in one that held a title in the last build, stops the build with nothing changed (exit code 6), as does a state folder whose snapshots can't be listed (`snapshot.latest`; one that isn't there has none). Another folder that can't be listed is passed over, and the build says so in one line. So is a file whose path isn't proper text (on Linux, a name an old program wrote in another encoding, such as Latin-1, which Python gives with stand-ins for its odd bytes): it is left out before any title is made, so no other title's files or id change, and the line shows it with those bytes as `\xe9` (`catalog.proper_name`, `catalog.shown_name`). A book file listed that can't then be looked at (on Windows, a path longer than Windows takes, or a name another system wrote that Windows can't take; anywhere, a link that leads nowhere, or a folder Hylly may list but not look into: `catalog.CANT_LOOK`; or one damaged file the disk can't answer for, while its folder and the library still do) is left out the same way, and named in a line with why (`catalog.a_file`), where `Path.is_file` passes over it in silence (on Python 3.14 whatever the trouble). A folder or a library that no longer answers stops the build instead, as a share gone does. On Windows a folder whose name ends in a dot or a space can't be listed at all: it is a folder that can't be listed, as above. `hylly doctor`'s `catalog-unseen` names such files, and the folders `catalog.unlisted` couldn't read, and counts nothing in them as gone. Before anything is kept (your edits, the days titles came, the titles), the build is held against the last one (`catalog.shrunk`): a source that had 10 titles or more and keeps fewer than half of them, or a whole catalog of 10 or more that keeps fewer than four fifths, stops it, naming those sources and the folders most of the missing titles were in. A title counts in every source it has a copy in; the systems' own folders, and titles all of whose files a build from before found in them, don't count. At the keyboard it asks; `--yes` keeps such a build; with nobody there it isn't kept (exit code 8), says to run `hylly catalog --yes` if the titles are gone on purpose, and sends a note saying so (`bell.job_note`); either way `hylly jobs` shows the run. The downloads' records are read from the database, not by listing folders.
- **The browser is the viewer, and the server sends it what it shows.** The library page, its catalog and the reader come from `hylly serve` (as README.md's quick start has it: build the catalog, then serve it), on this computer as on any other device, and so do the reading apps' feeds (OPDS). Opened from the folder (`file:`), the page says only that, and runs nothing.
- **All metadata is found automatically.** What can't be found stays empty. Nothing has to be entered by hand; what you correct or tag yourself is kept apart (*Your own changes*, below).

## Data model (one record per title, not per file)
- **Identity:** a stable id from the shop (Humble machine name, StoryBundle book id, DriveThruRPG product id, itch.io game id), or a path hash for folders.
- **Core fields:** title, authors, series and volume, publisher, year, kind (one of the kinds in the rules, `kinds.toml`: book, tech, rpg, comic, manual as they come), genres and subjects, game (RPG titles), description, ISBN.
- **Kind:** a shop's title is of the kind the rules find for it, the same way at every shop (`rules.Rules.kind_of`; `catalog.kind_of` by its files as downloaded, Humble's by its plan, by every format offered: [rules.md](rules.md#the-kinds)); a title of your own folders is of its folder's kind (`folders.py`). Your correction is laid over it by the server (`k`; what the catalog found is `k0` on the page). The page names the kinds as the server sends them with the catalog (`library.kinds_table`: the rules' `label`, `plural` and `device`): it keeps no list of its own.
- **Source:** the shop, bundle, purchase date and bonus flag; for your own folders, the collection (the first subfolder: `collections\Poetry\` gives Poetry) and the folder's label (`[folders.NAME]`, folders.py).
- **Files:** each file's path, format and size. Same-name files in several formats in one folder are one title. Names compare by their letters and digits, of any script, with case, spaces, punctuation and the Unicode form a name is written in not counting ("Some_Book.epub" and "Some Book.pdf" are one title, "Книга 1" and "Другая 1" two). Accents count, as one book's files are named alike: Tähti and Tahti, ガラス and カラス, Мой and Мои are two titles each. A `+` or `#` that ends a word counts too, so C, C++ and C# are three titles (`catalog._stem_key`).
- **Device suggestion:** e-reader, tablet or either (`ereader`, `tablet`, `either`), for every title, of every shop and every folder of yours, worked out once by one function after the title is read (`catalog.device_of`, by `plan.device_for`): by its kind (your correction of it, if you made one) and its main file as that kind picks it, of the files Hylly can read and those an e-reader takes (an FB2 beside a PDF), a ZIP package by the book inside it. A kind whose `device` in the rules is `tablet` (comics, RPG books) is a tablet's whatever its file. Any other is then a tablet's by `[devices]` in the settings: a fixed layout (PDF, DjVu, a comic file) or a text file over 21 MB (`image_heavy_mb`); else it is its kind's: `either` for a tech book, the e-reader for a book or a manual. So a tech book's PDF, or its EPUB over 21 MB, is a tablet's. A title in several places (one card) is read where the friendliest of its copies is (e-reader, either, tablet: `catalog._merged`), so the feed, which offers the best of every copy's files, lists it when one of them suits the e-reader; a title in one place keeps its own. A kind you correct moves its device at the next `hylly catalog`.
- **Cover:** a thumbnail path.

## Where metadata comes from (best first)
1. **Inside the file:**
   - EPUB: the OPF metadata (title, creator, description, `dc:subject` and BISAC subjects, ISBN, publisher, date), and the EPUB's own cover.
   - PDF: the document info, and the first page rendered as the cover (PyMuPDF).
   - CBZ/CBR: `ComicInfo.xml` if present, and the first page as the cover: its pages as the reader shows them
     (`archives.comic_pages`), which the page count goes by too.
   - MOBI/AZW3: the EXTH header and the embedded cover: only the list of records, the first record and the cover's are read, never the whole file.
   - ZIP (a package, as StoryBundle's): the book inside it that its kind picks first. An EPUB or a PDF is unpacked into a file of its own in `catalog\cache\unpacking\` and read from there, so a big one is never held whole in memory, and is removed once read; what a build that stopped left there goes at a later build, once it is more than an hour old (`catalog.tidy_unpacking`). A link in that folder's place is never followed: nothing is unpacked or removed through it, and a package's book is read again next time. A MOBI is read as it unpacks.
   - The file read is the title's main file: of its book files Hylly can read (never an extra, nor a readme or a picture
     beside them), the one its download stands on, else the first of its kind's formats under `[download]`. What it lacks
     of a description, series, publisher and ISBN a Humble title takes from the same book in its other formats that give
     them (EPUB, MOBI, a comic's ComicInfo; never a PDF). The caches, in `catalog\cache\`: `files.jsonl` for the main
     files, `details.jsonl` for those other files, `opens.jsonl` for whether each file opens; `--rebuild` sets the
     first two aside with the covers, and removes them once its build is kept (they're put back if it's stopped or fails;
     after a power cut, the next build reads what it hadn't and removes them).
   - A file that can't be read gets the title and author its name gives. One that can't be read just then (an `OSError` or `MemoryError` underneath, as from a share's stall or a file another program holds, even when zipfile calls it "not a zip file") isn't cached, and the next build reads it again; `--retry-covers` reads again the files cached without a cover, unreadable ones too. A file that trips up the build in some other way is named in a line, and the build goes on.
2. **Shop data:**
   - Humble: title, publisher, bundle, date, and often an ISBN in the publisher link.
   - StoryBundle: the author from file names (`Title_-_Author.epub`).
   - DriveThruRPG: publisher, order date, ISBN, short description, cover, and the Rule System, Product Type and Genre filters.
   - itch.io (`catalog.itchio_items`): title, the creator as publisher (and as author when nothing else names one), the first bundle, cover, short description, and the kind by itch.io's own classification (`[kinds.X]` `itchio`), unless the words of its bundles or its creator say otherwise.
   - A folder of your own with `named = true`: file names like "The Lantern Keeper (Harbor Lights Book 2)" give the series and number.
3. **Lookups, cached in `state\lookups\`:** the sources in [lookups.md](lookups.md). The build only reads their answers, so it works offline.
4. **Genre:** a short genre list (`genres.toml`, see [rules.md](rules.md)) matched as whole words against subjects, bundle names, collection folder names and the title, except at the sources the rules' `[genres]` `titles_unread` names (none, as shipped). In a folder of your own with `genres = true`, the first subfolder is the genre: the one its words find, else its name; a book outside a subfolder is matched as any title.
5. **Game** (`gm`, RPG titles only, after your kind corrections): DriveThruRPG's Rule System, else the names in `games.toml` matched against the title, series and bundle. A DriveThruRPG product without a Rule System also looks in its description (not for names that are ordinary words, `ordinary = true`), and last takes its bundle's game when at least half of that bundle has one and they all agree. A shop's name that one of them matches is shown as that one ("Pathfinder 2e" as Pathfinder). Rebuilt at every run, apart from your tags.
6. **Series parsing for comics:** "The Rust Orchard Vol. 20", "Marshal Kane Trail Logs 05" and "Lantern Wolf Vol. 1" become series plus a number (`series.toml`). Spellings of one series fold together, case, accents and punctuation not counting, in any script ("Marshal Kane: The Complete Trail Logs" ~ "Marshal Kane Trail Logs", "Café Lantern" ~ "Cafe Lantern", "ΟΔΟΣ" ~ "Οδός"), alike on the page and in the OPDS series feed (`Rules.series_key`, the page's `seriesKey`).

All of these word lists are rules files you can change: [rules.md](rules.md), and `hylly rules`.

## Cleaning what files say about themselves
- **Junk titles fall back to the file name:** "Microsoft Word - draft.doc", "Untitled-1", "cover", "test", web addresses, drive paths, and internal names such as "00 1234_FM_Intro".
- **Junk authors are dropped:** "Administrator", "Unknown", "calibre", "test". The lookup can then fill the author in.
- **Several authors in one string** ("Ann Writer; Bob K. Author") become separate authors.
- **A comic named "Marshal Kane - The Complete Trail Logs 006"** inside a folder whose name starts with "Marshal Kane" takes "Marshal Kane" as part of its series, not as its author. A note in brackets after the number ("(Deluxe Colour Edition)") doesn't hide the number, and a bare "Volume 8" title gets its series in front.

## Copies of one book in several places
A book bought twice, or also present in a collection, becomes one record that lists every file (`merge_copies`). The shop's copy leads, the others fill its gaps, and `cp` names the other places; the page and the OPDS feeds list the record under each of those sources.

Two records merge only when they are:
- **the very same file:** same format and size, under the same title; or
- **a title both confirm:** the shop's title, or one their file names repeat, with no conflicting author. Manuals never merge this way.

This keeps apart the issues of one magazine that all carry the same title in their PDF metadata, different maps that share the title "Map", and different series' "#1" issues.

Where the rule is unsure, a build asks ([The catalog's questions](#the-catalogs-questions), *same book?*), and your answer goes over the rule in every build: the same book is one card whatever its kinds and titles say (the lead as the order has it: your folders marked `first`, the shops, your other folders), and two apart never share a card (`merge_copies`'s `pairs`, from `same_pairs`). The reverse, a card that is two books, needs no question: `hylly set copies apart` (or *Not one book* in its details on the library page) keeps its copies apart, and `hylly set copies auto` lets the rules decide again.

## The page (`/catalog/index.html` + `/catalog/data.js`, from the server)
- One HTML file with inline JS and CSS (`src\hylly\catalog_page.html`), sent by the server from the program, whatever the library's folder holds. Its data is asked for by a small script at the top of the page, while the rest of the page comes, which keeps it fast; that script runs the page's own script (`pagescript`) once the data is in and the page is read. The page's policy runs only its own inline scripts, by their hashes, and the files they load (`'strict-dynamic'`, `serve.page_policy`), never a script file by a tag of its own; and Chrome lets a script allowed by its hash alone import no module, so the page's script, which imports the reader's engine, is run by the first one (`serve.LATER`). That data.js is the server's own (`library.Catalog.page_script`): the catalog as it has read it from `catalog\data.js`, your tags and corrections laid over it (`page_item`), each of the catalog's own thumbnails by its version (Caching, below), written out by `json.dumps` as one JSON value (U+2028 and U+2029 escaped too), so nothing in a title, an author or a tag can end its text and run as the page's code, and whatever a file in the folder holds is never sent as it is. Each record carries what the page sorts and groups by, made in Python by the rules: `sk`, its series' key (`Rules.series_key`, as the series feed groups), and `ak`, its first author's name surname first (`Rules.author_key`: `[names]` particles stay with the surname, suffixes go). The build writes them (`catalog.sort_keys`); the server makes them again for a series or an author you corrected. For a title you corrected, `fx` says what you corrected and `o` what the catalog found of it, for the details. It is made again when the catalog or the edits change and kept, packed, until then; the browser asks for it at every load with its `ETag`, and gets a 304 while it stays the same. The page itself keeps only the folding typed search and the shelves need (`fold`, `norm`, `words`; a test runs them against `rules.words_of` on every character). Opened from the folder (`file:`), the page shows one line, that it comes from the library's server and to run `hylly serve` and open the address it shows, and reads no further: the rest of it, its data and its scripts never come.
- **Search:** every query word must match, by prefix or with a small edit distance, weighted by title, then series, then author. A word is letters and digits of any script, with the vowel signs that are part of it (all of Hindi's and Tamil's, and Thai's but those below a letter); case and punctuation don't count, nor does any mark that Unicode treats as an accent on a letter (its combining class isn't 0): accents, Hebrew's and Arabic's vowel points, the nukta and the virama, and Thai's vowels below a letter and its tone marks, so ครู is found as คร. The page, the feeds' search, shelves and tag suggestions read words alike (`rules.words_of`, the page's `words`; a test runs both on every character). Japanese and Chinese have no spaces between words, so a search finds a title there by how a run of its text starts.
- **Layout:**
  - Facets: source, kind, game, genre, device.
  - A cover grid, with one card per series ("Series together") and the volumes in order inside it.
  - A detail pane: description, subjects, files with their links (saved as files: `?dl=1`), bundle and purchase date.
  - Sorting by best match, title, author (by surname, no author last) or purchase date.
- **Covers:** WebP thumbnails in `catalog\covers\`, or a shop's own cover by its address, kept only as `https://` with a host (`catalog.shop_cover`, the pattern of `library.COVER_SITE`, whose sites the page's policy names): anything else a shop gives (http to a device at home, a `file:` or share address) is no cover. The server checks every cover the same way as it reads the catalog (`library.good_cover`: those two, a thumbnail as `covers/<16 hex>.webp`), and the page checks it again (`library.shown_cover`: a thumbnail by its version too, as the server sends it), so any other address in a catalog reaches neither the page, the feeds nor the page's policy.
- **Help:** `/catalog/help.html`, the admin cheat sheet, rendered by the server from `src\hylly\help.html`. An owner (by their login, on any device) gets it with your settings filled in, with the port it listens on (`helppage.port`: its own note, else `[server] port`) and `address`, made afresh when the template, `settings.toml` or the catalog changes; everyone else gets the folders in words ("the library folder", "the database, hylly.db (in the settings folder)"), so it names no folder of this computer. With a mistake in `settings.toml` the owner keeps the help as last made, or, before any, gets the one in words. A file named `help.html`, `index.html` or `tags.js` in the library's `catalog\` is never sent, as one put there would run as one of Hylly's own pages; the build takes such files away.

## `hylly serve`
- **Lifecycle:** a small web server for the catalog and the reading apps. It runs until stopped: nothing stops it by itself. Unused, it takes about 70 MB and practically no CPU.
- **One at a time** (`instance.py`): the server holds an OS lock on `server.lock` next to the settings while it runs; the OS drops it when the process ends, however it ends. `server.json` beside it records the process, the port and where it listens, for `hylly server status`, `hylly server stop` and `hylly server restart`. A second start says where the running server is and leaves it as it is; with options typed, it says those aren't for it (exit code 4). A stop ends only the process that wrote the note (`instance.wrote`: one begun after it has only been given its number). On Windows the port is bound without `SO_REUSEADDR`, which there would let a second server share it unnoticed.
- **In the background:** `hylly serve --background` starts the server itself, `hyllyd --in-background`, detached, without a window, with the settings as its options (`instance.start_background`). `hylly server autostart on` starts it at every logon: on Windows it sets up a Task Scheduler task that runs `hylly --here serve --background --no-browser` (`instance.autostart_on`); on Linux and macOS it prints the systemd user unit (`hylly.service`; with lingering on, at the computer's start too) or the launchd agent for this computer, with the commands that install it, and installs nothing (`instance.logon_start`): the system then runs `hyllyd --in-background` itself, in the foreground, and starts it again if it fails. However it runs, the server writes `server.log` itself, with a size limit, and says the same on standard error (`instance.logged`). Every start of this computer's own server carries `--here` (`instance.HYLLY`), so it never goes to a server computer named in the settings instead.
- **Settings:** `[server]` in `settings.toml` (`listen`, `port`, `address`, `trusted_proxies`, `allowed_hosts`) are the server's only options. What's typed on `hylly serve` (`--port`, `--lan` for every IPv4 address, `"0.0.0.0"`, `--no-lan` for this computer only, `--library`, `--rules`) is for that one run in the foreground; `--background`, `hylly server restart` and the start at logon take the settings, and nothing remembers what was typed. A setting Hylly no longer reads is named once, with what took its place, and left out (`settings.RETIRED`). docs/ways-to-run-it.md has a block of settings for each way to run it.
- **Server page** (`/server`, `dashboard.py`): status, where it listens and the addresses for other devices (a browser's first, then the feeds, and with `address` set while it listens beyond this computer the plain one at home too, for a device that can't use it: `access.home_too`, as `hylly server status` and `hylly user link` have it), memory and CPU (psutil), devices seen and their apps, the tail of `server.log`, Restart and Stop, and whether it starts at logon, with the command that turns that on or off: the page writes no start-up entries itself. Everything it does is also a command: `hylly server stop`, `hylly server restart`, and `hylly server autostart on` or `off`.
  - **An owner's:** `/server` and `/database` answer the owner role only, from any device; everyone else, a borrower too, is told they're the owner's (403). Who may ask at each address is its row in `Handler.GET` and `Handler.POST` (its guards, `serve.Guard`), one rule for all: without a login 401, logged in but not for your role 403, and 404 only for what isn't there. A person's own writes (stars, reviews, a featured list) that their role or the settings don't allow are refused with 409, which the page's outbox lets go, as a 403 there means a stale key.
  - **Buttons:** POSTs carrying a key that is new at every server start and only in the page, plus a same-host `Origin` check, so other sites open in the browser can't press them.
  - **Roles** (`access.ROLES`, docs/architecture.md): each user's role is kept with them in the database (`account`); the first user is the owner, and a new user after that a reader (`access.add_user`). Borrower: reads in the page only, no file and no feed (`Handler._borrower_may`), e-books as pages drawn by MuPDF (`reader.BOOKS`); reader: no changes; librarian: `/api/tags` and `/api/fix` for one title (a merged title counts once), their own `/api/edits`; owner: several titles at once, `/api/suggest`, `/api/suggestions`, `/api/declined`, everyone's edits. The role is read on every request, so a lower one holds at once; `/api/session` says `role` and `can`.
  - **Logins** (`access.py`): every request needs a user, wherever it comes from, and a role is the same everywhere: nothing is decided by where a request comes from, which a proxy or a container in front would make look local. Only `/login` (the page, a one-time link's page and the form), `POST /logout`, `/healthz` (`ok`, for a health check), `/theme.css`, the app's manifest and its icons answer without one, after the `Host` check (421) and the cross-site check (403). Reading apps use HTTP Basic; browsers (they send `Sec-Fetch-Mode`, ask from one of the library's own pages by their `Referer`, or say Mozilla and take HTML) get `/login`, a form password managers fill in, and a session that ends after 30 days without use, a year after logging in at the latest: a random token in a cookie (`HttpOnly`, `SameSite=Lax`; over HTTPS `__Host-hylly`, `Secure`), stored only as its SHA-256 in the database (`browser_login`) with a stamp of the user's password hash, so a new password or a removed user ends it. A user keeps at most 20 (`access.SESSIONS_EACH`): one more ends their oldest. A browser opening a page without one is sent to `/login?next=…` (only paths on this server), and the login page, and the one-time link's, put the address's part after `#`, which no request carries, into `next`, so a place link (`#read=…`) goes on to its place; a page's own requests get 401 without `WWW-Authenticate`, so no password dialog, and the reader's own program files and fonts take a session only (`Handler._for_the_reader`). `/login` and `/logout` are POSTs whose `Origin`, when sent, must be this server. Both kinds are checked against salted scrypt hashes in the database (`account`). A one-time sign-in link (`access.sign_in_link`: `hylly user link NAME`, and at a terminal `hylly serve` and `hylly demo` for the one owner) is `/login?once=TOKEN`: opening it shows one button and uses nothing up; the button's POST uses it, once, within 10 minutes (`access.LINK_MINUTES`), while the user's password is the one it was made with. Only its digest is kept, beside the sessions, and the access log masks it (`once=-`). A verified Authorization header is remembered (by HMAC) until the user's password changes, so a page of covers costs one check. Ten failures from one address within 15 minutes refuse it for the rest of the 15 minutes (429): an IPv6 sender from outside by its /64, one inside by its own address (`access.sender_key`). Inside (`access.inside`, `access.INSIDE`): this computer, the private IPv4 ranges, 100.64.0.0/10, fc00::/7 and the link-local ranges, by the sender `client_address` works out, so a tailnet device through Tailscale Serve is inside and a visitor through Funnel or cloudflared, the public address the tunnel names, is outside. Past 10 failures for one name within 15 minutes, from anywhere, or 30 from all addresses together, a password from outside is checked only at its turn, 2 seconds apart (`access.SLOW_TURN`), waited for in the request's own thread for at most 4 seconds; a turn further off gets 429 at once, try again in a few seconds (`Gate._turn`). A sender inside never waits a turn, and still counts towards its lockout and the ceilings. Names are counted by a digest only. The address is the connection's own, or behind one of `trusted_proxies` (loopback as it comes) the nearest one in `X-Forwarded-For` or `Forwarded`, every line of them, that isn't a trusted proxy itself (`access.client_address`); from anyone else forwarding headers are ignored, and noted for `hylly doctor` (`serve.Noted`). The same trust decides the HTTPS flag (`X-Forwarded-Proto`) and the name the browser used (`X-Forwarded-Host`). Basic only encodes the password: beyond the home network it needs HTTPS (Tailscale Serve or Funnel, or a proxy that gives it).
  - **Access log:** one Combined Log Format line per request (GoAccess and fail2ban read it) in `access.log`, rotated at 5.2 MB; `/ping`, `/healthz` and the server page's own polling are left out. Only the last 30 days are kept (`access.LOG_DAYS`): older lines go from both files at the server's start, at a rotation by size, and at the first request of each new day (`access.AccessLog`), the log on or off. A name tried at a login is written only when it is a user's, otherwise only its length, `(an_unknown_name_of_9_characters)`, and so too in `server.log` and the alarm at a lockout (`Gate.tried`, `access.unknown_name`): people type passwords in the name field. The request line is cut to 2,000 characters, the Referer and the User-Agent to 200, their start and end kept around a `…` (`access.FIELD_MOST`), so a few huge requests can't roll the log twice. Every log, this one, `server.log`, `bell.log` and the runs' logs, is written one way (`storage.append_log`: moved aside beyond its limit, a move that failed tried again an hour later (`storage.MOVE_AGAIN`) and what one cut short left taken back in at the next, each line cleaned by `storage.shown`, the one cleaner: controls, U+0085 and U+2028/9 become `?`, and every format character (Unicode's Cf) goes but the joiners U+200C and U+200D), and read back split at line breaks only (`access.tail`). A line that can't be written is said once in `server.log`, after the alarms have seen the request.
  - **Restart** runs a detached `hylly server restart`, which stops this server and starts the new one. For a server the logon start runs on Linux or macOS, systemd or launchd is asked to restart it; one in a system-wide service ends itself with `instance.RESTART_CODE`, and the system starts it again (`instance.restart_through_system`). A stopped server can't be started from a web page; that stays with the launchers, the logon start and the command line.
- **OPDS 1.2 feeds:**
  - a root, with navigation by source, kind, game, genre and series (grouped by each title's series key, as the page groups them: `library.series_key`);
  - "recently added", the last 7 days by the date `catalog.first_seen` gave a title, and "recently bought";
  - OpenSearch, so Panels can search;
  - acquisition links that stream the files, with range requests.
- **E-reader feed** (`/ereader/opds`, `library.Device`): for e-ink readers that can add an OPDS catalog (KOReader, for one). A PDF is offered only from the sources in `pdf_from` (the shops with known publishers, by default), judged by the file's top folder. The same navigation and search, listing only titles of the allowed kinds (books, tech books) that have a file in an allowed format (the e-reader's formats under `[download]` that are books and flow to the screen: EPUB, then AZW3, then MOBI, and on) under a size limit (63 MB), leaving out titles whose device is a tablet (by a title's kind and main file, every title's: `catalog.device_of`; a ZIP package by the book inside it). Each entry offers just that one file. Its summary is an information text (format and size, series, genres, published, source, then the description), which KOReader shows as *Book information*; putting the format into the title instead would end up in KOReader's download file names ("author - title"). Rules: `[ereader_feed]` in `settings.toml` (`kinds`, `formats`, `max_mb`, `skip_tablet`).
  - **Books inside ZIPs:** StoryBundle ships each book as a ZIP holding several formats. The catalog records each package's book files once, from the ZIP's table of contents (`z` in the record; `inner` in the file cache), and the e-reader feed uses them after files of the same format outside a ZIP. The server unpacks the member while sending it, at `.../book.zip/inner/book.epub`: whole files only, since a range would mean unpacking up to it.
- **Caching:** files are sent with `Last-Modified` and `Cache-Control: no-cache`, and a 304 when unchanged, and the page's data.js with its `ETag` the same way, so a rebuilt catalog or a change shows on the next reload. The covers are the one exception: the page's data names each of the catalog's own thumbnails with its version (`?v=`, its file's time in nanoseconds: `library.cover_version`, from one listing of `catalog\covers\` for each data.js the server reads), and a cover asked for by the version its file has, as it is opened and read (`serve._by_version`), goes with `private, max-age=31536000, immutable` (`serve.KEPT_COVER`), so the browser keeps it and asks no more until a build makes it anew and the page's data names the new one. Asked for without it, or by another, a cover goes as any file does; the feeds, and `catalog\data.js` itself, name it as the build wrote it, so the reading apps get what they always did. The library page itself goes with an `ETag` of its text too, and is a 304 only for a browser that holds that very page, by its tag, or else by its `Last-Modified` exactly (`serve._same_page`): a browser holding another version's page, after the server went back a version, gets this one whole, never its own kept under this one's policy, which would run none of its scripts.
- **Access:** it listens where `listen` under `[server]` says: `127.0.0.1` as it comes, `"0.0.0.0"` or `"::"` for every address (`"::"` takes IPv4 too where the system lets it), or one of this computer's own; `--lan` is every IPv4 address for one run. One port: a tunnel or proxy points at it too. A request must call the server by one of its own names (`serve.Hosts`: `localhost`, any address itself, this computer's own name as the system gives it, plain, with a home network's suffix or as `<name>.<tailnet>.ts.net`, the name in `address`, and `allowed_hosts`), else 421; nothing is looked up, so no request waits on a name server. It refuses `state\`, `curation\` and paths outside the library; those two are told by the folder itself (`os.stat`'s device and file number), not by the spelling of the address, and by their names case folded as well; everything else, `catalog\`'s own files among it, by its plain name, as it is sent. A path is checked by its words before the disk is asked anything (`serve.plain_words`): `..`, an empty part and control characters are refused everywhere, and a colon, a backslash, a name ending in a dot or a space and a device's name (`aux.epub`) only on Windows (`paths.elsewhere_on_windows`, which `paths.inside_library` shares, and `paths.renamed_on_windows`); on Linux and macOS they are ordinary names. A name starting with a dot is served only when the last build listed that very file, by its path as resolved, exactly (`Catalog.lists`, from `data.js`, made from the database's `title_file`): on Windows that is the disk's own spelling, on Linux and macOS the spelling asked, so there the same path in other capitals is refused. So a shop's title or a folder of yours starting with a dot opens, and nothing in `.git`, `.Trash-1000`, `.stversions` and the other folders above does, at any depth, as no build lists them; nothing at the top of the library starting with a dot or `_` is served. `hylly doctor` names the catalog's files the server refuses (`serve.refused_files`). Every answer carries `Cross-Origin-Resource-Policy: same-origin`, and a browser's request that says `Sec-Fetch-Site: cross-site` is refused with 403 unless it is a GET or HEAD that opens a page (`Sec-Fetch-Mode: navigate`), so another site's page can't load `data.js` as a script, nor send a form, a login among them; reading apps send no such headers.

## Your own changes (`curation.py`)
- **Kept apart from everything generated.** `catalog\` stays safe to delete; the `edit` and `edit_title` tables of the database that keeps the library's records (`db.own`) are the one place your changes live. Catalog runs, the commands and the server only add to them.
- **One row per change** (`edit`, with its titles in `edit_title`), added and never rewritten: when, who (a login's name; `command line` for `hylly tag` and `hylly set`, not the computer's account name; `hylly catalog` for a reattach; a login's name has no spaces, so it is never one of these), the field (`tag`, or a correction below), the op (add, remove, decline, undecline; set, clear; reattach), the value, and the titles. The current state is the changes replayed in order (`curation.Edits`), which also gives the history. A change of a kind a version doesn't know is kept and ignored, so newer edits don't break older programs.
- **Titles are named by catalog id**, with the title and first file stored beside it. Humble and StoryBundle ids never change. A folder title's id comes from its first file's path, in one Unicode form (NFC) and lower case (`catalog.folder_id`), so a name that a Mac-made disk, a sync tool or an archive wrote with its accents apart is the same title, and a path already in that form keeps the id it always had. Which of a title's files is first is the same on every system: by path in that form, folder by folder and without regard to case, then as written (`catalog.path_order`), where Windows would list `Moonwake.epub` first and Linux and macOS `MOONWAKE.pdf`. After a move or rename `hylly catalog` moves your edits of an id no title has any more (and the day the title first came, `first_seen`) to the title that holds the copies the last build had merged with it (`title_alias`: a copy gone, the others still there), unless that title also holds a copy that was another title's then (a copy without an author can join another book's title once the copy it was merged with goes), else only to a title new in this build, never one already there: the one with the very same file (its path the same, in either form), else the one with a file of the same name and size as the last build had (`title_file`); one answer or none (`matching.Titles.follow`). It adds a `reattach` change. So a folder away for one build doesn't hand its `001.cbz`'s tags to another folder's `001.cbz`. Edits of ids nothing matches are kept and apply again if the title returns (`curation.placing` works it out alone, `reattach` writes it); the build says how many there are, and asks of each where it went ([The catalog's questions](#the-catalogs-questions), *which title?*): answered with a title, its tags and corrections go there (a `reattach` change by you, which `hylly decide NUMBER auto` takes back with a `detach`, putting back exactly what came, every mark of what was decided too, from where it is now: only a reattach made after it can have moved it on, `curation.Edits.chain`); *forget them* forgets them (a `forget` change, brought back by an `unforget`); *keep waiting* is the guess.
- **What a person keeps** (places, lists, bookmarks, reviews) is found when it is read, by the very same file, else the same file name, else the same title (`matching.Titles.find`); nothing of it is moved, so a title that comes back has its own again. Names compare in NFC and without regard to case.
- **Merged copies:** a merged record lists its other copies' ids (`ids`), and a title's tags are those of all its ids, so a tag stays when a new copy becomes the lead. A change that takes something away (a tag removed, a no taken back, a correction set back to automatic) also names the copies' ids, by the title's id (`copies`), and takes it from them too, so a tag or correction a copy had before it was merged under another lead can be taken off; what a change gives (a tag added, a no, a value set) goes on the title's own id, which counts for the whole title (a set value wins over its copies'; `curation.Edits.apply`).
- **Where tags show:** the server lays the edits over the catalog it has read from `data.js` whenever either changes (`library.Catalog`), for the page's data.js, search and the OPDS feeds (By tag, and categories). Nothing else holds a copy of them, so the page can't fall behind the database. A server on a computer that doesn't keep the library's records can't read them, and shows the catalog as built.
- **Tags** compare without regard to case and keep the spelling they were first given.
- **Editing in the page** (served by `hylly serve`): the page asks `/api/session` whether it may edit. Librarians and owners may (*Roles*, above), wherever they log in; everyone else only reads. Changes go to `POST /api/tags` (`op`, `tag`, `ids`) with the editor's own key from the session (their name signed with this start's secret) and a same-origin `Origin`, and come back as the titles' new tags. Undo is the opposite change on exactly the titles that changed; `/api/edits` lists the latest changes for the Changes list. Group tagging (bundle, folder, series, or everything found) opens a ticked preview first.
- **Suggestions** (the words in `curation\tags.toml` in the library, the queue in the database's `suggestion` table): each tag's name plus its `keywords` (word-start matches; phrases match words in a row), blocked by `not` words. Looked at, in this order: bundle, folder, collection, series, title, subjects, and with `description = true` the description. The fields a group shares come first, so a bundle's titles share one reason and can be reviewed together. `hylly tag suggest` or `POST /api/suggest` finds the queue afresh, in place of the one before, leaving out every title and tag already decided; `GET /api/suggestions` gives what's still unanswered.
- **Declines:** `decline` edits record a "no", and `undecline` asks again. A title and tag count as decided once added, removed or declined, so a removed tag isn't suggested again either. Adding always overrides an earlier no.
- **One-value corrections:** field `kind` (a kind in the rules; it steers downloads too: a title not downloaded yet comes as that kind, [downloads.md](downloads.md)), `ereader` (the e-reader feed: always, never) or `format` (the Humble format to keep: `plan.for_library` reads it, so it changes what `hylly download` fetches, and a PDF master makes the title a tablet one; cleared, the order under `[download]` decides for a title not downloaded yet, and one downloaded keeps its format), op `set` or `clear` (automatic again), with each title's previous value in `was` so undo is exact. Two more come from answering the downloads' questions ([downloads.md](downloads.md#questions-what-the-rules-cant-settle), `hylly decide`): `file` (the file to keep of a Humble title, by its name as Humble lists it, which its plan takes over a format; for an item with no book of its own, the file that makes it a title: `hylly set file NAME --id ID` makes one too) and `answers` (a title's answers that no other correction says, by the question: keep the guess, I moved it, the same book or two, a lookup's match used or refused, a folder's files books or not), each taken back with `auto` (all of a title's), or one by its question with `hylly decide NUMBER auto`. An edit of answers is a whole title's (op `set`), or a few keys on several titles at once (op `update`: two copies' answer is on both; `hylly set copies apart` and `hylly set refused` are on every id of the card). The library page's Recent changes says those two in words (`curation.history`'s `said`), and its Undo puts back exactly what was (the owner's: `/api/fix` takes a title's answers as a dict, and `undo: true`, which brings a value back in its place, so a format set again by an undo is as old as it was and a file chosen after it stays the one kept). A file answer keeps its option's format with it (`format`), so a file listed without an extension is overridden only by a format of another sort (`Edits.overridden`). `hylly set` takes a shop's title not in the catalog yet by `--id` when a question or the shop's newest snapshot names it. A merged title's lead wins over its copies. The server lays them over the catalog with the tags: `kind` replaces `k`, and the e-reader feed obeys `ereader` (always: any file of the feed's `formats`, then of the e-reader's under `[download]`, of any size, if the rules find none). The page gets them laid over its data.js, and edits them with two lists in the details and the same group preview (`POST /api/fix`, `hylly set ereader`), whose answer is each title as the page gets it. The session also lists the e-reader feed's titles, for the page's e-reader feed filter.
- **Details:** field `title`, `authors` (a list), `series`, `number`, `year` or `publisher` (`curation.TEXT`), op `set` with any text (empty: none) or `clear`. The server lays them over `data.js` (`Catalog.get` keeps what the catalog found in `_found`), so the page, the search, the series lists and both feeds use them. Files are never changed.
- **Possible next:** reading status (to read, reading, read), as another one-value field.

## The catalog's questions

What the catalog's rules can't settle by themselves, a complete build (`hylly catalog`, and the Inbox's pass, which builds as it does) guesses and keeps as a question for you, in the same list as the downloads' ([downloads.md](downloads.md#questions-what-the-rules-cant-settle)): the table `question`, under the shop `catalog` (`curation.CATALOG`), through `curation.keep_questions`. Each kind's finder is a plain function of what the build has (`catalog.questions_of`: its copies before and after `merge_copies`, the lookups' answers, your edits, the titles gone, the files of your folders it passed over), so the check tool can count them offline on the last build. A build no longer finding one takes it off the open list, but for the files questions of a folder it could read only in part (a subfolder passed over just now); one answered stays on the answered list while its answer stands and its subject is there (two copies found by their ids or first files, the title, the folder: `catalog.subject_gone`), its answer's edit staying as it is either way; nothing is asked twice. With nothing answered, every build makes the very catalog it made before. The build ends with "N questions to decide" as a shop's run does, and a line of its own for the near matches (below). The catalog's answers are kept in a field of their own (`catalog`), apart from the downloads' (`answers`).

- **A used match that is wrong** needs no question: `hylly set refused openlibrary --id ID` (or *(not this book)* beside the source in the title's details) refuses it, an edit on every id of the card: that source's answers give the title nothing, it isn't asked about it again, and the next source in the order is asked as if it had found nothing; `hylly set refused auto` takes the refusals back. A hand-written `refused` line in a source's cache says the same, and is read too.
- **Who:** these answers, and *Not one book* (`hylly set copies apart`), are the owner's alone, as the format and the file to keep are: `/api/fix` refuses `copies`, `refused`, `answers` and `catalog` to anyone else (403), and the page shows their buttons only to the owner (`EDIT.manage`). A title's answers go to `/api/fix` as a dict only with `undo` (an Undo's), else `auto` alone, as `hylly set answers auto` takes them.
- **Undo:** the toast's Undo of *Not one book* or *(not this book)* undoes that one change (its `update` in the answer: each id's keys back to what they were, `curation.undo_update`), never with auto, which would take back your other answers about those copies or sources; Recent changes' Undo of an edit of a few answers (op `update`) is the same, key by key on each id it names, a copy's too. A reattach, detach, forget or unforget (a title gone's tags put elsewhere, or forgotten) is listed in words with no Undo: `hylly decide NUMBER auto` takes its answer back.
- **Where they show:** `hylly decide` and the Server page's To decide, for the owner, with the downloads' (an answer from either is the same edit), the quiet near matches left out but for a short line counting them ("and N near matches from the lookups, in each title's details (hylly decide --kind match)"); hylly decide's `--kind` lists one kind alone (`hylly decide --kind same`, say), and `hylly decide --kind match` the near matches. The library page shows the owner alone a count, *N to decide* in Library management (`/api/session`'s `toDecide`, a number), linking to it; a title's details ask for its own questions as they open (`/api/questions?id=ID`, the owner's: 403 for anyone else), a near match with *Use it* (`POST /api/decide`, the page's key, as the Server page answers) and *Not this book*, any other with a link to To decide. Your word on a lookup's match follows a title that moved in the very build that moves it.
- **A kind more** is a row in `curation.QUESTIONS`, its finder in `catalog.questions_of` and, if its answer is no file, answers code, reattach or forget, a line in `curation._made`.
