How to run the commands

One at a time: a catalog build, a copy with hylly add or hylly copy, a backup, a lookup or a download from one shop runs once at a time, also across computers that reach the library through a share. A second is refused and told where the first runs, and hylly jobs stop NAME ends one that has hung (hylly jobs names each one running). One refused by a run on another computer, or under other settings on this one, is told of that run's note, in the library's state\locks, and how long it has been as it is when that's an hour or more: if that computer isn't running the job (it was switched off mid-run, say), delete the note, and the job goes. A job on the computer that has the disk itself and one coming through a share to that computer don't see each other, so don't start the same one on both at once.

Open a terminal, in any folder (on Windows: Terminal from the Start menu), then type the commands below. Every hylly command works on the library at {{library}}.

One program, hylly, takes every command, and a command with actions takes one after it, as in hylly humble download or hylly server status. Each command and action has its own --help, and takes only its own options, written in full: an option it doesn't take, or one shortened, is refused. hylly alone shows where to start, and hylly --help lists every command by what it's for. Every command that changes something does it at once, and with --dry-run (-n) only says what it would do, changing nothing. -H HOST and --here, which choose the computer a command runs on, go before the command (From another computer). Beside it, hyllyd is the library server itself, and only that: hylly serve starts it for you, hylly server looks after it, and a service starts it as hyllyd --in-background, with the settings as its options. The server's code can't reach the shops' logins, nor the code that talks to the shops: docs/architecture.md, in Hylly's source, tells how the code is kept in parts.

Installing it: Hylly is a command-line tool, installed as any other is with uv, which brings a Python of its own, and fetches Hylly with git, which must be there too. One command, the same on every system, installs it, and installs it again over itself for an update:

{{install}}

It puts hylly and hyllyd on the PATH, in uv's own folder for commands (%USERPROFILE%\.local\bin on Windows, ~/.local/bin on Linux and macOS; uv tool dir --bin says which, and uv tool update-shell adds it to the PATH if it isn't there yet), with a Python and libraries of their own, apart from any other program's. uv takes no lock file for a tool, so the two files from Hylly's own address give it the versions of its libraries that Hylly was tested with, which the weekly check for published flaws goes by (tool-constraints.txt), not just the newest of each, and leave out what a library would bring along that Hylly never uses (tool-overrides.txt). No folder of the program's is needed: Hylly keeps its own files where Where things are says. Keeping it up to date has the update, and uv tool uninstall hylly takes it away again (Stopping using Hylly). To work on Hylly itself, from a checkout of its source, CONTRIBUTING.md there tells how.

Sizes and how long: the size of a file or a disk counts as disks are sold and as macOS shows it, so 1 GB is 1,000,000,000 bytes and 1 MB 1,000,000; Windows' Explorer, which counts in 1,024s, shows the same file about 7% smaller. The commands, the library page, the server page and the feeds say it in the largest unit it has at least one of once rounded to one decimal, such as 350.2 MB or 1.4 GB, and so does this page of the limits Hylly keeps by itself, such as 12.6 MB. The settings and options that set a size count in thousands too: cache_gb, max_mb and image_heavy_mb in the settings, prose_max_mb in the rules, --max-gb and --mb; the defaults of the last three (63, 21 and 8.4 MB) are where they keep the limits they had when they counted in 1,024s, and cache_gb's 10 is now 10,000,000,000 bytes, so the reader's cache keeps about 0.7 GB less. Memory counts in 1,024s, as the systems show it (memory_mb, the server page's memory), and so does a shop list's MB column, so that the lists written before still match. How long something took, or should take, is in minutes up to 89 (under a minute, 89 minutes), then in hours (1.5 hours).

Every command and option is listed under Every command and option below, and hylly COMMAND --help shows the same in the terminal. hylly --version says which version of Hylly you have, such as hylly 0.1.0. Your own settings (where the library is, your StoryBundle account, your own folders) are in {{settings}}. Downloads can be stopped with Ctrl+C at any time; running the command again picks up where it stopped.

Opening the library

Every device logs in, this computer too: a browser at the login page, once, and a reading app with a name and password. How other devices reach the library is up to you: Ways to run it.

  • On this computer: run hylly serve. At a terminal, it shows a one-time link that logs you in as the owner, while the library has one owner, and opens it in the browser on Windows and macOS, or where there is a desktop (DISPLAY or WAYLAND_DISPLAY set); over ssh to a server it opens none. The library page always comes from the server, which lays your tags and corrections over the catalog as it sends it, and has the reader: opened straight from a folder, a copy of it only says to run hylly serve and open the address it shows.
  • On a tablet or an e-reader: a device with Tailscale uses the HTTPS address of Tailscale Serve, at home and away, and the server can go on listening on this computer only (A home server). A device without Tailscale needs the server to listen on the home network: set listen = "0.0.0.0" under [server] in {{settings}} (hylly settings edit), then hylly server restart. For one run in a terminal instead, with no server running: hylly serve --lan, until Ctrl+C. Its window, and hylly server status, show the addresses to use: In a browser first, then the reading apps' feeds, and with address set, the plain one too, as Home network, for a device without Tailscale.
    • Once only: add an OPDS catalog at that address (it ends in /opds, such as http://192.0.2.10:{{port}}/opds) in each reading app, with your name and password, for example Panels for comics and Yomu for books. The app then browses and searches the library like a shop, and downloads whole books, which stay readable without a connection, on a journey for example. Recently added, at the top, has what came in the last 7 days; above it come Featured and the owner's lists ticked for the reading apps, if there are any (see Your lists). After Recently bought come Best rated, from everyone's stars as the library page ranks them, while stars are on, and Most read: the titles at least two people have read in, the most first, so that one person's reading isn't shown to everyone; it says how many, never who. A listing of more than 100 titles, a genre or a source say, starts with an A to Z index, by series or else title, with All first; so does Series when there are more than 100. A search's answer stays one list. When Windows asks whether Python may accept connections, allow private networks only.
    • On an e-ink reader, use the e-reader address, which ends in /ereader/opds. It lists only books that suit an e-ink screen, so no comics or picture books, and offers each one's best file: books and tech books with a book file that flows to the screen, the first of EPUB, AZW3, MOBI and the like in the e-reader's order (ereader under [download], as a book's download goes; no PDF and no plain text), under 63 MB by default ([ereader_feed] in the settings), leaving out those Hylly suggests reading on a tablet (by their kind and their file, see your choices). StoryBundle books, which come as ZIPs, are offered as the EPUB inside. In KOReader, tap a book: Book information shows the format, size, series, genres and description, and Book cover shows the cover. The rules are under [ereader_feed] in your settings (see settings.example.toml); restart the server after changing them. To see what the e-reader gets, use the library page's E-reader feed filter (Listed or Not listed); to overrule the rules for single books, see Correcting kind and the e-reader feed. E-readers that can add an OPDS catalog use it; KOReader is one that can.
    • Your own feed: both feeds are the logged-in person's own. Each starts with what's yours: Continue reading (what you're in the middle of, the latest first, as on the library page), your reading list, and your own lists ticked Show in reading apps (see Your lists); then the whole library. Where you've got to in an app stays the app's own: the library page doesn't hear of it. A borrower has no feeds. A feed's address opened in a logged-in browser goes to the library page.
    • Write the address in full, starting with http://, or https:// for an HTTPS address. Without it, some apps (Yomu) try a secure connection and fail with “A TLS error caused the secure connection to fail”.
    • At the plain home address, the device and this computer must be on the same home network. Away from home, use the address of Ways to run it instead.

Ways to run it

Hylly runs on Windows, macOS and Linux: on the computer you read on, on a server at home, or open to the internet. Whichever way, every request logs in, wherever it comes from, this computer, the home network, a VPN, a tunnel or a proxy, and each user's role is the same everywhere (Logins). What changes is where the server listens (listen under [server] in {{settings}}), the address people use (address), and what stands in front of the server to give it HTTPS. The address people use, as this server has it: {{address}}. The same, as a page of its own: docs/ways-to-run-it.md in Hylly's source.

First, whichever way: on the server computer, hylly user add NAME makes you the owner, as the first user is, and hylly serve at a terminal shows a one-time link that logs a browser in as the owner, and opens it on Windows and macOS, or where there is a desktop (DISPLAY or WAYLAND_DISPLAY set). Every other device logs in once.

One computer

[server]
# listen = "127.0.0.1"    as it comes: this computer only

Nothing to set. The server listens on this computer only, at http://127.0.0.1:{{port}}/, so no other device reaches it, and nothing crosses a network.

A home server

For the tablets, phones and e-readers at home, and your own devices away from home, with HTTPS everywhere through Tailscale Serve. Tailscale is a VPN with a free plan. Once you are the owner (above), step by step:

  1. Put Tailscale on the server computer and on every device that can run it, all in the same Tailscale account.
  2. At the server computer, turn Serve on: tailscale serve --bg {{port}}, with Tailscale's command for that system. tailscale serve status then says the address, https://….ts.net.
  3. Put that address in address under [server] in {{settings}} (hylly settings edit), and for a device at home that can't run Tailscale, listen = "0.0.0.0" too, as below. Then hylly server restart.
  4. On each device, open that address and log in, once. In a reading app, add it followed by opds (an e-reader: ereader/opds), with your name and password.
[server]
listen = "0.0.0.0"                                # every IPv4 address: for a device at home that can't run Tailscale
address = "https://lantern-pc.tail1234.ts.net"    # the address people use: what tailscale serve status shows
tailscale serve --bg {{port}}          # on
tailscale serve status             # on? at which address
tailscale serve --https=443 off    # off

Tailscale's command: on Windows "C:\Program Files\Tailscale\tailscale.exe", in PowerShell with & before it. On Linux it's tailscale, and serve and funnel need sudo before it, unless you once run sudo tailscale set --operator=$USER. On macOS, the App Store app's command is /Applications/Tailscale.app/Contents/MacOS/Tailscale, which isn't on the PATH. The first time, Tailscale asks you at a link to turn HTTPS on for your account, and for Funnel to allow Funnel too. Both are part of Tailscale's free plan.

  • HTTPS at home too. Use the https://….ts.net address on every device with Tailscale, at home as well. The plain home address (http://192.0.2.10:{{port}}, say) carries names, passwords and books across the Wi-Fi as they are. Nobody outside your Tailscale network can reach the Serve address, and no port is opened on your router. Serve runs on this computer, so its forwarding headers count as they come (trusted_proxies): the lockout after wrong passwords and the access log see each device's own address.
  • address is what the server's start, hylly server status, the Server page and the one-time links show other devices, and this page above. It is also a name the server answers to, which this computer's name in Tailscale may not be otherwise.
  • A device that can't run Tailscale, an e-reader with KOReader for example, uses the plain home address with a name and password, such as http://192.0.2.10:{{port}}/ereader/opds with this computer's own address at home in it. That is what listen = "0.0.0.0" is for, and then, with address set, hylly server status, the Server page and hylly user link NAME show that one too, as Home network. With Tailscale on every device, leave listen as it comes, as Serve reaches the server on this computer. Give such a device a reader account of its own (hylly user add NAME --role reader): what could be read off the Wi-Fi is then a login that only reads, and its password can be changed, or the account removed, without touching yours.
  • The firewall: private networks only. When Windows asks whether Python may accept connections, allow private networks, never public ones.
  • Or without Serve: with listen = "0.0.0.0", your devices with Tailscale can also use this computer's Tailscale address, http://100.x.y.z:{{port}}/ (tailscale ip -4 shows it). They log in there as anywhere; Tailscale encrypts the way, though the address is HTTP.
  • hylly serve --lan listens on every IPv4 address for that one run, in its terminal, without the setting; a restart takes the settings again.

Open to the internet

For an e-reader or a friend's device away from home, which can't run Tailscale: Tailscale Funnel, or an HTTPS proxy of your own (Caddy, nginx, a domain of yours), pointed at the one port. Hylly is tried most behind Tailscale. Step by step, with Funnel:

  1. Give every user a long password (hylly user add NAME, at the server computer only), and set up the alarms on your phone, for wrong passwords and new devices.
  2. At the server computer, turn Funnel on: tailscale funnel --bg {{port}}, with Tailscale's command for that system. tailscale funnel status then says the address.
  3. Put it in address under [server] in {{settings}} (Funnel needs no change to listen), and run hylly server restart.
  4. Run hylly doctor: it says whether it's all set up safely (below).
  5. On the device away from home, open that address and log in. In a reading app, add a catalog at it followed by opds (an e-reader: ereader/opds), with the name and password: it starts with https:// and has no port.

A proxy of your own takes Funnel's place in the second step (below), and the address is then yours.

[server]
listen = "127.0.0.1"                       # as it comes: the tunnel or proxy is on this computer
address = "https://books.example.org"      # or the https://….ts.net address Funnel gives
# trusted_proxies = ["127.0.0.0/8", "::1", "192.0.2.20"]    # only for a proxy on another computer: its address too
tailscale funnel --bg {{port}}          # on
tailscale funnel status             # on? at which address
tailscale funnel --https=443 off    # off
  • Funnel gives the same https://….ts.net address to the whole internet. The login page is then on the public internet. New addresses are listed openly, so scanners try them within minutes. They get only “login needed”, and the access log shows them; after 10 wrong passwords within 15 minutes an address waits 15 minutes. Turn Funnel off when nobody needs it.
  • With Funnel, as with Serve, there is nothing more to set: logins through them are what Hylly is tried with most.
  • A proxy of your own gives HTTPS, points at the server's one port, and hands on three things: who sent the request, in X-Forwarded-For (set, or added to); that it came over HTTPS, in X-Forwarded-Proto; and the name the browser used, as the Host it came with or in X-Forwarded-Host. Without that name, the login form's own address (its Origin) isn't one of the server's, and the login is refused (403). Caddy does all three as it comes. nginx as it comes does none of them, and sends Host as the address it proxies to, so its location needs: 
    proxy_pass http://127.0.0.1:{{port}};
proxy_set_header Host $host;                                   # $http_host when the address has a port
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
    A proxy on this computer needs nothing more in the settings. One on another computer or in a container needs listen to reach it ("0.0.0.0", or this computer's address on that network) and its own address in trusted_proxies, as uvicorn's forwarded_allow_ips, Jellyfin's known proxies and Home Assistant's trusted_proxies do: only those proxies' forwarding headers count, for who sent a request (the lockout, the access log), whether it came over HTTPS, and the name the browser used. Behind cloudflared, proxy_header = "CF-Connecting-IP". A name the proxy calls the server by, other than an address or the name in address, goes in allowed_hosts.
  • hylly doctor says where the server listens, the address people use and who can log in, and notes an address that isn't https, forwarding headers from an address not in trusted_proxies, and wrong logins from a proxy that names no sender.
  • On Linux, walled in: examples/hylly.service runs the server as a system-wide service with most of the computer out of its reach (The library server). Its SocketBindAllow names the one port, the settings' port: hylly serve --service-file prints the service with this computer's own. hylly doctor says when a server runs outside those walls, and how to start the walled one instead, and notes an address set while the server has no walls around it.
  • On Windows and macOS there are no such walls: the server runs with the rights of your whole account, so a flaw in it, in reading a book say, could reach your own files, and the shops' logins and the lookups' keys saved in the logins folder. Two ways keep more out of its reach, each its own part. A separate standard account for Hylly, the server and the downloads alike, keeps your own files out of it, but not the logins the downloads use there; and the server's start at logon then runs only while that account is logged in (switching users keeps it so). Keeping the shops' logins on another computer, and giving one only to the download that needs it, in its variable in the environment (HYLLY_HUMBLE_SESSION and the others in settings.example.toml), keeps the logins out, as none is saved where the server runs. hylly doctor says so when an address is set and logins are saved there.
  • This computer must be on and awake, with Tailscale and the library server running. Both start at logon, and Serve and Funnel stay on after a restart. Big comics take longer than at home: they come over the home connection's upload, and through Funnel by way of Tailscale's servers too.

The library server

A small program that serves the library to the browser and the reading apps. It runs hidden in the background, or on Linux and macOS under the system's own care, and keeps running until stopped; unused, it takes about 70 MB of memory and practically no CPU. Only one ever runs: the launchers use the running one, and a start while one runs says where it is and changes nothing. This computer, in this help and in the library, is the one the server runs on.

The server page: for an owner, the library page's Manage menu has Server (/server; on this computer http://127.0.0.1:{{port}}/server), on any device the owner logs in on. It shows how the server is doing, one part at a time, in tabs that stay at the top as the page scrolls (on a phone the row of tabs scrolls sideways): To decide, with how many are open, and Removed, each while it holds anything; Addresses, where it listens and the addresses for other devices, a browser's first and then the reading apps' feeds, and its address on the server's own computer only when you look from that computer; How it runs, with memory and how the reader's pages came; Devices, which used it, the one you look from and the server's own computer marked; Alarms, Access log and Messages. The tab shown is in the page's address (/server#decide, #removed, #addresses, #running, #devices, #alarms, #access, #messages), so a link opens that one; with none, it opens on To decide when there are questions, else on How it runs. ← and → go from tab to tab. It has Restart and Stop. Whether it starts at logon the page only says, with the command that turns that on or off: a web page doesn't write the system's start-up entries. Anyone who isn't an owner is told it's the owner's page. The same from a terminal:

hylly server status          # running? where, and since when
hylly server stop            # stop it
hylly server restart         # stop and start again with the settings, after a program update or a change to them
hylly server autostart on    # start it at every logon (off: no longer)

The start at logon: on Windows, hylly server autostart on makes a task in Task Scheduler that starts the server in the background at every logon, with the settings, and starts it now. On Linux and macOS the system runs the server, as it does any service: the command prints the systemd user unit, or on macOS the launchd agent, with this computer's folders filled in, and the commands that install it, and installs nothing itself. Its output, as it is, is the file, and the commands it prints save it in its place and turn it on (systemctl --user enable --now hylly.service, or launchctl bootstrap). The server then runs in the foreground: its messages go to the system's journal (journalctl --user -u hylly) as well as its log, and the system starts it again if it fails. For a Linux computer that nobody logs in to, such as a server, it also has to start with the computer: that goes for all of your services, so it's yours to choose, and the command says how. macOS asks once whether Python may run in the background. There, hylly server autostart off prints how to take it away again. After hylly server restart or the server page's Restart, the system still looks after it.

Not as root: on Linux and macOS, no command of Hylly's runs as root or through sudo, but for hylly doctor, which says so. Where it truly can't be otherwise, such as some containers, HYLLY_ALLOW_ROOT=1 lets it. hylly doctor also says when something in Hylly's own folders isn't yours, as a command run with sudo leaves behind, or is open to others on this computer, and gives the command that puts it right.

A server open to the internet, on Linux: examples/hylly.service runs it as a system-wide service with walls around it. Of your folders it sees only the library, Hylly's own folders (its settings only to read) and the program, it can gain no rights, and it can't start other programs through their sockets. It can still read what any user may in /etc and /usr, and reach the network, and it can change the library and Hylly's records, so a flaw in it could still do harm there. hylly serve --service-file, run as the user the server is to run as, prints it for this computer, filled in from the settings (that user, the library, Hylly's own folders, the program and the port), with the commands that install it in place of the start at logon, which copy it to /etc/systemd/system/ with sudo, yours to type: the command itself installs nothing, and writes nothing of its own (as every hylly command, it makes Hylly's own folders and secrets if they aren't there). Or fill in your own folders as the file says. hylly doctor says when the one installed doesn't match the settings: the user it runs the server as, the library, the port, each with its line and the line it wants. It reads the unit where systemd finds it first (/etc/systemd/system, /run/systemd/system, /usr/lib/systemd/system), and its drop-ins in hylly.service.d and service.d there and where systemctl set-property keeps them (system.control); the library is the one the service's Environment= names in HYLLY_LIBRARY, else the settings' own. What it can't tell from the files, an EnvironmentFile= say, it says it didn't compare. hylly server restart and the page's Restart then work as usual: the server ends with code 75, which the unit's SuccessExitStatus and RestartForceExitStatus lines take for a restart, not a failure. It starts with the computer. Nothing else may start a server then, as it would run outside the walls: after a stop, sudo systemctl start hylly, with sudo systemctl reset-failed hylly first if that says it started too often. Options on the command line are refused: its options are the settings, as for any server in the background. Commands such as hylly catalog or a download are outside the walls, as they are what you run yourself, and they don't take a 7-Zip that's in one of Hylly's own folders or the library, where the server could put one. The shops' logins and the lookups' keys are in the logins folder, which the walls hide from the server: it needs none of them; so is what long jobs started from another computer said. The settings folder, with settings.toml, the rules and the alarms' ntfy address and token in its secrets folder, the server may read and not change. The service starts the server itself, as hyllyd --in-background, which writes its log itself, in the state folder the walls let it write, and to the system's journal too (journalctl -u hylly). Every folder the file names must be there before the server starts: any hylly command run as that user makes Hylly's own, and its secrets. One printed for an install that keeps everything in one folder also names settings.toml there, which hylly settings edit makes, and your rules and themes folders with a -, as nothing makes those for you. A service made from this file when Hylly kept everything in one folder, ~/.local/share/Hylly, names that folder, and the program's folder as its working one: it goes on working as it is, as Hylly keeps using that folder all in one while it holds Hylly's files; examples/hylly.service names a folder for each kind instead, runs in the data folder, and needs no program's folder (Where things are).

  • Its settings are in the [server] part of {{settings}}: name = "Our Library" is what the library calls itself, in the browser's tab, the page's heading, at the login and in the e-reader feed (the server reads it when it starts; an icon already on a home screen keeps the name it was added with); listen = "0.0.0.0" serves the home network, and address is the address people use (Ways to run it); port is 8770 as it comes, and this server's is {{port}}; source_url is where this Hylly's source is, which its Source links lead to: Hylly's own as it comes, for a changed version run for others its own (Licences and source). They are the server's only options. What's typed on hylly serve, such as --port or --lan, is for that one run, here in the foreground, and nothing keeps it: a server in the background, restarted, or started at logon takes the settings, and --background takes no options. With a server running already, hylly serve with options leaves it as it is and ends with exit code 4, naming a port, a library, where it listens or rules files it doesn't have (It runs on port 8770, not 8771). Restart it after changing the settings. It never stops by itself.
  • Its messages (started, stopped, errors) are in {{server_log}}, however it runs: the server writes them there itself, and beyond 1.0 MB moves the file to server.log.1, the one before that going. They are on standard error too: in its terminal, or under a service in the system's journal. hylly logs server shows the end. A mistake in a rules file or in the settings stops it as it starts, and the message says where; the command that started it shows it too. A rules folder that isn't there yet, on a share that comes up later, doesn't stop it: it reads the rules once they are there.
  • hylly serve without --background runs it in that terminal instead, until Ctrl+C.
  • When it's stopped, the server page can't start it again (a web page can't start programs): run hylly serve --background.

Its periodic jobs: the server makes the nightly copy of the database and the settings, looks every minute for what the alarms watch (users changed, a library out of reach) and sends the daily summary, says in its log as it starts what is worth updating, keeps its address at home up to date for the pages, and passes over the Inbox once a minute. A job that fails is said in one line in its log and tried again when it's next due: it never stops the others, nor the server. To have a timer run them instead, as a container or a systemd setup may want, set jobs = "external" under [server]: the server then leaves the nightly copy and the alarms' look to hylly server jobs, which runs what's due and ends, and something must start that every minute, such as examples/hylly-jobs.timer with its hylly-jobs.service (walled in as the server is), a line in cron, or Task Scheduler. It runs the alarms' look itself, and starts the nightly copy as a program of its own, which it doesn't wait for, so the alarms go on every minute while a copy takes its time; a copy still running after two hours ends itself, and one that fails or ends so says it in {{bell_log}}, as a long job does; each job has a lock of its own, so one still running isn't started again. hylly server jobs --dry-run says which are due. With jobs as it comes, it runs nothing and ends well, as the server runs them. What only the running server can do (its own alarms held back, its address at home, the update check) it does either way. With jobs = "external" the timer runs the Inbox too. The Inbox is the other way round as well: a server walled in can't run it, so beside such a server hylly server jobs runs the Inbox, and nothing else, even with jobs as it comes, and says nothing when there was nothing to do. That the server itself is down it can't say: that's for systemd's OnFailure=, or a container's health check of /healthz.

Logins and the access log

Every request logs in, wherever it comes from: this computer, the home network, a VPN, a tunnel or a proxy. Where a request comes from never lets it in, and each user's role is the same everywhere. Only the login page and what it needs (its colours, the app's icons) answer without a login, and /healthz, which tells a health check ok and nothing more.

  • The first user is the owner: hylly user add NAME on the server computer, while there are no users, makes the library's owner; every user after that is a reader, unless --role says otherwise. Until there is a user, nobody can log in, and the login page says what to do.
  • A browser shows the login page, once, and then stays logged in (below). A reading app is asked for a name and password, which you give it with the catalog's address.
  • A one-time link logs a browser in without the password: hylly user link NAME makes one for NAME, at each address the library has. It works once, within 10 minutes, and only while NAME's password stays the same. hylly serve, with or without --background, and hylly demo, run at a terminal, show and open one for the owner, when there is one owner; a server started out of sight (the hidden server itself, the start at logon, a system service) shows none, as its log would keep it. Opening the link shows a page with one button, Log in as NAME, so a chat app's preview of the link uses nothing up. A link that has been used, or is too old, gets the login page, which says so.
  • The lockout: after 10 wrong passwords within 15 minutes, that address is refused for 15 minutes. An IPv6 address counts together with the rest of its block (its /64), which one home or one machine is given whole, so a guesser can't take a fresh one at every try; devices at home that reach the server over such an address share one count. IPv4 addresses, Tailscale's and a home network's own IPv6 addresses (starting fd or fe80) count each on its own.
  • The slowdown: past 10 wrong passwords for one name within 15 minutes, from anywhere, or 30 from all addresses together, each try from outside waits its turn, 2 seconds apart, so someone guessing from many addresses gets one try in 2 seconds. A try whose turn is further off is told to try again in a few seconds: while someone guesses past that many from outside, a fresh login from outside may be told so too, until it gets a turn. At home and on your Tailscale network, by their own addresses (the home network's, Tailscale's, this computer's), no try waits, so a stranger can't keep you out there; a device that comes in through the public Funnel address, or over the home's public IPv6, counts as outside. A browser already logged in, and a reading app whose login the server remembers, go on as ever, and a few typing mistakes never come near it. The server's log says when it starts.

What each user may do is their role:

BorrowerBrowse, search and read in the library page, and nothing more: no files, no reading apps. A title's details show its files without links, and the server refuses every file of the library and both feeds, however the address is written. E-books come to a borrower as pages drawn on the server, like a PDF's, so the book's file never leaves the library; in that reader the text can't be searched or restyled. AZW3 books can't be drawn that way, so a borrower can't open a title that is only AZW3.
Reader (every user after the first, unless you say otherwise)Browse, search, download and read; nothing they do can change the library.
LibrarianAlso change one title at a time: its details, tags, kind, e-reader feed and format, with undo; Your recent changes in Manage.
Owner (the first user)Everything: many titles at once (Edit these…, a whole series, bundle or folder), and the library's management in Manage: tag suggestions, everyone's recent changes, and the Server page and the Database page, on any device the owner logs in on.
hylly user add NAME                    # the first is the owner, the rest readers; asks for the password twice
hylly user add NAME --role librarian   # with a role
hylly user add NAME --role borrower    # reads in the page only
hylly user add NAME                    # again: a new password, which ends their logins; the role stays
hylly user add NAME --password-stdin < password.txt   # the password from a file or a pipe, for a script
hylly user role NAME owner             # another role: borrower, reader, librarian or owner; asks first
hylly user link NAME                   # a one-time link that logs a browser in as NAME, at a terminal
hylly user list                        # names and roles
hylly user remove NAME                 # what's kept about them is kept aside (What's kept about you)
hylly user restore NAME                # a removed user back, with it: a new password, while nobody has the name
  • hylly user add is for both, a new user and a new password: before it asks for the password, it says which (New user NAME (reader), or NAME exists: this sets a new password for them, and ends their logins elsewhere), and a name it can't take is refused before anything is asked: one no user can have, or a removed user's while what was kept of them is kept aside (What's kept about you).
  • Users and roles take effect at once, on every device: a lower role holds from that user's next click. With users but no owner, nobody has the library's management: hylly user list and hylly doctor say so. hylly user role asks first, as a role says what a user may do: with nobody at the keyboard, as in a script, it changes nothing and ends with exit code 8, unless --yes says you have said yes. hylly user link shows its link only at a terminal: into a pipe or a file, which would keep a link that logs a browser in, it takes --yes, and ends with exit code 8 without it.
  • The page shows each user only what they may do, but it's the server that decides: whatever a user's browser sends, a change their role doesn't allow is refused.
  • A forgotten password: set a new one with hylly user add NAME. There is no reset by e-mail.
  • Without a keyboard, as in a script that sets up a server or a container: --password-stdin reads the password once from standard input, one line, as docker login --password-stdin does. It takes a pipe or a file, never the keyboard, where it would show as it's typed, and on Linux and macOS it refuses a file others on the computer may read (chmod 600 it first). The password is never shown or written to a log.
  • A borrower is a login that reads in the library page and gets no file, at home as anywhere else. What a screen shows can always be photographed; a borrower just never gets the files.
  • In a browser, a login page asks for the name and password. iPhone, iPad and Android offer the saved password above the keyboard and fill it in (with Face ID or a fingerprint); one not saved yet, the browser offers to save after the first login. The browser then stays logged in for as long as you use the library: until 30 days pass without using it, and for a year at the most. One user keeps at most 20 browsers logged in: logging in on one more ends that user's oldest. Log out in the account menu (top right) ends it in that browser.
    • Browsers log in only on this page, never through the browser's own password dialog, so Log out really logs out.
    • Log out also has the browser forget what it kept for you, as on a family tablet the next person shouldn't see it: where you are in each book, and your shelves. Your changes still on their way go to the library first; with a slow or busy library, one still on its way after a few seconds stays in this browser, under your name alone, and goes at your next login here. If the library can't be reached, it says so and you stay logged in, as the log out couldn't reach it either.
    • A login ends after 30 days without use, a year after logging in at the latest, at Log out, and on every device when its user gets a new password (hylly user add NAME again) or is removed.
    • When it has ended, the library page goes to the login page as soon as it asks the server for anything, and whenever it comes back on screen (another app, the screen locked); after logging in you're back in the library, and Continue takes you to your place. A book already open stays readable until then, without a network too (on a train, say), but nothing new comes from the server without the login.
    • The browser keeps it in a cookie that its scripts can't read, other sites' pages don't get, and that, at an HTTPS address, goes over HTTPS only. Logins are kept in the database with the users, as digests that can't be used to log in.
  • In the reading apps, enter the name and password with the catalog: KOReader has fields for them, Panels and Yomu ask when they connect. A reading app with no place for a login can't use the library.
  • Only a scrambled form of each password is kept, in {{users_file}}.
  • Passwords travel merely encoded, not encrypted. At the plain home address a login crosses the Wi-Fi as it is; the HTTPS address of Tailscale Serve works at home too (A home server). Away from home, reach the library only over HTTPS, through Tailscale or a proxy that gives it (Open to the internet), never through an open router port.
  • After logging in the browser goes on to the page you opened, your filters included.
  • Text goes packed: the library page, its data, the feeds and the help shrink to a quarter of their size or less on the way, which matters on mobile data. Books, comics and covers are already packed and go as they are.
  • Through a tunnel or a proxy, such as Tailscale Serve and Funnel on this computer, the access log, the devices list and the wrong-password lockout see each visitor's own address, which it passes on, so a stranger guessing passwords can't lock you out (but see the slowdown above, from outside). Only the forwarding headers of trusted_proxies under [server] count, this computer's own as it comes: anyone else's are whatever the sender typed, and are ignored, as a guesser could otherwise pose as someone new at every try. Of X-Forwarded-For, the nearest address that isn't one of those proxies counts. A proxy on another computer goes in trusted_proxies (Open to the internet), and hylly doctor says when forwarding headers came from an address that isn't there. Behind cloudflared, set proxy_header = "CF-Connecting-IP" under [server].
  • The access log ({{access_log}}) has one line per request, from every reader, logged in or not: the device's address, the user if logged in, the time, the address asked for (which book or page, and the words of a search), the result, the size and the app. It keeps the last 30 days: older lines go each day, and when the server starts. It also stays under about 10.5 MB: 5.2 MB, then one older file. access_log = false under [server] turns it off. The server page shows the latest lines.
    • What a sender chose is cut: the request, with the address asked for, to 2,000 characters, the page it came from and the app to 200 each, keeping the start and the end, with … where the middle went. So a few huge requests can't push the older lines out. In this log and every other of Hylly's, nothing a sender wrote can start a line of its own: a control character shows as ?, and the invisible marks, which turn text round or hide words in it, are left out, but for the two joiners that some alphabets and emoji need.
    • A disk full, or the file held by another program: the server's log says so once, and the alarms still see each request.
    • A name typed at the login page, or in a reading app, is in it only when it's a user's. Any other name appears only by its length, such as (an_unknown_name_of_9_characters), so a password typed in the name field is never written down. The same goes for the server's log and the alarms when an address is locked out.
    • The access log isn't part of what hylly people export gives, and hylly people forget leaves it as it is: its lines go by themselves after 30 days.

From another computer

The server computer owns the library's data (the database), so Hylly's commands run there. On another computer, name it in that computer's settings, and every command typed there is passed on to it over ssh, with its output where you typed it. Running on server. on standard error, before the output, says that it was.

[remote]
ssh = 'server'              # the server computer's name for ssh: an alias in ~/.ssh/config, or user@host
programs = '~/.local/bin'   # the folder hylly is in there, if ssh doesn't find it by its name
  • For one command, or one terminal: hylly -H HOST before the command names the server for that command (hylly -H box download), and HYLLY_REMOTE in the environment for every command typed in that terminal; -H wins over HYLLY_REMOTE, and both over [remote] ssh. hylly --here before the command runs it on this computer, whatever they say (hylly --here doctor). An empty name, or one ssh would take for an option, is refused, rather than taken for this computer: every command stops at it, but hylly doctor, which runs here and counts it as a problem, with what to write instead.
  • Prompts work, such as hylly login's: you paste the cookie here, and it's kept there. Ctrl+C stops the command.
  • A long job, such as a download, the catalog, lookups or adding books, starts on the server on its own: closing the window, or losing the connection, doesn't stop it (its dry run, which changes nothing, runs only while the connection lasts). What it says follows here until it ends, its result on standard output and its progress and notes on standard error, as when it runs here; Ctrl+C stops only the following, hylly jobs stop NAME stops the job, and hylly jobs shows it from any computer. What it said also stays on the server, the last 50 jobs, each in two files, its result and its .err.txt, in job-output in the state folder, which the server's walls hide from it as they hide the logins; or, with Hylly's files all in one folder, outside that folder, which the walls let the server write: ~/.local/state/hylly/job-output (on Windows, Hylly-jobs beside that one folder). hylly settings places says where.
  • What stays here: , which are about this computer and its disks, and any command given --here. A backup made here asks the server for a fresh copy of the records, and sends its note of when it ran to the server, if this computer can't write to the library's share.
  • It needs ssh with a key to the server, so no password is asked each time, the same version of Hylly on both, and a server computer that runs Linux or macOS. Windows' own ssh server hands a command to cmd.exe, which reads it before Hylly starts: the quotes around its words are letters of them, so a folder or a name with a space arrives wrong, and &, |, > and %NAME% in a word act there, on the server, as cmd.exe's own (run another command, send the output elsewhere, put in a variable). A long job would also end with the connection. Hylly on a Windows server computer refuses a command that came quoted that way, and a long job, but what cmd.exe has already done by then it can't undo; commands to a Windows server are for a later version.
  • A library server on another computer, one reading the library over a share, shows the catalog as the last build wrote it, without your tags and corrections: those are in the server computer's database, which only its own server lays over the catalog. Open the library at the server computer's address instead.
  • Adding books from another computer: give the server a share of its own to drop them in, the Inbox, named by folder under [inbox]: the server takes each book into the folder of yours its kind belongs in, and the catalog shows it. The library's own share can then be read-only. The Inbox

The database

What Hylly keeps that the books can't bring back is in one SQLite file, hylly.db in {{data_folder}}, on the server computer. That's what's kept about people, the decisions on reported titles, and the library's own records: your tags and corrections, the shelves for everyone and the suggestions waiting, the catalog itself, every title and its files, with when each first came, the users with the browsers kept logged in, and what came in: each file downloaded from a shop, and each book hylly add copied in. What stays a file: your settings and rules, the logins, the books, the shops' and lookups' answers as received, the catalog's files that the server reads and the covers, and the logs (docs/database.md in Hylly's source says why).

  • Only Hylly writes it, on the computer it's on: the server, and the commands run there. Never open it over a network share, where SQLite's locks don't hold.
  • One computer keeps the library's own records: the first one that works on the library, whether its disk is in that computer or it's reached over a network share. state\database.json in the library names its database, and the Hylly install that keeps it, by a token of that install's own: records-token, beside hylly.db in {{data_folder}}, which a copy of the database doesn't take along. A command anywhere else is refused, with where to run it instead (From another computer does that for you), and so is a copy of the database in another settings folder or on another computer: two of them never keep the records apart, each missing the other's changes. Of two computers starting on a new library at the same moment, only the one the marker names goes on. A library restored or moved to another computer wants its database along: a restore puts it in place, and the latest nightly copy is in state\db-backup. To move the records to another computer, first stop the server on the one that keeps them (hylly server stop there), so that no change made there meanwhile is left behind; then, on the new one, hylly server take-over (hylly --here server take-over where [remote] ssh names another), which says what it takes over and asks first: from then on that computer's database keeps them, and with none of them yet, they start afresh there. A restore does that itself. While the library's disk is away, another folder isn't taken for the library, as it may be another one: for one that is that library, moved, hylly server take-over says so. A server that is still running when another computer's database takes the records on notices at its next request: from then on it keeps no change, writes no nightly copy, shows the catalog without the tags and corrections (they are the other computer's now), and says so once in its log and as an alarm. Stop it then, and use the other one.
  • The catalog is kept whole at each hylly catalog, in one go, and the library page's data is made from what the database then holds, checked to be the same. hylly catalog --page makes the page's data again from the database alone, reading no book. A title is in the library when the catalog has it: a book copied into a folder shows once hylly catalog has taken it in, and hylly doctor says how many book files it hasn't taken in yet, and how many of its own are no longer on the disk, and names what it can't look at.
  • What came in is recorded as each file is on the disk: a download with the shop, the title, its size and checksum, and a copy with where it came from. Every record is kept, and the latest of a path counts: hylly verify checks the files against them. On the Database page, the table download has every record, and the view downloaded each file as it stands, for questions in SQL.
  • A newer version's database is left alone, and lets nobody log in: nothing is read from it or written to it, the page says so, and an alarm goes out until Hylly is updated. For one left alone, hylly doctor says what to do.
  • Every night the server copies it (or, with jobs = "external" under [server], hylly server jobs on its timer: the server's periodic jobs) to state/db-backup/day on the library's disk, each kept until seven newer ones are there, or until it's 14 days old, as long as the newest is good: after one whose check isn't, none goes (the newest stays whatever its age): hylly.db as it was that night, every table beside it as .jsonl, a line of JSON for each row that any text editor reads (without the password hashes and the logins' digests, which only hylly.db has, to go back to), check.json with SQLite's own check of it and which library's records it holds, and a README that says how to go back to that night. hylly doctor says when the last one was made and whether its check was good, and calls it a problem when there has never been one though people have been kept for two days. A copy that fails is tried again every hour, and one made whose check isn't good is made again the next night; either is said in the server's log once a day while it lasts, and raises one alarm, as a long job's note; the first good one after says so. hylly backup takes the newest along with the rest of state. Only the database that keeps the library's records, the one state/database.json names, is copied: a server on another computer, or with another settings folder, makes no copy there, and says why in its log once. Copies of another database found in state/db-backup never count, nor go: they are left where they are, and the server says once that they are there. A library without state/database.json has had no database take it on, so nothing tells its copies apart: there, every copy counts.
  • To look inside, the Database page, /database, linked from the Server page and like it for an owner only, on any device the owner logs in on: every table with its rows, each table a page at a time with how it's made, and questions of your own in SQL, with examples to learn on. It only ever reads: the database is opened read-only, and SQLite itself refuses anything but reading. The password hashes and the logins' digests show as nothing. A question stops after 3 seconds and shows at most 500 rows.
  • Or on a copy: open a nightly copy with a program such as DB Browser for SQLite. The copy is a day old at most while the server runs, and nothing done to it reaches the server. The live file is the server's.
hylly doctor  # the database, and its last nightly copy

Bots try every address on the internet, so refused requests are normal and are only counted. An alarm is sent at once for the rare things worth a look:

Wrong passwordsWrong passwords for a real user's name (3 within 15 minutes), or any address locked out after 10 wrong ones. Bots guessing names like admin don't count.
New deviceA login from a kind of device not seen before for that user, such as Windows · Firefox or Yomu (app). This is how a stolen password shows. Each device once; the first logins after setting this up announce the devices you already use. A user renamed (hylly user rename) keeps theirs, and a new user given an old name starts with none.
DownloadsOne login, or one address, getting many different files within an hour (downloads_per_hour). Only the library's own files count: not covers, feeds or the page, nor the reader's program files, fonts and the app icons that come with opening a book.
UsersA user added or removed, or a role or password changed. Normally that's you, and then it's a confirmation.
What's kept for a userSomething kept about a user couldn't all be read, or is from a newer version of Hylly. Nothing is thrown away: see What's kept about you.

This works when Hylly itself runs from another disk, so it can still speak up. Said once, again each day while it lasts, and when it's back. A disk pulled out while in use may need mounting again and the server restarting.

Said once for each copy it's late after. Only where this computer keeps the library's records, as only that database is copied.
A review waits for youWith moderation under [reviews] on, or for borrowers, someone's words wait for an owner to look at them: how many wait, never what they say or whose. Stars and reviews
A title was reportedSomeone reported a title's file, and the title newly waits to be gone through: how many wait, never which or whose. Reporting a bad file
  • A daily summary at 8:00 says what was refused (and what bots looked for), who logged in from what, and what was downloaded. Its hour is daily_summary; -1 for none.
  • Where they go: always {{bell_log}}, whose latest lines the server page shows; a notification on this computer (on a Mac, a click on it opens Script Editor, as macOS takes a script's notification for Script Editor's; with terminal-notifier installed, brew install terminal-notifier, Hylly uses it instead, and a click opens the Server page; toast = false under [bell] turns them off); your phone through ntfy, a free push app for iPhone and Android; and a program of your own, if you name one, for e-mail or a webhook.
  • On the phone: install ntfy, tap +, and subscribe to a topic: a long, random name nobody could guess, as the topic is as good as a password for reading the alarms. Put its address, such as https://ntfy.sh/ followed by the topic, in a file of its own, ntfy-url in the secrets folder of the settings folder, and keep it to yourself. Anyone running their own ntfy server puts its address there instead, and a token, if the server wants one, in ntfy-token beside it. hylly bell says where the address is read from and shows only the topic's end; it warns about a topic short enough to guess on ntfy.sh, and in a terminal suggests a stronger one (never into a pipe or a log, where it would be known before you set it).
  • Not in settings.toml: the address and the token are secrets, so they have files of their own, and settings.toml holds none: it can be copied, compared and pasted as it is. They can come from elsewhere too, the first that has them counting: HYLLY_NTFY_URL and HYLLY_NTFY_TOKEN in the environment; a file named by HYLLY_NTFY_URL_FILE or HYLLY_NTFY_TOKEN_FILE, as Docker gives its secrets; systemd's credentials, LoadCredential=ntfy-url:FILE (and ntfy-token) in a unit; then the files in secrets. The token comes from where the address does, and from nowhere else, so that a token kept for one ntfy server never goes to an address named elsewhere: with HYLLY_NTFY_URL set, only HYLLY_NTFY_TOKEN counts.
  • What the phone gets: counts and kinds, such as 3 wrong passwords for a real user within 15 minutes. A push service passes it on and keeps it a while, so names, addresses and file names stay in {{bell_log}} and this computer's notification. remote_detail = "full" under [bell] sends those too.
  • A program of your own, for e-mail, a webhook or another push service: command under [bell], the program and its arguments as a list of words, each in quotes. It runs for everything that goes to the phone (each alarm, the daily summary, long jobs' notes and hylly bell test), at the same time as ntfy and with or without it, so that neither waits for the other. It gets what the phone gets (remote_detail), as long as the phone's at most: on its standard input the title, a blank line and the text, as mail and curl take it, and the same in its environment, HYLLY_ALARM_TITLE and HYLLY_ALARM_TEXT, with HYLLY_ALARM_PRIORITY (high for most alarms, default for the gentler ones and long jobs' notes, low for the daily summary) and HYLLY_ALARM_TIME (such as 2026-11-16T08:00:00+02:00). None of it is put on its command line, where others on the computer could read it, and Hylly's own secrets, the shops' logins and the ntfy address, aren't in its environment. No shell reads the words, so |, > and $HOME are only letters there: for those, a script of yours is the program. On Windows, the program by its full path; elsewhere by its full path, or its name alone, looked for on the PATH. As it comes, there is none.

    mail is on macOS as it comes, and on Linux in mailutils or bsd-mailx; it hands the mail to a mail server on this computer, which must be able to send it on. For a webhook, curl's file says where to send it, as url = "https://hooks.example.org/…", with any header the service wants as header = "…", so that an address with a key in it stays out of settings.toml, which holds no secrets. Make the file yours, the account's that runs Hylly, and readable by it alone (chmod 600). With curl -f, an answer such as 404 counts as a failure. Not where the server can write: neither the program nor a file its words name (a script, or curl's file: as a word of its own, after =, stuck to a short option as in -K/etc/…, or after @ in any of those) may be in one of Hylly's own folders (Where things are), the settings folder's secrets too, or the library. The server can change those, even in its walls, and your own commands run the program as well, a download with the shops' logins at hand among them; so a flaw in the server mustn't get to choose what they run, as for 7-Zip. Such a command isn't run, and {{bell_log}} and hylly doctor say why. On Windows, a .cmd or .bat file of yours reads the alarm from its standard input, or leaves it to PowerShell, as $env:HYLLY_ALARM_TEXT: never write %HYLLY_ALARM_TEXT% in one, as cmd would read the text, a name someone typed with it, as part of the script. Its time: 15 seconds. One that takes longer is stopped, with what it started: on Linux and macOS its process group, which what it starts stays in unless it makes a group or a session of its own; on Windows its job. What leaves them, as a program that detaches itself does, can't be told apart from any other program, and runs on. What it says on standard output goes nowhere, and of standard error only the end is kept. A Ctrl-C during hylly bell test or a long job's note ends it too, as does the end of the program that runs it. One that isn't found, ends with another code than 0, takes too long or isn't run is written in {{bell_log}} each time, and so is the first run that works after it; hylly doctor says when its program can't be found, or when it failed the last time it ran. It never holds up the other alarms or the server. hylly bell test runs it too, and says what went wrong.
  • Long jobs too: a download, copy, lookup, catalog build or claim tells you when it fails, in the same places, and when it finishes after more than half an hour or with files that failed; the database's nightly copy once when it fails or its check isn't good, and again when a copy is good once more. Not for Ctrl-C, a stop you asked for or a dry run, nor for one that fails within a minute with you at the keyboard: you can see that. The computer stays awake while one runs.
  • The same alarm comes again at most once an hour (quiet_minutes), also after a restart, so a stubborn bot can't flood your phone.
  • All alarms together go out at most 10 an hour and 100 a day (alarms_per_hour), so that a flood can't use up what the phone service allows and lose a real alarm later. Changed users and a library out of reach have a few places of their own. The ones held back are in {{bell_log}}, and one message says how many. The daily summary is apart from this, and long jobs' notes keep a count of their own by the same limits.
  • Every limit can be changed under [bell], and turned off with 0 or false; restart the server afterwards. The exception is alarms_per_hour, where 0 keeps every alarm in the log and sends none: to allow more, set a bigger number. settings.example.toml lists them all.

A program of your own, in the walls: it runs where what sends the alarm runs, with that one's rights: the server's alarms within the server's walls with examples/hylly.service, and within those of hylly-jobs.service when its timer runs the jobs. There it sees only what they let through: the library, Hylly's own folders without the shops' logins, the program, and what any user may read in /etc and /usr (in the jobs' walls the Inbox and the lookups' keys too); not your home folder, so a script of yours goes in /usr/local/bin, say. It may write only where the server may, reaches the network but no other program's socket, and gains no rights. A long job's note runs it where the job runs: at a terminal as you, with all your account may reach, or in hylly-download.service, hylly-lookup.service or hylly-backup.service, which have fewer walls (the shops' logins and your home folder may be in reach) but gain no rights either. So a mail program that hands the mail on through a mail server's socket, or through a program with rights of its own, as Postfix's and Exim's sendmail do, can't send from any of them: use one that sends over the network itself, such as msmtp (on Debian and Ubuntu, msmtp-mta has mail send through it), with its settings in /etc/msmtprc. Make that file the account's that runs Hylly, readable by it alone (chmod 600): under the walls' PrivateUsers only a file's owner counts, not its group, so a file for a group would have to be readable by everyone, its mail password with it. curl works as it is. A program that makes code as it runs, such as Node.js, is stopped by the walls' MemoryDenyWriteExecute. Without the walls, on Windows and macOS too, it runs with the rights of the account that runs Hylly.

hylly bell            # where alarms go, the settings, the latest ones
hylly bell test       # a test alarm, to each place

Security

What keeps the library yours when it is reachable from your home network or from outside. A review of the whole program before its first release attacked a test server; what it found is fixed, and the tests try it again on every change.

  • Books can't act in your name. An EPUB may carry scripts (interactive textbooks use them; novels and comics don't). In the reader they never run: the page allows no script but its own, not even a script file of the library's server unless the page's own scripts load it, and the book's pages inherit that, and its scripts, frames and script links are taken out before a page is shown. In Chrome, Edge and Firefox a book's pages may run no script at all. Safari, and every browser on an iPhone or an iPad (all of them Safari's engine, WebKit), needs them able to, for a tap in them to reach the reader, and there the rest stops them. That goes for every part of a book a browser could show as a page, whatever type the book gives it, and the cleaned page reaches the browser marked as UTF-8, so that the browser reads exactly what was cleaned. A book can't read the library, change it, or send anything elsewhere, nor load a style, a font, a picture or a sound from another site, in any format and however its pages are written. (A picture from another site would tell that site when and where the book was read.) The browser itself refuses them: the library page allows pictures only from the library and the sites its shop covers come from, and each page of a book only its own. A page that is nothing but an SVG picture (or other XML that isn't a web page) has no place for that last rule, so it could at most ask those cover sites. A tap on a book's link to another site first shows where the link goes, by the site's own name, and Open opens it in a tab of its own that has no hold on the library's (a site with that hold could put a false login page in its place). Only web and email addresses open; any other kind of address, such as one that would start a program, does nothing. The library's own pages also tell the browser to keep any other site's tab from reaching them, which browsers do over HTTPS and on this computer. A link in a picture (an image map's or an SVG's) and a form's send button do nothing, as only the book's own frame would follow them, out of the reader. Everything else in a page works as before: a box that opens, a box to tick, a sound's own controls.
  • Files of the library don't run either. Only books, comics, PDFs and pictures are sent as themselves; anything else a browser could run as a page (HTML, SVG, XML under any name) opens in a sandbox where nothing runs (and where it counts as another site, so it shows none of the library's pictures either), and a script file comes as plain text, whatever it is named: Hylly goes by the type this computer's own list gives the name. A packed file (a .gz, say) comes as plain bytes, whatever is inside, and a file of the library that a page asks for to run, as a script, a worker or a style-sheet transformation, is refused.
  • Pictures and archives from books are read carefully: only the usual kinds of picture (JPEG, PNG, WebP, GIF, BMP) are decoded, none over 40 million pixels, four at a time; a file in a ZIP is read no further than its limit, whatever it claims; a solid RAR is unpacked whole only when it holds nothing but pages, no links or copies, and fits the cache and the disk. Comic pages always leave the server as pictures Hylly made, never as a book's own bytes. CHM files (Windows Help, where a file's scripts run) aren't taken into the library.
  • PDFs: MuPDF draws them (PyMuPDF 2.1 or later: MuPDF 1.28.6, which fixes a flaw where a crafted PDF image could write past its memory). It never runs a PDF's JavaScript, launch actions or links, and it opens a file only as what its name says, a PDF or an e-book: MuPDF would open a picture, an SVG or an office file under such a name too. A PDF that says it has more than 100,000 pages is taken for a broken one. A PDF page, and a cover, is drawn at no more than 40 million pixels. It all happens in a process of its own, as does laying out a book for a borrower. A file that crashes it costs that page, and it is left alone for ten minutes, or until it changes. A page that takes over two minutes is stopped, and left alone for two. After three such pages in ten minutes the whole file is left alone for a while. One that wants more than 3 GB of memory gets an error (macOS has no such limit); on a computer with less than about 7 GB, less than that, as such processes together get at most nine tenths of its memory. A file uses one such process at a time, of two on most computers, so a slow one leaves the other for everybody else: one with less than 3 GB of memory has one, and one with 8 cores and 16 GB or more has four. As many 7-Zips run at a time for CBR comics. They still run as you, so this is no sandbox: what stops a real attack is MuPDF being new. Pictures in comics are still decoded inside the server.
  • Books' own fonts: a book's font files are read by the browser, and a font is a complicated thing to read. If you'd rather not, book_fonts = false under [reader] makes the browser refuse them, for the whole library; the book then shows in the font you pick, and the program's own fonts still work. An SVG picture is out of reach of that refusal, so the reader takes fonts out of an EPUB's and an AZW3's SVG pictures itself, and leaves out any picture written directly into a page or a style sheet; a part of an AZW3 that names no type isn't taken as a style sheet. It has no effect on PDFs, drawn on the server, or on reading apps, which read the files themselves.
  • Only its own names. The server answers to localhost, to any address itself (192.0.2.10, say), to this computer's own name, alone or with .local, .lan, .home, .home.arpa or .localdomain after it, and as its Tailscale name (name.tailnet.ts.net), to the name in address, and to those in allowed_hosts; a web page whose own name merely points at this computer gets nothing. Another name of yours, such as your own domain behind a proxy, goes in allowed_hosts = ["books.example.org"] under [server], unless it's the one in address. Nothing is looked up for this: the names are only compared. Where a request comes from, and by which name, never lets it in: every request logs in.
  • Other sites can't read it. A web page you happen to visit can't take in anything of the library through your browser, not the list of your books nor a cover, nor send it a form, not even to log your browser in as someone else: every answer says it is for the library's own pages only, and a request another site's page makes is refused, unless it only opens a page, so a link or a bookmark to the library from anywhere still works. Reading apps aren't affected.
  • What the downloads and lookups fetch: a link a shop or a lookup source gives, and every place it sends them on to, is fetched only over https, and never from this computer, the home network or your Tailscale network, so a shop's page can't have Hylly fetch a device at home. A name server that answers names on the internet with addresses that aren't public (a proxy in fake-IP mode, say) therefore stops the downloads and the lookups.
  • Paths stay inside the library, checked as text before Windows is asked anything: no other PC's share, no drive, no device name, no name Windows would quietly change. On Linux and macOS these (a colon, a backslash, a name ending in a dot or a space, or named like a device, such as aux.epub) are ordinary names, and such a book opens there. A name starting with a dot is served only when the catalog lists that very file, such as a shop's title or a folder of yours that starts with a dot. Nothing at the top of the library whose name starts with a dot or _ is ever served, and no build reads the folders that version control, trash and sync tools keep among your books, at any depth (.git, .Trash-1000, .stversions and the others named under The library page), so nothing in them is served either. hylly doctor names any file the catalog lists that the server refuses. Of Hylly's own folders only what the library page needs is served; state\, curation\ and the lookups' answers aren't. They are told by the folder itself, not by how an address spells its name, so a disk that ignores case or folds letters its own way (a Mac's may) can't open them by another name either.
  • The help's folders (the settings, the database, the logs) show only to an owner, logged in on any device: the server fills them in, with the port it listens on and the address people use. Everyone else gets the help with them in words, made from the program's own page, and so does the owner while settings.toml has a mistake, if the help wasn't made before it. Nothing of the help or the library page is written into the library: both come only from the server, made from the program, so a file of that name put in the library's catalog folder is never sent and can't run as the library.
  • Limits a stranger can't push past: a request has 20 seconds to arrive whole, however slowly it is sent; at most 128 connections are served at once, 32 from any one device but a proxy in trusted_proxies, and more get "busy" at once rather than waiting (up to 128 of those at a time: past that, a connection is closed with no answer); a request body has a size; two password checks run at a time; two 7-Zip unpacks.
  • Keep the readers up to date: the reading apps and devices (iPadOS, Panels, KOReader on an e-reader, the browsers) read the books' own files themselves, fonts and pictures included, so their updates are part of the library's safety. More
  • Two keys: the one for changes in the library page, which librarians get, and another for the Server and Database pages' buttons, which only owners see.
  • What still travels in the clear: at the plain home address, the library goes over plain HTTP, so on a shared or guest Wi-Fi a login can be read. Use the HTTPS address of Tailscale Serve wherever a device can, at home too, and from outside nothing but HTTPS (Ways to run it). The reader's word lookup sends the word or words you picked, the few words next to it (on the Wikipedia tab only capitalised ones, as in a name) and the book's language to Wiktionary or Wikipedia, and the browser sends the library's address with it. word_meanings = false under [reader] in the settings stops that for the whole library: the page may then ask neither site anything.

Keeping it up to date

Books come from anywhere, so what reads them should be new. Hylly checks what is really in use, offline, and says so when something is older than it should be: hylly doctor, the server's log and the server page, each under Worth updating or marked old, with the next step. It goes on working, and nothing is refused for it.

  • Hylly and its libraries: the install again, over itself: the newest Hylly, with the versions of its libraries it was tested with; then the server restarted on them, and a look at how it all stands. 
    {{install}}
hylly server restart
hylly doctor
    uv tool upgrade hylly isn't enough here: it keeps the versions of the libraries the first install was given, and an update may need newer ones. hylly server restart stops the server and starts it again in the background, with the settings; one the system runs as a service, walled in on Linux say, it asks the system to restart. A server you run in a terminal of its own instead: stop it there with Ctrl+C, and start it again. On Windows, a running server holds its libraries' files open, and the install can't replace them (Access is denied, os error 32): stop the server first, and start it again after. 
    hylly server stop
{{install}}
hylly serve --background
hylly doctor
    A start at logon goes on as it was, and starts the new Hylly from then on.
  • Python: uv brings it. The install asks it for Python 3.14 (its --python 3.14), as uv would otherwise take any Python it finds on this computer that will do, an older one too. A 3.14 that this computer has already is taken as it is, an early one too: uv python install --upgrade 3.14 brings uv's own newest 3.14, which uv then takes first, and the install again moves the hylly command to it, as hylly doctor says when it's time. For a newer Python than 3.14, the install again with its number after --python, with the same versions of the libraries (on Windows, with the server stopped first, as above); hylly doctor says the whole command when it's time. A Python from your system's own packages may have the fixes under an older number, and then the warning can be ignored.
  • 7-Zip comes from 7-zip.org, or your system's packages, and doesn't update itself. It is used for CBR comics only. Here too a system's package may have the fix under an older number, and it may leave out the RAR part most CBR comics need (CBR comics).
  • The reading apps and devices read the books' own files, so their updates count as well: iPadOS, Panels, the browsers, and KOReader on an e-reader. Hylly can't see those.
  • Behind the scenes: pyproject.toml names the oldest version of each library Hylly accepts, a test keeps the check above to the same numbers, and every week GitHub checks the versions Hylly installs (uv.lock, which tool-constraints.txt gives the hylly command too) against the published flaws.

Stopping using Hylly

Hylly removes nothing of its own when you stop using it: this says what to stop, what to keep, and what stays behind for you to remove. Your books stay in the library as plain files, whatever goes. What starts the server goes first, while the command that removes it is still there: a start at logon outlives the program, and then either goes on starting a server, which may be open to the home network or a tunnel, or fails unseen at every logon.

  1. The start at logon: hylly server autostart off. On Windows it removes the task; on Linux and macOS it prints the commands that stop and remove the systemd user unit or the launchd agent.
  2. The server: hylly server stop. A demo's server stops with Ctrl+C in its window.
  3. The jobs' timer, if you set one up from examples/hylly-jobs.timer: sudo systemctl disable --now hylly-jobs.timer, then sudo rm /etc/systemd/system/hylly-jobs.service /etc/systemd/system/hylly-jobs.timer and sudo systemctl daemon-reload. A line in cron, or a Task Scheduler task, that runs hylly server jobs goes by hand too.
  4. The way in from outside: Tailscale Serve and Funnel stay on after the server has gone, on its port, ready for whatever listens there next: tailscale serve --https=443 off and tailscale funnel --https=443 off (Tailscale's command on each system). A proxy of your own: take the library out of its settings. On Windows, the firewall's permission for Python to accept connections, if you gave it when the server first listened on the home network, stays with that Python: Windows Security → Firewall & network protection → Allow an app through firewall.
  5. What to keep, before anything goes. Your records (your tags and corrections, the catalog, the users, what people have read) are in the database, hylly.db in {{data_folder}}: hylly backup copies them, fresh, with the library, the settings and the rules, but never the shops' logins or the lookups' keys (A backup on another disk). Each nightly copy in {{library}}\state\db-backup has them too: as hylly.db, and without the password hashes as .jsonl files, a line of JSON for each row, that any text editor reads. hylly people export NAME gives one person all the database keeps about them.
  6. The logins and keys, in {{logins_folder}}, work at the shops until they're ended there: hylly login SITE --forget deletes one here, and hylly login --forget-all every one, each saying how to end it at its site; an environment variable such as HYLLY_HUMBLE_SESSION, if you set one, is yours to unset. Revoke the keys you made for Hylly where you made them: DriveThruRPG's Library App Key (Account → Settings), itch.io's API key (Settings → API keys), and the lookups' keys at Metron, Comic Vine and Google Cloud's console, where the site offers it. A cookie you gave is a login to your account at Humble Bundle, StoryBundle or itch.io: log out there in the browser it came from, or change your password there. The alarms' ntfy topic, in the settings folder's secrets folder, is as good as a password: unsubscribe from it in the ntfy app on your phone.
  7. The program: uv tool uninstall hylly. A checkout of the source, if you worked on Hylly from one, goes as any folder does.
  8. By hand, if the command is gone already. Windows: the task Hylly library server in Task Scheduler, or schtasks /Delete /TN "Hylly library server". Linux: systemctl --user disable --now hylly.service, then remove ~/.config/systemd/user/hylly.service; lingering, if you turned it on for the server, stays until loginctl disable-linger. macOS: launchctl bootout gui/$(id -u)/io.github.janisc.hylly, then remove ~/Library/LaunchAgents/io.github.janisc.hylly.plist. A system-wide service made from examples/hylly.service: sudo systemctl disable --now hylly, then sudo rm /etc/systemd/system/hylly.service and sudo systemctl daemon-reload.
  9. What stays behind, for you to delete once you've kept what you want (Where things are has each):
    • Hylly's own folders (hylly settings places lists them, before the program goes). All in one, as an install that has kept them so: %LOCALAPPDATA%\Hylly on Windows, ~/.local/share/Hylly on Linux and macOS, or the folder HYLLY_HOME names. Otherwise each kind in its own, unless its variable puts it elsewhere: the settings folder, %APPDATA%\Hylly on Windows, ~/.config/hylly on Linux, ~/Library/Application Support/Hylly on macOS, with the settings, the rules, your themes and the alarms' address and token; the data folder, %LOCALAPPDATA%\Hylly\data, ~/.local/share/hylly, or on macOS the settings folder itself, with the database (the users' password hashes and everyone's reading), its copies from before an update changed its tables (hylly.before-NNNN.db), the token that ties the library's records to this install (records-token), what HyllyCopy knows of its targets, and the shops' logins and keys in logins; the state folder, %LOCALAPPDATA%\Hylly\state, ~/.local/state/hylly, state in the macOS settings folder, with the server's log, the access log (who opened what, for 30 days), the alarms' log, the notes of the last jobs with the commands they ran, and what long jobs said; the cache folder, %LOCALAPPDATA%\Hylly\cache, ~/.cache/hylly, ~/Library/Caches/Hylly, with the reader's cache (up to cache_gb, 10 GB as it comes).
    • The reader's cache elsewhere, if cache_folder under [reader] puts it there: the pages and drawn folders in it.
    • What long jobs said, with the folders all in one: ~/.local/state/hylly on Linux and macOS; on Windows Hylly-jobs beside the folder of all in one (%LOCALAPPDATA%\Hylly-jobs).
    • The demo: hylly-demo in your home folder, or the folder you gave hylly demo, with its own settings in it.
    • In the library, beside your books, Hylly's own folders: state (with your order keys and the nightly copies of the database and the settings), catalog and curation; _Removed, with the files you removed on the Server page (To decide); and a folder of yours whose name starts with _, such as _originals, if you parked files there. And .hyllycopy in each folder hylly copy copied to, and on a backup disk saved, whose zips hold the users' password hashes and the order keys.
  10. In the browsers and the reading apps: each browser that used the library keeps its login there, as a cookie, and what the page keeps for you (places not sent yet, the theme, the filters, the reader's settings, under names starting hylly.): clear that site's data in the browser's settings, and the password it saved for it. In each reading app, remove the library's catalog, with its name and password.

hylly doctor names the program the start at logon starts, and says so when that program is gone.

After buying something

Every shop works the same way: hylly SHOP download fetches what you own there and downloads what's new into the shop's own folder, keeping where each title came from (the shop, the bundle, the date). Each shop needs its login once (hylly login SHOP; see below and the shops' sections).

Your account, your shop's terms: Hylly uses your own logins and only what your accounts offer you, but automating a shop may go against its terms. Whether to do that is your decision, at your own risk.

It asks gently: a second between requests to a shop's own site, and downloads side by side only as many as --jobs says, from 1 to 6. When something stops it, the message says what was asked for in words and never shows an address, as addresses can hold your order keys. So it's safe to paste one when you ask for help.

hylly download                    # every shop you have a login for, one after another
hylly drivethrurpg download       # or one shop: DriveThruRPG,
hylly humble download             # Humble Bundle,
hylly storybundle download        # StoryBundle,
hylly itchio download             # itch.io (claim its bundles' items first: see itch.io)
hylly catalog --lookup            # adds the new books to this page
  • Preview first: hylly download --dry-run lists what each shop would download, reading each shop's site as its download would, and downloads nothing and saves nothing. Every shop's dry run is the same, Humble's too: hylly humble download --dry-run.
  • One at a time for each shop: while a shop's download runs on this computer, a second one for the same shop is refused and says where the first runs. Two at once would ask the shop twice as fast and fetch the same files twice. Different shops can run side by side, and so can a lookup. One that has hung is ended with hylly jobs stop SHOP, for example hylly jobs stop humble; the files it had finished are kept.
  • When a shop says no: a shop that asks to wait (HTTP 429 with a Retry-After) gets its wait, up to 15 minutes, and every download waits with it, not just the one that was told. A shop that turns five files in a row away (HTTP 401 or 403 even with a fresh link, 429 after its waits; at StoryBundle a 422 for a book's link too) is blocking the run, so the run stops and says so instead of going through the rest of the list at full speed; what was downloaded is kept, and the next run goes on from there. A refused file among good ones is just a failure, listed with the others. The same goes for a shop that doesn't answer at all, or answers only with an error of its own (HTTP 500 and the like), each time asked again first, for three files in a row: it's down, so the run stops, and the next run goes on from there.
  • A full disk stops the run at once, with exit code 6, instead of failing every file left one after another: nothing is a failure, and the run says how much room the files not downloaded yet need. Make room and run it again; a file cut short goes on from where it stopped. Every run, a dry run too, also names the partial files (.part) no download goes on from, such as one beside a file that came another way: nothing deletes them, so delete them yourself to get the room back.
  • A library on a network share that is gone for a moment, as when a NAS restarts its file sharing, is waited for on Windows, where it looks like a missing folder: a download, hylly add or hylly humble seed looks again every 15 seconds, for up to 4 minutes, before it stops as for a disk that isn't there. What was done is kept, and the next run goes on from there.
  • Programs, scripts and shortcuts never come, from any shop: an installer, a .url or .lnk shortcut, a script, or an Office file with macros among a title's files is left out, even under a name like Setup.exe., as it could be run by whoever opens the library's folders. Every run lists what it left out, a dry run too (a StoryBundle book's once a run has had its link, as its name comes only with it), and the log has it; it is no failure, and a copy an earlier run downloaded stays where it is. Which kinds these are is in the rules (programs under [media]), and Windows' own stay out whatever a rules file says.
  • Files a shop has replaced: add --update, for Humble and DriveThruRPG, the shops that say when a file has changed. The old versions are kept in superseded\. An old version another program has open (a viewer, or the server showing it) can't be moved there on Windows, nor from a share that says it's busy: that file fails, saying so, and comes once you close it and run again. StoryBundle's books come once, as they are. itch.io's downloads look at an item's files again by themselves once what itch.io said of them is two weeks old (a few days more for some items, so they don't all come due on one day), and at once after a file of it has gone; a new or replaced file comes beside the old one, which stays (see itch.io).
  • Humble: one file of each title. Humble offers most titles in several formats, so hylly humble download reads your library on Humble's site (read only, as its own library page reads it: the list of your purchases, then each purchase's page with its files, a second between requests, so some ten minutes for a large library before the first file comes) and keeps one of each title, the best by your lists under [download], with its extras; a dry run reads them too and lists what it would download. Each run ends by saying what the whole library has and still needs, as the run leaves it, a run that failed or was stopped too, and so does a dry run, after its list: kind by kind, the files done, still to download and changed on Humble, those that failed last time, the partial files, the recorded files missing on the disk, those downloaded that no title chooses any more (no longer chosen), and the titles below with another format in their place or kept in an older format (--json has all of it, and a dry run's each file's reasons: its kind, its format and where it is read). Besides every shop's options it takes --device (where a title is best read: ereader, tablet or either), --bundle and --max-gb; hylly humble download --limit 0 reads and saves your orders without downloading anything. hylly humble seed FOLDER … adopts copies of Humble files you already have, so they aren't downloaded again: offline, from the orders the last download read. Now and then Humble gives no data for a purchase, or its page is one of its own errors: a download then keeps it as the newest snapshot that has it had it, so its titles stay in the library page, says how many, and ends with exit code 1 (partly done), a dry run too; such a purchase's titles keep their folders, so none of them comes again, and a file of it still to download is asked for as before, or, in the first run after Humble's site changed, comes from another purchase of the title if Humble answered for one that lists the very same file, else fails, for the next run to try again. Humble's site gives no purchase date, publisher or cover: those of what you had bought before Humble rebuilt its site are kept from the snapshots, so every title keeps its place, its date and its folder, also a title of an old purchase (2010 to 2013) that Humble's site no longer lists, which a run names in a line; Humble's site lists more of some older bundles than it did, which a dry run shows before anything comes; a purchase made since is dated the day a download first saw it, and its titles' publishers and covers come from a lookup (hylly catalog --lookup).
  • What each shop listed is kept as it was, without its links or keys, as a snapshot in the shop's own folder of the state folder (state\humble\ and so on), named for when it was made: the library page lists a shop's titles from its newest one. A download adds one when what the shop lists has changed since the newest (a dry run never); then the shop keeps its newest five snapshots and the newest of each month before them, and the others are removed, which the run says, in state\download-log.txt too. The one just saved is never removed. The shop's folder also has its failures file and its working files, such as StoryBundle's left-out.json and itch.io's answers and survey.
  • A file Humble can't give (Humble): when Humble no longer has a title's chosen file (not even with a fresh link) or no longer lists it, or what comes is wrong twice, the download tries the title's other formats, best first (for a novel: EPUB, then MOBI, then PDF), and the log says which one it got instead. Any other trouble, such as the network or the share gone for longer than the retries last, Humble turning files away or asking to wait again and again, or an old version in use, brings no other format: a title with none in its place yet is failed, listed in the failures file, and the next run tries the same file again. A full disk stops the run (above). A format that came instead stands in for the chosen one, and every later download gives the chosen file one try, after the other files: one download at most, without the retries, so a title whose file is gone costs a run a moment. While the other format stands in, however the chosen file fails, the run says why and that the other stays, and it counts as neither a file done nor a failure: no line in the failures file, no exit code 1, and the run's last line counts these titles apart. When the chosen file comes, the run says so, and the other stays in the folder, still the title's. Every Humble download, a dry run too, counts these titles, and with --json lists them with their ids. To keep the one that came for good, choose its format with hylly set format (see Correcting); the download says for which titles that works, as it can't keep, say, a PDF that came instead of another PDF. Extras, such as bonus files, have no other format to try: if Humble's own link for one is broken, only Humble support can fix it.
  • “Not logged in” or “session expired”:
    1. Log in on the shop's website.
    2. Copy the session cookie's value in the browser's developer tools, under the shop's site: in Chrome and Edge, F12 → Application → Cookies; in Firefox, F12 → Storage → Cookies; in Safari on a Mac, Develop → Show Web Inspector → Storage → Cookies (the Develop menu first needs Show features for web developers, in Safari's settings under Advanced). For Humble it is ory_session_stoiccohens510ht9xek, the cookie of its sign-in (not _simpleauth_sess, which it no longer takes as a login); for StoryBundle, _storybundle31_session.
    3. Run hylly login humble --clipboard or hylly login storybundle --clipboard.

DriveThruRPG and itch.io use a key instead of a cookie: see DriveThruRPG and itch.io.

Choosing what to download: the shop list

A download takes everything you own at a shop that the rules keep. When that is still more than you want, do it in two steps: first a list of all of it, a row per file, with what a download would fetch ticked; then a download that goes by the list once you have edited it in Excel, Google Sheets, LibreOffice or any editor. Nothing is downloaded only to be deleted afterwards.

hylly humble list ~/humble-list.csv             # every file, the rules' picks ticked
hylly humble download ~/humble-list.csv         # then by your edits
hylly list ~/hylly-list.csv                     # every shop you have a login for, in one file
hylly download ~/hylly-list.csv --dry-run       # what it would bring

The file goes where you name it, or as humble-list.csv or hylly-list.csv in the folder you are in; give it a place of your own, as above (in PowerShell $HOME\humble-list.csv), rather than Hylly's own folder.

  • Every shop the same: hylly SHOP list for Humble, StoryBundle, DriveThruRPG and itch.io, and hylly list for all of them in one file. A shop's list takes the options of its download that choose titles (--title, --kind, and its own, such as Humble's --bundle and --device, StoryBundle's --no-bonus, itch.io's --types), and lists only those titles. It reads the shop as a dry run does, and keeps nothing. A plain hylly SHOP download works out the very same list by the rules and downloads its ticked rows: a list written and given back unchanged downloads exactly what a plain download would.
  • The file: a CSV with semicolons between values, as Finnish and other European Excels open it by a double-click; any spreadsheet or editor will do. Its columns: shop, bundle or publisher, title, kind, format, role (a book, or an extra such as a map), MB, in library, why, listed (the day it was written), id, picked and download. download is the one to edit: (X) ticked, ( ) not. picked says what the rules ticked when the list was written: leave it as it is. A book offered in three formats is three rows, the one the rules pick ticked; why says why the rules chose as they did (a guess between two files, say), so you can move the mark. Kinds no download takes (games, music, video) and programs aren't in it at all, and nor is a Humble item of extras only until you answer that it is a title (What the rules leave to you). Sort the rows, delete them, change, move or drop the other columns as you like. (X), [X], X, yes and 1 are ticked; ( ), [ ], nothing, no and 0 are not. A title that starts like a spreadsheet formula (with =, +, - or @) is written with a ' before it, so it stays text.
  • Only your changes count: a row whose mark you left as it was goes by the rules as they are when the download runs, so a file held back for your answer then, and answered since, comes. A mark you changed is yours: ticked, the file comes in that run; unticked where the rules had ticked it, it is left out for good (below). A row you delete isn't downloaded in that run. A list whose picked column is gone counts its marks for that run alone, and keeps nothing of them, which the run says.
  • A list you edited is never written over: hylly SHOP list refuses a file that is there already, unless you add --force or give another name (hylly humble list ~/comics.csv --kind comic). - as the file writes the list to standard output, and as the list reads it from standard input.
  • Nothing is ever deleted from the library: a file there whose row you untick stays (in library says yes). Beside a list, the options that choose titles are refused, as the list chooses them; --limit, --update, --dry-run and --json work as ever. --dry-run says what would happen: with a list, From your list: 1,204 rows, 380 ticked: 212 to download (14.2 GB), 168 in the library already., and without one, From the list the rules make: …
  • Left out by you, for good: a row the rules ticked that you untick is remembered as your choice (an ordinary correction, kept with your tags): no later download fetches it, the jobs on a timer included, and each run counts it apart (Left out by you: 3 files), never as a failure. A new list shows it unticked, with left out under in library. Tick it again in a list to take it back, or run hylly set left-out auto --id ID with the row's id (humble:lanternwolf_book:Lantern Wolf.epub: that file) or the title's catalog id (h:lanternwolf_book: all its files left out). For a title in the library page, Recent changes has an Undo of it too; a title not downloaded yet isn't in the page, so there it has none. A row you tick that the rules don't (another format, say) is downloaded in that run, and is then simply in the library.
  • Moving the mark answers the question: where the rules were unsure which of a title's files to keep (which file), tick exactly one other of those files and untick the guess, and the list answers the question with that file, as hylly decide NUMBER FILE would: that file comes, the question closes, and the guess is never fetched later; a guess downloaded already stays in the library as it is. Tick several of them and none is an answer: each ticked one comes, and the question stays. The run says which questions the list answered; a dry run says what it would answer. A file you said you moved by hand is unticked, with moved by you; tick it and it is fetched again, and your answer stays, so should it go again it isn't fetched behind your back.
  • An old or broken list: either separator, the byte order mark or not, moved or missing columns, any row order, an Excel's own sep= line, and a size a spreadsheet saved as a whole number (88 for 88,0) are all fine, and so is a file the shop changed since: what it lists now comes, under the same id, and the run says so. A row whose id the shop doesn't have any more, one with a mark that can't be read, and two rows of one id with different marks are each said with why, the rest goes on, and the run ends with exit code 1 (partly done). In hylly download LIST, the rows of a shop you aren't logged in to are said in one line for that shop, with how many, and the run ends with exit code 1 too. A file that isn't a list, or has no id or download column, stops the run before anything is downloaded, saying which. And an old list says so: This list was written 40 days ago; 6 items bought since aren't in it: run hylly humble list again to see them (itch.io gives no purchase dates, so its lists never say it). If one shop's part of hylly list can't be read from the shop, the run says so at its end, and the list has no rows of it.
  • From another computer: with the commands passed on to the server computer, give the list through standard output and input, as hylly humble list - > ~/humble-list.csv and hylly humble download - < ~/humble-list.csv; a file name alone is refused there, with what to type instead. A download given its list so runs while the connection lasts: closing the window stops it, and the next run goes on from there.

What the rules leave to you

Where the rules of a download or of the catalog can't be sure, they guess, as they always have, and keep the guess as a question for you. Every run and every hylly catalog ends by saying how many there are (3 questions to decide, the new ones said apart), and hylly doctor counts them. You may answer them, or leave them: the guesses stand. The downloads ask:

  • Which file to keep (Humble): a title offered in several files of the format its list keeps (a PDF and a PDF (HQ)), or in none of its formats at all. The guess is the largest. Asked of a title about to be downloaded, and open until you answer.
  • Is it a title? (Humble): an item of your orders with no book of its own, only extras or files of formats the rules don't know (an art book labelled a bonus, say). The guess: leave it out, as it was. Answer with one of its files to make it a title, downloaded with its extras and shown in the page. An item with any file the rules know as no book (a game's, a program, music, video) is never asked about.
  • Gone from where it was downloaded (every shop): a file, or a title's whole folder, no longer where its download put it. The guess: download it again to that place. If you moved it by hand, say so, and it is never fetched again.
  • A file the shop renamed is no question: the very file (its checksum, or where the shop gives none, the same name in letters of either size and the same size) is not downloaded again under its new name, and the run says so; nor is one you said you moved by hand.

And the catalog asks, at every hylly catalog and every pass of the Inbox:

  • Are these two copies one book? Two copies with the same title, in two places, that the rules keep as two cards because they can't be sure: one's title isn't in its file's name, the title is short, or one is a comic and the other a book. The guess: two cards, as before. Answer the same book and they are one card in every build; two books and they are never asked about again while they are the same files. Never asked of manuals, nor of books whose authors differ. The other way round, a card that is two books: hylly set copies apart --search WORDS, or Not one book in its details, keeps its copies apart; hylly set copies auto lets the rules decide again.
  • A lookup's near match: a title no lookup found for sure, whose sources found something close (scoring under the 0.8 they need, and at least 0.6): mostly the right series in another edition, so these aren't on the list. The title's details show the owner each near match, with Use it, after which its details fill the title in every build, and Not this book, after which that source isn't asked about it again; hylly decide --kind match lists them all. The guess: none is used, as before. A match the catalog used that is another book: hylly set refused openlibrary --id ID, or (not this book) beside the source in its details; the next source is then asked in its place, and hylly set refused auto takes it back.
  • Which title are your tags for? A title gone from the library whose tags and corrections are kept for it, with the titles that may be it (new, or of the same file name or size, or alike): choose one and they go there; forget them; or keep them waiting, the guess, should it come back.
  • Are these files books? Files in one of your folders of a kind the rules don't take as books, asked once for the folder and the kind (7 .xyz files in Comics), never of hidden files, pictures, the systems' own files, what reading apps keep beside a book (a Kindle's .mbp or .apnx, KOReader's .sdr folders), file_id.diz, stylesheets, or kinds the rules know. The guess: passed over, as before. Books takes them into the catalog from the next build, in that folder only, hidden ones of that kind too; a file of that kind beside a book of the same name joins that book, which keeps its own file first.
hylly decide              # the questions, each with its number, its options and the guess
hylly decide 7 2          # answer question 7 with its second option
hylly decide 7 keep       # keep the guess: it isn't asked again
hylly decide --answered   # the questions answered, each with its answer
hylly decide 7 auto       # take that one answer back
hylly decide --kind match # the lookups' near matches, or any one kind
  • On the Server page too, for the owner: To decide shows each question with its options as buttons, the guess marked, and under Answered those you answered, each with a Take back. Two copies that may be one book, and a title offered in several files, have Compare the files, which fills the window, one question at a time, with nothing to scroll: the question at the top, with × (or Esc) to close it; then a column for each file, side by side on a phone too, with its name, format, size, date, language and the page shown, its cover, and below that the page as large as the column lets it, never cropped, drawn as sharp as the screen shows it. Each shows the same page, the same way through (it opens a tenth of the way in, or past the cover of a short one, and passes over an empty or plain page there), with a corner magnified where you click on either page, the page drawn large there (a comic's page as large as it comes, up to 2,400 pixels wide), so a sample, a poorer scan or a tilted one shows; ◀, ▶ and the slider at the bottom turn both together, and so do the ← and → keys. Right under each page is the answer that keeps that file, in the theme's colour: Keep this file for a title's files, the rules' guess marked, and for two copies Keep only this one (below). A file that wasn't downloaded shows what the shop lists of it in its column, with its own Keep this file, and a file the reader doesn't show for its title shows its facts alone. An answer closes it, and the list says how it went. The language is the one the file says (an EPUB's own, a comic's ComicInfo.xml), else one its name names by the rules ([languages]: Lantern Wolf (Spanish).epub), and where the two files differ in it, Compare says so. The library page shows the owner a count, N to decide in Library management, and a title's details its own questions, a near match with its buttons, any other a link to it; nobody else sees them, nor the buttons Not one book and (not this book), which are the owner's too.
  • Two copies, on the Server page, have Keep both and Compare the files in place of their answers, the copies named by their first files under the question: Keep both is the answer two books, two cards, not asked again, marked where it is the rules' guess. The removals are in Compare the files, which shows each copy in a column of its own: Keep only this one, under a copy's page, removes the other copy's files; at the bottom, Keep both again and Remove both…, which removes both copies', once you have said yes to its question. Only while both copies are shown can one be removed. A copy is its card, with all its files (Compare says how many). One card for the two, the same book, is no button there: hylly decide NUMBER 1 answers so.
  • A removal deletes nothing: each file moves into {{library}}\_Removed, at the same place below it as it had below the library (_Removed\comics\Sagas\Moonwake Saga.epub; a name taken there gets (2), never written over), a folder no catalog build reads, the server never sends anything from and a backup leaves out; never through a link: _Removed, or a folder in it, that is a link or a junction is refused, as it could lead anywhere. Then a catalog build starts by itself, and the card leaves the library page once it's done; with one running already, another starts once that one has ended, and the page says so. A shop's file is never fetched again: its title gets your answer that you moved it, as I moved it by hand gives, which stays when _Removed is emptied; and a book hylly add copied into a folder of yours isn't copied in again from its original while its removal stands, in _Removed or emptied from it. Nothing in Hylly's own folders (catalog, state, curation, superseded) is ever removed, and a file in use stops the removal there, those before it removed.
  • Removed, a tab of the Server page while _Removed holds anything, lists its files, the latest removed first, each by its place in the library, its size and when it was removed. Put back moves one back to its place, if nothing is there now, takes back the answer its removal gave a shop's title, and starts a catalog build, which brings its card back. Empty _Removed… says how many files and how much space, and how many of them were put there by hand, and once you have said yes, deletes them for good: only what the list showed, each by its place and size, so with anything else there by then it deletes nothing, and you look again. hylly verify doesn't count a file you removed as missing, in _Removed or emptied from it: the database keeps each removal. A file you move into _Removed by hand, at its own place below it, is listed the same way, and put back there. On Windows and macOS, where a name's capitals don't count, a folder _removed of yours is this one.
  • An answer is a correction, kept in the database with your tags: choosing a file sets the file to keep (as hylly set file NAME --id ID does), and the other answers are kept with the title. Recent changes in the library page lists them in words, with an Undo. hylly decide NUMBER auto (or Take back) takes that one answer back alone, exactly as it was before it; hylly set file auto --id ID or hylly set answers auto --id ID all of a title's; and the next download or build asks again where its rules are still unsure. A format you set later (hylly set format, or Format to keep) wins over a file you chose of another format, and set back to automatic, the file counts again; a format that agrees with the file (PDF, after choosing one of its PDFs) keeps that file.
  • An answer goes by what you saw: each question has a number that is never given to another, and the Server page sends what the question offered with your answer, so an answer to a question that offers other files by then is refused, and you look again. hylly decide NUMBER CHOICE also takes a file's name as the choice, and says what the answer did.
  • Held back until you answer: with unsure = "ask" under [download] in the settings, a download takes no guess: it holds that file back, says how many it held back, and fetches it once you have answered. "guess", the default, takes the guess, so a first big download isn't held up.

StoryBundle

StoryBundle has no keys, so Hylly uses your browser's login, along with your account's number:

  1. Log in on storybundle.com and open My Book Bundles. The address ends in your account's number: storybundle.com/users/<number>.
  2. Put it in {{settings}}, at the top, above the first [section]: storybundle_user = '<number>'.
  3. Copy the value of the _storybundle31_session cookie (where each browser keeps it: a shop's login again), and run hylly login storybundle --clipboard.
  4. Then hylly storybundle download fetches every book into storybundle\, and a new run only what's new.

Each book once: StoryBundle lists a book in every bundle it came in, so it is downloaded once, into the folder of the first of them by purchase date. --bundle TEXT takes only the bundles whose name has the text and --no-bonus leaves out the free newsletter bonus bundles; a book also in a bundle they leave in comes there. --title, --kind and --limit work as for every shop. A book that has gone from its folder, or was cut short, comes back to the same place, under the same name (a copy cut short is kept in superseded\); if StoryBundle now gives another format for it, that one comes under its own name in the same folder. Each is a book unless its bundle's name says otherwise (a comics bundle, say), as at every shop, and the library page suggests where each is best read, as for every title.

A book's file name comes only with its link, which Hylly asks StoryBundle for once, as the book's download starts: that link names the file and fetches it. So a dry run lists the books by their folders. When a link names a program, script or shortcut, that book is left out and named, as every shop's are, and remembered (in the state folder's storybundle\left-out.json), so later runs, dry runs too, name it at once without asking StoryBundle again, unless StoryBundle lists it with another size. To have Hylly ask about such books again, delete that file: the next run asks about each of them once more (a newsletter bonus book is listed with no size, so only this has it asked about again).

When a book doesn't come: if StoryBundle answers with an error for one book (a file it no longer has, say), only that book fails: the run goes on with the others, lists it, and the next run tries it again. StoryBundle turning five books in a row away stops the run, as with every shop. When StoryBundle is busy (HTTP 429 or a server error) or doesn't answer, Hylly asks again a few times first, as with the other shops, and then that book fails; three books in a row with no answer, or only a server error, stop the run, as with every shop: try again later. Only when StoryBundle sends it back to its login or front page does it stop and ask for a fresh cookie (“Not logged in” under After buying something).

DriveThruRPG

Every file in your DriveThruRPG library is downloaded into {{library}}\drivethrurpg\<publisher>\<product>\, instead of clicking them one by one on the website. That includes the RPG bundles from Humble that you redeemed there.

Once: make an application key and save it.

  1. On drivethrurpg.com, open Account → Settings. Under Library App Keys, make a new key and copy it.
  2. Run hylly login drivethrurpg --clipboard. It says how many titles your library has.

The key is stored only in {{logins_folder}} (Where things are), and is never shown. It is the kind of key DriveThruRPG's own Library app uses; to stop it working, remove it in the same settings. hylly login drivethrurpg --forget deletes it here.

Then, whenever you like:

hylly drivethrurpg download --dry-run  # what would be downloaded
hylly drivethrurpg download            # downloads it; Ctrl+C stops, running it again continues
hylly drivethrurpg download --update   # also the newer versions publishers have put up
hylly catalog                 # shows them in the library page
  • Every file of a product is downloaded: the book, and the character sheets, maps or printer-friendly copies that come with it. Only a program, a script or a shortcut is left out, such as a character generator that is an EXE or a spreadsheet with macros, as no shop's are downloaded (see After buying something); every run names it. In the library page the product is one title, with its biggest file first. Its source is DriveThruRPG, and its kind an RPG book, for a tablet, unless its publisher's name or a comic's file says otherwise, as at every shop (a comic by a comics publisher or as a CBZ, say, or a novel by an RPG publisher: kinds). Its game, product type (such as Adventures), description and cover come from DriveThruRPG (see Games of RPG books).
  • Checked: each file against DriveThruRPG's MD5 checksum.
  • Newer versions: when a publisher puts one up, the next run says how many files changed. --update fetches them, and the old versions go to superseded\. A file keeps its folder and name.
  • Only part of the library: --title, --publisher, --kind and --limit (a number of titles).
  • If it stops working: DriveThruRPG doesn't document this interface (its own Library app uses it), so a change on their side can break the command until it is updated. A product the listing gives in a shape Hylly can't read is named and left out of that run's downloads; what the library page had of it stays there. Failed files are listed in state\drivethrurpg\failures.csv.

itch.io

itch.io is mostly games and software, and much of what its charity bundles hold isn't worth opening, but there are gems among the books, comics and tabletop games. So the first step only counts: hylly itchio survey says what your library holds, by kind, how many files and how much space, before anything is claimed or downloaded. Downloading comes later, once you have seen the numbers and chosen.

Once: make an API key and save it.

  1. On itch.io, open your name (top right) → Settings → API keys → Generate new API key, and copy it.
  2. Run hylly login itchio --clipboard. It says which account it logged in as.

The key is stored only in {{logins_folder}} (Where things are), and is never shown; to stop it working, revoke it in the same settings. hylly login itchio --forget deletes it here. For the bundles, itch.io's pages need your browser's login too: copy the value of the cookie named itchio, under https://itch.io (where each browser keeps it: a shop's login again), and run hylly login itchio-bundles --clipboard.

Then:

hylly itchio survey          # counts; with big bundles the first one takes about half an hour
hylly itchio survey --again  # reads the bundles and asks about every item again
  • By kind, as each item's creator chose it on itch.io: books, comics, tabletop (RPGs, board and card games), other (zines and the like) and games. Tools, assets, mods and soundtracks are counted but not looked into. A game whose files are all PDFs, EPUBs or comics, a rulebook say, is counted apart so it isn't lost.
  • What counts: files on itch.io itself, without programs (installers, and files for Windows, Mac, Linux or Android). Files that are only links elsewhere, such as Google Drive, can't be fetched and are counted apart.
  • The result is in state\itchio\survey.txt: your bundles, then per kind the items, how many are claimed, files and GB known and guessed, the file types, the 20 biggest, and the space left in the library. state\itchio\survey.csv lists every item but the software and the programs, with whether it's claimed, its bundles, whether it's free, its size (known or guessed), file types, link and description, to sort and filter in a spreadsheet.
  • It continues where it stopped: each item's files are saved as soon as itch.io lists them, so after Ctrl+C a new survey only asks about the rest. One survey runs at a time; hylly jobs stop itchio ends one that has hung.
  • Bundles are counted too, with the login cookie saved: their items aren't in the library until each one is claimed on the bundle's page, so the survey reads those pages (one every two seconds) and counts every item once, also when it is in more than one bundle. An item with files for Windows, Mac, Linux or Android is a game or a program and isn't looked into; for the rest it asks itch.io what kind each one is.
  • Known and guessed sizes: itch.io shows a paid item's files only once it's claimed. So for those the survey guesses: the number of files the bundle's page shows, times a typical file of the same kind among the ones it knows (free items show their files). The report says which part is known and which is guessed; the exact sizes come once the chosen ones are claimed.
  • Reused answers: a new survey reuses the bundles' pages and the answers it already has, so it only asks about what's new; --again reads and asks everything again, for example when a bundle has grown.
  • If it stops working: itch.io doesn't document this interface (its own app uses it), so a change on their side can break the command until it is updated.

Claiming the bundles' items, after a survey, puts them in your itch.io library, where they can be downloaded; it takes no space yet:

hylly itchio claim --dry-run      # how many, from which bundle, and how long it takes
hylly itchio claim                # books, comics, tabletop and other, one every 20 seconds
hylly itchio claim --types book   # only these types (book, comic, tabletop, other, game)
hylly itchio claim --all          # every item the survey has classified, games and software too
  • It asks first. Claiming changes your itch.io account, so it shows how many and from which bundles, and goes ahead on your yes. --yes skips the question, once you have decided; without a keyboard to ask at, it needs that. Like everything Hylly does with a shop, it comes under itch.io's terms: yours to judge.
  • Only what the survey classified. An item is claimed only once the survey knows its kind, from itch.io, or for a program from its bundle's page; --types and --all don't change that, as a claim is hard to take back. If a survey stopped before it asked about every item (Ctrl+C, or itch.io too busy), the claim says how many wait for a finished one: run hylly itchio survey again. An item itch.io wouldn't describe (hidden or taken down, say) isn't claimed either; hylly itchio survey --again asks about every item once more.
  • At a person's pace, on purpose. It claims only what you ask for, one item at a time, no faster than every 20 seconds (--every, never under 10), much as you would by pressing Download on the bundle's page. So even a big bundle asks no more of itch.io's servers than a person pressing the buttons would. A thousand items take about six hours; leave it running.
  • A claim itch.io doesn't take (it happens: one item answered with a server error) is noted and left: claiming pauses five times as long as usual and goes on with the rest, and the next run tries that item once more, after all the others (also with --limit). An item itch.io hasn't taken in three runs is left for good, and the run says which. Three new items in a row not taken stop it, because then the trouble is the site or the login, not one item; it says which, and doesn't keep trying. Each claim is written to state\itchio\claims.jsonl at once, so after Ctrl+C or a stop a new run goes on from there, and an item already in your library, or in two bundles, is claimed once. hylly jobs stop itchio ends one that has hung.
  • Afterwards, hylly itchio survey counts the claimed items with their exact sizes, as itch.io now shows their files.

Downloading fetches what the library is for from your itch.io library, claimed bundle items included, into itchio\<creator>\<title>\:

hylly itchio download --dry-run          # how many titles and files, how many GB, and the first 40 paths
hylly itchio download                    # books, comics, tabletop, and the other items that are all books
hylly itchio download --types comic      # only these types (book, comic, tabletop, other, game, reading)
hylly itchio download --creator "Ann"    # or --title: only the items whose name contains this
  • What it takes: the books, comics and tabletop games, and from the other kinds (zines, games) the items whose files are all books or comics (PDF, EPUB, MOBI, AZW3, FB2, CBZ and the like), such as a rulebook filed as a game: reading in --types. Of those it fetches only the kinds of file on a list: the books' own formats, archives (ZIP, RAR, 7Z, CBZ, CBR), pictures (JPG, PNG, GIF, WebP) and plain documents (TXT, MD, RTF, ODT, DOCX, ODS, XLSX). Anyone can put any file in an item, and a script or a shortcut in the library's folders could be run by whoever opens them: programs, scripts and shortcuts never come, whatever the list or your rules say, nor music, video and art assets by itch.io's own type. A kind goes by the name the file is saved under, so Setup.exe. is an EXE, as Windows would have it. Files only linked elsewhere (Google Drive and the like) can't be fetched.
  • Every run lists what it left out, a dry run too, after its summary: each file's title, name and kind, and why. A run that fetches files writes the list in state\download-log.txt too. None of it is a failure, and a file an earlier run downloaded stays where it is. To take a kind too, such as music, write fetch_add = ["mp3"] under [itchio] in a rules file of your own: hylly rules copy formats makes one with that line ready, and hylly rules show itchio shows the list in effect.
  • First it reads your library (about a minute for a few thousand items) and asks itch.io for the files of the items the survey didn't see, one a second. The answers are kept for two weeks, or a few days more by item so that they don't all come due on one day, and the next runs ask only about new items; then an item's files are asked about again, as creators revise their rulebooks and zines. A new file comes; so does a replaced one, whether itch.io lists it anew or in the old one's place (another checksum), beside the old one under a name of its own, such as guide (2).pdf, and the run says so; the old one stays. The same file uploaded again isn't fetched twice. A file itch.io no longer has (its link answers 404) fails, saying so, and the next run asks about its item at once; its old record then no longer counts as missing in hylly verify. A run asks only about the items it may take (--types, --title, --creator; of the old answers, those of the first --limit items), and a dry run lets no answer age. --again asks about every item now.
  • Like the other shops: each file is checked against the checksum itch.io lists, a stopped download goes on where it was, and a new run only fetches what's missing; each item keeps its folder and file names. The links itch.io gives live a short while, so each is asked for right before its file, and never saved. hylly download runs it with the other shops.
  • In the library page the items show with itch.io as their source, their creator as the publisher, and as the author when nothing else names one (written as it is on itch.io, and now and then a studio; a lookup's answer or your correction comes first), and itch.io's cover and description where the file has none. Each is of the kind its creator chose, unless the words of its bundles or its creator's name say otherwise, as at every shop, and is read where its kind and its main file say, as every title is (kinds). --kind takes only the items of these kinds, as found so; --types still says which of itch.io's own classifications are looked at.

Your own folders

Books, comics and manuals you have yourself, from wherever they came, go into folders of your own at the top of the library, next to the shops' folders. Every such folder is read as it is: one title per book, files with the same name in different formats (EPUB and MOBI) together, and the first subfolder shown as the title's collection. Names compare in any script, without regard to capitals, spaces or punctuation, but accents count: Tähti and Tahti are two books, as C, C++ and C# are three. The folder's name is its source in the library page and the feeds. Yours now: {{own_folders}}.

  1. Copy the files into a folder in the library, for example {{library}}\collections\<collection name>\, {{library}}\comics\<series or publisher>\ or {{library}}\manuals\<platform>\, or let hylly add copy them (below).
  2. Run hylly catalog --lookup.
  • A folder at the top of the library whose name starts with _ is left alone: no build reads it, the server never sends anything in it, and a backup leaves it out. Hylly's own are _settings-from-backup, which a restore makes in its new folder, and _Removed, which the Server page's removals move files into and its Removed part empties (To decide); any other is yours, so one such as {{library}}\_originals is a safe place to park files on their way out, until you empty it yourself.
  • Folder names count. A subfolder's name becomes the collection, and words in it help pick the genre: a folder called “Science Fiction” gives the Science Fiction genre (the words are yours to change: rules files).
  • Copies become one card. A book that is already in the library elsewhere joins that card; its details list every copy.
  • Comic series: files like Moonwake Vol. 1.cbz or Ironclad Hearts 007.cbz are grouped into a series automatically.
  • Built in: a folder called comics holds comics and one called manuals manuals, as the kinds in the rules name them (folders under [kinds.comic]); any other holds books, unless its settings say otherwise. Each title is read where its kind and its main file say, as the shops' titles are.

A folder's settings, all optional, go in a section of their own in {{settings}} (see settings.example.toml):

[folders.ebooks]
label = "My e-books"     # the source's name in the library page and the feeds
kind = "book"            # what its files are: a kind in the rules (book, tech, rpg, comic, manual)
kinds = { "Graphic Novels" = "comic", "Programming" = "tech" }   # subfolders whose files are another kind
genres = true            # the first subfolder is the genre
named = true             # the file names are the books' own titles: "Title (Series Book 2)" gives the series
first = true             # its copy leads when a title is in several places, and it is looked up first

kinds names subfolders without regard to capitals, so "Graphic Novels" is also the folder Graphic novels; an entry that names no subfolder there, a name written wrong say, is told once when the catalog is built. With genres = true, a subfolder whose words find one of the genres in the rules is that genre (Dystopias is Science Fiction), and any other is a genre of its own, as named; a book outside a subfolder gets its genre as any other title, by its words.

Copying books in with hylly add: it copies from a folder elsewhere on your computer into one of yours, checking each copy against its original, which is only read.

  1. Under the folder's section, name where the books are: copy_from = 'D:\Books'.
  2. Optionally, a list that says which book goes into which subfolder, list = 'D:\Books\add-list.csv' (examples/add-list.csv is one to start from): one line per book, the file name, a comma, then the subfolder. Put a file name in quotes if it contains a comma: 
    file,category
The Lantern Keeper (Harbor Lights Book 2).epub,Science Fiction
"Small Tools, Big Habits, 2nd Edition.epub",Programming
    A list made in a spreadsheet does as well: save it as CSV UTF-8; a semicolon between the columns, Excel's own sep= line first, other columns beside them and empty rows are fine. The subfolder is taken as written, spaces and all, and a book with an empty one goes at the top of the folder. A list without those two columns on its first line, or naming one twice, or a line with no file or no cell at all for the subfolder, stops it before anything is copied, naming the line. Without a list, every book there is copied, in the subfolders it is in.
  3. Copy them: hylly add ebooks --dry-run to check, then hylly add ebooks. Books already copied are skipped, so the list can just grow. A listed book that isn't there stops it before anything is copied, unless it was copied before and its copy has left the library too, as a book you removed: that one is passed over and named at every run, until you take its line out of the list. The list's folder in the library not there, or not to be read, or more than half of the books it has copied gone at once (two or more), look more like a folder moved or a disk away, and stop it as before, nothing copied; if you did remove those books, take their lines out of the list. --from and --list give another folder or list for one run. Two books that would get one name, such as the same file name in two folders given one category, stop it before anything is copied, the dry run too; a book whose name another book's copy already has stays out and is shown as NAME TAKEN on every run. Give one of them another category, or rename it. A book that can't be copied doesn't stop the others: each is named as FAILED, and running it again tries those again. A run is refused before it starts when the library's disk hasn't room for them all, and stops when the disk fills or stops taking copies; running it again carries on from there. Going through the source, it passes over a folder it isn't allowed to read, and names it, and follows no link; a source inside the library, or holding it, is refused.
  4. Update the page: hylly catalog --lookup.

The Inbox does all of that by itself, for books of every kind, each into the folder its kind belongs in, and empties as it goes: The Inbox.

Each copy is compared with its original as it is made, and books already copied are skipped even if their original is gone, or its folder is reached another way now (another drive letter, say): a book with the size and MD5 of the one copied counts as that one. Before removing any originals, run hylly add ebooks until a run has nothing left to copy (it says 0 to copy, then Nothing left to copy) and shows no NAME TAKEN line, then run hylly verify --hash: it reads every copy again from the disk and compares it once more, and it's the only proof that a copy really arrived. Then move the originals into a folder such as {{library}}\_originals (one Hylly leaves alone) rather than deleting them.

The Inbox: books that pass through

The Inbox is a folder where you drop books, whatever they are and wherever they came from, a share on the home network say, and the library server takes them in by itself, each into the folder of yours its kind belongs in: a comic into comics, a manual into manuals, as the kinds in the rules give them folders, and every other book into books, unless into says otherwise. A book gone from the Inbox is a book the library has: copied in, checked, looked up and in the catalog. The library's own folders can then stay read-only to everyone else, as the Inbox is the one place where anything is put. In {{settings}}:

[inbox]
folder = '/srv/inbox'              # the Inbox, by its full path
into = { default = "collections" } # where each kind's books go: here every book but comics and manuals
# folders = ['/srv/scans']         # more Inboxes, each emptied the same way
# lookup = false                   # its books aren't looked up online (as it comes, they are)

Its folders say more, to make sorting easier, though a book dropped at the top is taken as happily:

  • At the top (Lantern Wolf.epub), a book has no collection, and its genre comes from the file, as for any title. Its kind, there or in a collection's folder, is what its file makes it (a CBZ, CBR or CB7 is a comic, and goes where comics go), and otherwise what the folder of yours it goes into says, by that folder's own settings (kind, kinds), as for a book you put there yourself.
  • A folder is the collection, kept as that folder in the folder of yours: Harbor Lights/The Lantern Keeper.epub in the Inbox becomes collections/Harbor Lights/The Lantern Keeper.epub. Its words help pick the genre, as in your own folders (Science Fiction gives the Science Fiction genre).
  • A folder named for a kind, as the rules name and call the kinds, in any capitals (Comics, Manuals, RPG or RPGs, Tech, Books), says its books' kind, and the folder below it is the collection then: Comics/Moonwake/Moonwake 001.cbz becomes comics/Moonwake/Moonwake 001.cbz. A kind with no folder of its own (RPG books and tech books, unless into names one) goes into the folder for every other book, and is kept as that kind as your own correction would keep it (Correcting kind), so the library page shows it as an RPG book, and it is read where RPG books are.
  • A folder whose name starts with # gives its books a tag, the rest of its name, and counts for nothing else: #To read/Hedge Lore.epub goes in tagged To read, and Science Fiction/#Favourite/Star Seeds.epub goes into the collection Science Fiction, tagged Favourite. A name no tag can be (over 40 letters, or nothing after the #) is said once, and its books come in without one.
  • Deeper folders stay folders, with no more meaning.

A tag or a kind given so is an edit like your own, made by the Inbox: Recent changes in the library page lists it with its Undo, and a tag goes with its × as any other (Your tags). into can name a folder of yours for any kind (book, tech, rpg, comic, manual), and default for every kind it doesn't name, as in into = { default = "collections", rpg = "rpg" }; a folder that isn't there yet is made. One Inbox is all most people need; folders names more, each read the same way, each with its own Not added.

  • Once a minute the server looks. A book is taken once it has stayed the same for two minutes, so one still being copied in over the network waits for a later look. It is copied into the folder of yours, as hylly add copies, and the copy is checked against it by size and MD5, and recorded. Then the lookup sources are asked about the new books only, within each source's own budget, as hylly catalog --lookup does: a source that is out of budget or offline is asked again at a later pass, and the book shows meanwhile with what its file says. Then the catalog is built, and only then is the original removed from the Inbox, once its copy and it, both read again, are the same; and with it the folders that leaves empty, but for those at the Inbox's top named for a kind or giving a tag, which stay for the next books. A book whose copy no reader can open, as the build finds, stays in the Inbox, and goes into Not added at the next pass if it's still so.
  • What it never touches: nothing in the library is ever removed or written over, and nothing outside the Inbox is touched: a link or a junction in the Inbox is never followed, and a Not added that is one is left alone, nothing moved into it. An Inbox that is the library, is inside it or holds it is refused, said once, and nothing is taken from it, nor removed. That is told by their paths with links followed; by the folders' identities on the disk (\\?\ before a path, a link or a junction, a bind mount of one of the library's folders); and by a file Hylly writes for a moment in each and looks for in the other (a second share name or mount of the same folder). A library or an Inbox that takes no such file just now, being read-only say, has nothing taken from that Inbox, said once. Before an original goes, the same kind of file is written beside it and looked for beside its copy in the library, so the library's own file is never removed. An Inbox inside another Inbox is refused too. The Inbox's own folder is never removed.
  • Already in the library: a book whose copy the library has, by the size and MD5 that copy was recorded with, goes from the Inbox at the first pass, whatever its name, said as already in the library. So does one identical to a book in your own folders, which have no record of a copy: the files the catalog lists with the same size are read and compared. Dropped under a # folder, the card it is in gets the tag, an edit by the Inbox you can undo. Each file's tags are given once: one that stays in the Inbox, as when it can't be removed from there, never gives back a tag you took off.
  • Not added: what can't be taken is moved into the Inbox's Not added folder, at the same path below it, with a note beside it (NAME.txt) saying why and what to do: a file that isn't a kind Hylly reads as a book, one that is damaged or cut short, one whose name another book in the library has, or one whose copy didn't check. It isn't tried again until you put it back in the Inbox, anywhere in it: then it is, and its note goes by itself. No book in Not added is deleted: what goes from there is only Hylly's own notes whose book is gone, what the systems leave (.DS_Store, Thumbs.db, desktop.ini, macOS's ._ files) and the folders that leaves empty.
  • What you see: the books leave the Inbox and come into the library page; your phone gets a note for each pass that took books (3 books added from the Inbox, details found for 2, and 1 set aside in Not added), within the alarms' usual limits, and the daily summary a line. Each pass's lines are in the Inbox's log: hylly logs inbox. Left alone, as they are: hidden files, whose names start with a dot (as a copy under rsync's temporary name does) or with ~$; a download or a copy still on its way, ending in .part, .crdownload, .partial, .download or .tmp; and what the systems leave in a folder (.DS_Store, Thumbs.db, desktop.ini). A book whose end is all zeros, as a copy that set its full size first and then stopped has it, waits in the Inbox until it's whole, said once; so does one the user Hylly runs as can't read, until it can.
  • By hand: hylly add --inbox --dry-run shows what a pass would take, set aside and remove, and where each book would go, and changes nothing. hylly add --inbox makes a pass there and then, saying so first, and the first time it asks before it removes anything: --yes says yes for you, and with nobody at the keyboard it ends with exit code 8. One at a time: a hylly add typed while a pass runs is refused with exit code 4, and a pass leaves the Inbox to one that runs. hylly add FOLDER with copy_from is the plain hylly add, which only reads.
  • A full disk makes the books wait in the Inbox, said once, never set aside; a copy that couldn't be finished leaves nothing in the library.
  • An Inbox whose folder isn't there, as when its disk isn't connected, or the folder was removed by hand, is said once, in the Inbox's log and by hylly doctor: make the folder, or connect its disk. Hylly makes nothing there itself, as an unmounted disk's place must stay empty. Each pass looks again.
  • Where it runs: the library server starts each pass, as a program of its own, whenever there is anything to do. A server walled in on Linux (examples/hylly.service, The library server) can see neither the Inbox nor the lookups' keys, so there hylly server jobs runs it from its timer, outside the server's walls, whatever jobs says, as it does anywhere with jobs = "external": install examples/hylly-jobs.service and hylly-jobs.timer, with your user, library and Inbox filled in as the file says, and run sudo systemctl enable --now hylly-jobs.timer. Its walls let it write the library and the Inbox, and read the lookups' keys, but not the shops' logins. The user it runs as must be able to change the files in the Inbox, which a share may have written as a user of its own. With nothing to run it, the server's log and hylly doctor say so, with what to install.

Your tags

Your own labels, such as Knitting or To read next. The library page has a Tags filter and shows them in each book's details, search finds them, and both reading-app feeds have a By tag section.

In the library page, for a librarian or an owner (everyone else only sees the tags):

  • One book: in its details, type a tag in the + tag box and press Enter. The × on a tag removes it.
  • Many books: Edit all… in a book's details covers its whole bundle, folder or series, and Edit these… in Manage covers everything the search and filters found. A preview lists the titles, all ticked: untick any that don't belong, then press Add (or choose Remove first). The same preview also changes the kind or the e-reader feed.
  • Undo: each change offers Undo for a few seconds, and Recent changes in Manage lists the latest changes, each with its own Undo.

From a terminal, the same:

hylly tag add Knitting --bundle "Yarn Lovers"          # every title of a bundle
hylly tag add Knitting --search "knitting socks"       # the titles a search finds
hylly tag add "Weird Fiction" --folder collections/Poetry
hylly tag remove Knitting --search amigurumi           # from some titles; with no choice, from all
hylly tag list                                          # every tag, with counts
hylly tag list Knitting                                 # the titles with one tag
  • Each command lists the titles first and asks before changing anything; --dry-run only lists. The choices combine: --bundle Craft --search knit.
  • Tags match without regard to case and keep the spelling they were first given.
  • They are kept in the database on the computer the library is on, every change in order, apart from the generated catalog, so rebuilding the catalog never loses them. If a folder or a file is moved, its tags follow it at the next hylly catalog: to a title new in that build that has the same file, or a file of the same name and size, never to a title that was already there. If one copy of a title in several places goes, its tags stay with the copies left, unless one of them has joined another book's title, when they wait as below. Tags of a title gone, or of a file renamed, wait there, should it come back: each hylly catalog ends by listing them, with the file each title had, and you can put them on the right title yourself, as above.
  • The library page and the reading apps have a change at once, as the server lays your tags over the catalog it sends them; a page already open shows it once it's reloaded.

Games of RPG books

Every RPG title gets its game automatically, such as Traveller, Starfinder or Mothership, so everything for one game is a click away. The library page has a Game filter, and a book's details show its game: click it to see the rest. Search finds it too, and both reading-app feeds have a By game section.

  • Where it comes from: for DriveThruRPG products, DriveThruRPG's own Rule System; when a product lists none, its title, then its description, and last the other products bought in the same bundle, if at least half of them have a game and it is the same one. For the rest, known game names in the title, series or bundle name: everything in a Humble bundle named after Traveller is Traveller, whatever its title.
  • Which games it knows: the program comes with the widely known ones. Add any other, with the words that find it, in a rules file of your own: [games."Iron Stride"] and words = ["iron stride*"] (see rules files). It comes after the shipped ones.
  • Only RPG titles: a Dune novel isn't put under the Dune game. If you make a title an RPG title (see Correcting), it gets its game at the next hylly catalog.
  • Kept apart from your tags: games are worked out again at every hylly catalog and never change your own tags. A stand-alone game with a name of its own, such as a one-book indie game, gets none; give it a tag if you want to find it that way.

Correcting kind, the e-reader feed and the format

The catalog sorts every title into a kind (book, tech book, comic, manual, RPG book), and the e-reader feed's rules decide what an e-reader gets. Where either is wrong for a book, say so yourself:

  • In the library page (where you can edit tags): a book's details have Kind and E-reader feed lists. Automatic shows what the catalog and the rules decide; choose a kind, or Always listed or Never listed, to overrule them. For many books at once, use Edit all… or Edit these… and choose Change: the kind or the e-reader feed.
  • Always listed puts a book in the e-reader feed even when the rules leave it out, for example a PDF or a comic: any file of the e-reader's formats will do, the first it has, whatever its size (formats under [ereader_feed] if you gave it some, then ereader under [download]: EPUB, AZW3, MOBI, AZW, PRC, FB2, PDF, DjVu, CBZ, CBR, CB7, TXT). So the e-reader's list decides what such a title is offered, and it can be a format your e-reader doesn't open (a CBR, for one): take that format off the list, or put the ones it reads first. A PDF counts only if it came from Humble, StoryBundle or DriveThruRPG: an e-reader has no sandbox, KOReader's MuPDF is older than the one with the fix for a crafted PDF, and on itch.io anyone can upload. pdf_from under [ereader_feed] names the sources, your own folders by name, and ["any"] takes them from everywhere.
  • Undo and Recent changes work as for tags, and put back exactly what each book had.
  • The kind you choose steers the downloads too, at every shop: a title not downloaded yet is downloaded as that kind, in the format its kind's list keeps (Humble's) and read where that kind is read, and --kind takes it by it. A title is found by its id in the catalog (h:, s:, d: or i: and its shop's id for it; for a title in several places, the copy that leads). One downloaded already keeps the files it has, so nothing comes again; hylly set format moves a Humble title to another format. Where a title is best read follows your kind at the next hylly catalog.
hylly set kind tech --bundle "Python"        # a bundle of programming books filed as plain books
hylly set ereader never --search "atlas"     # never in the e-reader feed
hylly set ereader always --id h:some_title   # always in it
hylly set kind auto --search "atlas"         # back to what the catalog found

The format to keep (Humble titles): the download keeps one format of each title, chosen by the rules, for example the EPUB of a book or the CBZ of a comic. A book full of pictures can be better as its PDF. Choose it yourself, then download and update the catalog:

hylly set format pdf --search "field guide"  # this title's PDF from now on
hylly humble download --title "field guide"  # fetches the PDF
hylly catalog                                # shows it in the page
hylly set format auto --search "field guide" # no choice of your own: the files there stay as they are
  • The chosen file becomes the title's main file: a PDF goes to the tablet and leaves the e-reader feed. The file you had stays in its folder and in the page.
  • A title already downloaded keeps its format while Humble offers it, so changing the order under [download] in the settings doesn't download your library again: it decides for the titles not downloaded yet. Nor does a better format Humble adds later download by itself (an EPUB for a book you have as MOBI, a CBZ for a comic you have as PDF): every Humble download, a dry run too, says how many titles have one, hylly humble download --dry-run --json names them (kept_behind), and choosing the format here moves one. auto leaves a title in the format it has; one with no file yet gets the order's choice.
  • A format Humble doesn't offer for a title is left out, with a message saying so.
  • This one is set in the terminal only. Recent changes in the library page's Manage menu lists it and can undo it; undoing changes what later downloads fetch, and removes no files.
  • One file of several in the same format (a PDF and a PDF (HQ)): hylly set file fr_hq.pdf --id h:some_title keeps that very file, by its name as Humble lists it, over the format; it is what answering a question does. A title not in the catalog yet (not downloaded) is chosen by its id. Recent changes lists it, with an Undo; hylly set file auto --id h:some_title takes it back too. A format of another sort set later wins over it; one that agrees with it keeps it.

The corrections are kept in the database with your tags, and survive catalog updates the same way.

Editing a title's details

When the catalog got a title, its authors or its series wrong (many comics come without any details at all), write your own. The library page, the search, the series lists and both reading-app feeds then show your version. Your files are never changed.

  • Finding what's missing: the library page's Missing filter shows how many titles lack each detail, and lists them when you pick one:
    • Everything: nothing but the file name. The title comes from it, and there is no author and no description.
    • Title (file name): there is no shop title, and the file's own title is missing, unusable or the same as the file name's. Many of these are fine (“The Lantern Road”), others are not (“moonwake-vol-1”). Files in a folder whose settings say named = true are named by their titles, so they never count.
    • Author, Description, Cover, Publisher, Year.
    It combines with the other filters, for example Comics and Missing: Author. Picking two (Author and Year) lists titles that lack either. A title you fix leaves the list when you save it.
  • In the library page (where you can edit tags): a book's details have Edit title, authors, series…. Change the Title, the Authors (one per line), the Series and its Number, the Year or the Publisher, and press Save.
    • Under each field, Found shows what the catalog found. Use found brings it back for that field, and All as found for every field.
    • An empty field means none: an empty series takes a book out of a series the catalog wrongly put it in.
    • Undo and Recent changes work as for tags, one line per field.
  • In the reading apps: the feeds give each title its title, authors, year (dc:issued) and publisher (dc:publisher), and start its description with its series and number, as in Series: Moonwake #3. OPDS has no field of its own for a series, so apps show it with the description. What an app shows after downloading a file can also come from the file itself, which is left as it is.
hylly set title "Field Notes, Volume One" --id h:some_title
hylly set authors "Ann Writer; Bea Artist" --search "field notes"    # several names: separated by ;
hylly set series "Field Notes" --search "field notes"                # one series for everything found
hylly set series "" --id h:some_title                                # no series
hylly set year auto --id h:some_title                                # back to what the catalog found

Kept in the database with your tags and corrections, so a catalog update never undoes them.

Tag suggestions

Words in {{library}}\curation\tags.toml point to tags. Each tag's own name always counts, so a tag in use suggests itself; add words for more:

[Knitting]
keywords = ["knit", "purl", "yarn"]
not = ["tightly knit"]

[Crochet]
keywords = ["crochet", "amigurumi", "granny square"]
  • A word matches the start of words, so “knit” also finds knitting; a phrase matches words in a row. A title matching a not word is never suggested for that tag. Names with spaces go in quotes: ["Weird Fiction"].
  • Bundle and folder names, collections, series, titles and subjects are looked at. description = true under a tag also looks in descriptions: more finds, more wrong ones.
  • Finding them: Find new suggestions in Tag suggestions, in the library page's Manage menu, or hylly tag suggest. Nothing is tagged until you say so.
  • Reviewing, one title at a time: Y adds the ticked tags (unticked ones count as no), N says no, S skips for now, B goes back. When titles share the reason, say a whole bundle, Review them together… shows them all, ticked.
  • Stop whenever you like: each answer is saved at once, and the rest wait for next time.
  • A no is remembered, so the same suggestion doesn't come back. To change your mind, add the tag as usual, or open Declined under Suggestions: Add after all, or Ask again.

Looking up details online

Many files carry no details of their own: most comics have no authors, description or genre inside them. hylly lookup asks online databases for what is missing, and the next hylly catalog shows it in the page and the reading apps' feeds.

MetronComics. A free community database. Needs an account and its API token.
Comic VineComics that Metron doesn't know. Needs an account and its API key. Non-commercial use only.
Open LibraryBooks, tech and RPG books. No account.
Google BooksWhat the others left out: mostly book descriptions, and comics' collected editions (TPB, HC, manga volumes). Needs a free API key from Google.

Once, for each source that needs a key: make a free account, copy its key, and save it. The key is stored only in {{logins_folder}} (Where things are), and never shown.

Each login command checks the key straight away, and says the same about where to get one. Google's key works for any API its project lets it use, so it is kept to the Books API, in a project that pays for nothing: should it ever get out, it can cost no money and open nothing else.

Then:

hylly lookup --dry-run           # how many titles each source would be asked about, with its site, its terms and when Hylly was last checked against it
hylly lookup                     # asks them; can run for hours, Ctrl+C stops safely
hylly catalog                    # shows what was found
hylly lookup --kind comic --limit 50    # a first, small try
hylly lookup --search "moonwake"            # only the titles a search finds
hylly lookup --source metron --again    # ask again about titles already answered
hylly jobs stop lookup              # ends a lookup that has hung
  • Slow on purpose. Each source has its own pace, and the program stays well inside it so your account is never blocked: Metron about 18 titles a minute, Comic Vine at most 190 requests an hour, Open Library one a second and at most 10,000 a day, Google Books at most 900 a day. A first run over a few thousand comics takes a night or two. Later runs only ask about new titles, so they take minutes. Every minute or so it says how far it is and about how long is left, counting the waits for the hourly budget.
  • It continues where it stopped. Every answer is saved the moment it arrives. After Ctrl+C, a crash, a full day's budget or the computer sleeping, running it again picks up the rest. The day's budget rolls: it counts the last 24 hours. So a source that ends its turn on a spent day says from when there is more, and a run the same time the next day goes on as places come free, waiting up to 15 minutes for the next one.
  • One at a time. A second lookup on this computer, in another window or from a scheduled task, is refused while one runs, and says which process runs it, since when and how it was started: two at once would each keep their own count and ask every source twice as fast as its limits allow, a sure way to get blocked. hylly catalog --lookup then builds the page from what has been found so far. Counting with --dry-run works at any time.
  • If it has hung, or runs in a window you can't find, hylly jobs stop lookup ends it; everything it found is kept. A quiet lookup isn't necessarily hung: when it waits for a source's hourly budget, or because a source asked it to slow down, its last line says so and until when (Comic Vine: this hour's 190 requests are used; waiting until 15:15, then it goes on.). Comic Vine uses its hour in about ten minutes, then waits the rest of it.
  • A source that keeps asking to slow down gets the wait it asks for, up to three minutes, and after three such answers in a row its turn ends for this run; a later run goes on. One that asks for a longer wait, or doesn't say how long, has its turn end there at once. Every request counts towards the budgets as it's sent, also one that fails or is cut short.
  • Off altogether: enabled = false under [lookups] in the settings, and no source is asked: not by hylly lookup, nor hylly catalog --lookup, nor the Inbox. Each says so once. What was found before stays in the catalog. As it comes, every source is asked, in the order of the table; order under [lookups] lists the ones to ask, and a source it leaves out isn't: hylly lookup --source googlebooks with one of those says so. With no source left to ask, it looks nothing up and ends with exit code 3 when all that's missing is a key (hylly login metron and so on), else 5.
  • Your contact, if you want: contact under [lookups] in the settings goes with each question to the sources, so that their people can reach you; Open Library asks clients for one. None is sent unless you set it.
  • When it has to stop, for example because a key no longer works, a source changed its answers, or the disk is full, it says why in the terminal and in state\lookup-log.txt, and shows a notification on this computer. The other sources go on.
  • Each source fills in only what is still missing. The sources are asked in the order of the table. A later one is asked only when the earlier ones left something out: Google Books, for example, about a book Open Library found without a description, or with one that is left out (below). Until the earlier sources have answered a title, the later ones leave it alone, which matters when one stops for the day at its limit.
  • Only sure matches are used. Collected editions ("Vol. 3", HC, TPB) are told apart from single issues ("#3"). A doubtful match is not used at all, and a title not found is asked again after half a year.
  • A title is asked about with its own details and your corrections, not with what a lookup found, so an answer stays and the title isn't asked again.
  • A book asked about by its name alone, with no author or ISBN of its own, takes a match's authors, publisher, year and ISBN only when the match has the very same title, of three words or more (the and a not counted; a subtitle may differ), or when the match's publisher or year is the book's own. Under a short or common title, the first book of that name a source knows is seldom the right one, and no author is better than another book's. Its description and genres are still used. Now and then an answer is about another book of the same name all the same: correct the author in the title's details, where what you write comes first, and the next hylly lookup asks again with it.
  • An itch.io title with no author is asked about with its creator, so a game doesn't take the author of a book with the same name. Most indie games and zines aren't in the sources, and then the creator shows as the author.
  • An answer that can't be right is left out each time the catalog is built, so a saved answer drops out without a new request: a comic's edition dated more than a year after you bought it (a year's slack, as a comic's cover date runs ahead of the day it went on sale; books are left alone, since a later edition of a book is the same book), and a description that is an advert or only a link: selling words with a phone number, or with a link and more selling, not one word such as bonus with a link a sentence on. The next hylly lookup asks the next source for what is left out. Descriptions are shown as plain text, without links or Markdown, and text read in the wrong encoding (doesnâ€™t, CarrÃ©) is put right, in the files' own details too.
  • What it fills: only what the files and the shop left empty: authors (for comics, the writers first, then the artists), description, genres, series and number, year, publisher and ISBN. Your own edits always win (see Editing a title's details). If you correct a title, the next lookup asks about it again under the new name.
  • Where details came from: a title's details in the page show Details from with a link to the source's page, which also credits the source, as Metron's open licence asks. The reading apps' feeds credit them too: such a title's summary ends with Details from and the sources' names, and in the feed for tablets (/opds) the title links to each source's page.

For developers: each source is a small plugin, and adding one is described in docs\lookups.md, for people and for AI agents (the skill .claude\skills\add-lookup-source). Beside it are the skills .claude\skills\add-shop, for a shop in Hylly's own code (docs\downloads.md), and .claude\skills\set-up-server, for setting a library and its server up (docs\playbooks.md).

What the catalog goes by: rules files and your choices

Hylly guesses a lot from names: a title and its author from a file's name, a series and its number, whether a bundle holds comics or RPG books, a genre from a title's words, a game from an RPG book's name, which files are books. What it goes by comes from rules files, in the same language as the settings, that come with the program; files of your own change any part of them. Your rules folder: {{rules_folder}}.

namesWhat is taken out of file names, titles and authors in a file's details that mean nothing (“Untitled”, “Administrator”), and what a person's name looks like.
seriesThe words before a number in a series (Vol., Book, Issue), and the words a series' name leaves out when it is compared.
kindsThe kinds a title may be, one table each, and these are all of them ([kinds.comic] and so on): the name each has in the library page and the feeds, where it is best read (device: ereader, tablet or either), and the words in a bundle's name and the publishers (whole words of who made it) that make a shop's title a comic, an RPG book or a tech book, at every shop, over the shop's own (a book at Humble and StoryBundle, an RPG book at DriveThruRPG, at itch.io the kind its creator chose). A kind added in a file of yours is a kind everywhere; none can be taken away (inherit = false and off = true there act on the words alone). Also what marks a shop's file as an extra, audio or video, or a translation.
genresThe words that give each genre.
gamesThe names of widely known RPG games, for the Game filter; add any other in a file of your own.
formatsEach file format: whether it flows to the screen or keeps its pages, whether it is a book, whether it can be the format you keep. Also the kinds of file an itch.io download takes ([itchio]), and the programs, scripts and shortcuts no download takes, from any shop.
  • Your own files go in your rules folder, any name ending in .toml, saved as UTF-8, read in name order after the shipped ones; hylly rules names what it doesn't read there, such as Notepad's mine.toml.txt. hylly rules copy genres puts the shipped genres there with every rule commented out, each on one line, to start from: it changes nothing until you take the # off a line. Take it off only the lines you change; the rest stays as shipped and gets the program's updates.
  • How they change the shipped ones: a genre, game, kind or format you name changes that one and leaves the others (capitals don't count in a genre's or a game's name); a value you write replaces the shipped one; words_add and words_drop (any list with _add or _drop) add to it or take from it; off = true takes an entry away, and inherit = false at the top of a table starts it empty. A genre or game you add comes after the shipped ones. Taking away what isn't there (a name written wrong) is no mistake: hylly rules lists it as nothing to take away.
  • Words are whole words or phrases, in every table; capitals and accents don't count, nor the spaces or punctuation between a phrase's words, and a * at the end means “starts with”: dystopi* finds dystopia and dystopian. A _ ends a word as a space does: audio finds a file labelled MP3_Audio. Where words can't say it, patterns (regular expressions) go in single quotes.
  • A number at the start of a name stays in its title, as in 2.5 Moons. If your files' names start with a list's number, as in 53.01 Lantern Wolf, number_pattern under [filename] in a rules file of yours takes it off file names and titles alike: docs/rules.md, in Hylly's source, has one to copy.
  • A mistake stops the command and names the file, the table and the entry. The server reads the rules and the settings when it starts, and a mistake there stops it; started hidden or at logon, it says so in its log. A rules folder that isn't there yet doesn't stop it: it reads the rules once they are there, and until then a page that needs them says something went wrong. A running server keeps the rules and settings it had, the home network included, until the mistake is put right, and says it once; made again later, it says it again.
  • When it shows: a command reads the rules and the settings once, as it starts; a running server looks at them again every few seconds. hylly catalog applies a change to kinds, genres, games, series and formats, and to titles and authors that came from a file's name; the feeds group series by what the catalog saved. What a file's own details say is read with the file, and so are how its authors are split and what a ZIP holds ([packages]): --rebuild reads every file again.
  • Every computer the same: rules = '…' at the top of the settings, above the first [section], or HYLLY_RULES, points to a folder every computer reads, such as {{library}}\curation\rules, or to one file. --rules FILE_OR_FOLDER, on a command that reads the rules (Every command and option lists them), adds one more for that command; given to hylly serve, for that one run in the foreground. A server in the background, restarted or started at logon goes by the settings: rules there, or HYLLY_RULES.
[genres."Railway Stories"]      # a genre of your own
words = ["railway", "steam locomotive", "branch line"]

[genres."Travel"]               # one more word for a shipped genre
words_add = ["guidebook"]

[genres."Romance"]              # a shipped genre you don't want
off = true

[filename]                      # tags in your files' names to take out
strip_add = ["(shelf copy)", "[scan]"]
hylly rules                      # where the rules come from, and what your files change
hylly rules show genres          # the genres in effect, each marked shipped or yours
hylly rules try "Neon Rangers 002 (2009).cbz" --bundle "Comics Bundle"   # what they make of a name

Your choices are settings in {{settings}}, each with a default (see settings.example.toml):

hylly settings show              # every setting, with its value and where it comes from: the file, the environment or the default
hylly settings check             # every mistake in the file, not just the first; exit code 5 if there's one
hylly settings edit              # the file in your editor (VISUAL, else EDITOR, else the system's), checked afterwards
hylly settings path              # where the file is
  • [download]: the format a title is kept in, as a list of formats, best first, for each device: ereader for books, tech books and manuals (EPUB, then AZW3, MOBI, and on), tablet for comics (CBZ, then CBR, CB7, else the larger of the PDF and the EPUB), and a list of a kind's own where you want one, rpg for RPG books as it comes (the PDF first). The first format on the list that a title is offered in wins, its largest file; "largest" on a list takes the largest file of the formats after it; and when nothing on the list is offered, the largest file. The same order picks a title's main file in the page, read for its details and its cover, of its book files Hylly can read, never an extra (the one you chose with hylly set format first), and a Humble title takes what it lacks, such as a description or a series, from the same book in its other formats (never a PDF); and the book read inside a ZIP; the e-reader feed offers the e-reader's formats that flow to the screen. Also the language, when a shop offers translations, and unsure: "guess" (the default) or "ask", whether a download takes the rules' guess where they are unsure, or holds that file back until you answer (What the downloads leave to you). settings.example.toml has a list for a Kindle and one for a Kobo. The e-reader feed takes the e-reader's list as the server starts: hylly server restart after a change. hylly humble download --dry-run or hylly download --dry-run shows what a change would download: a title already downloaded stays in its format, so a new order downloads nothing again (hylly set format changes one title's).
  • [devices]: a PDF, DjVu or comic file goes to a tablet; a text file over 21 MB is probably full of pictures. Which kinds suit a tablet, and which either, is each kind's own, device in the rules (kinds, above). Every title gets one, of every shop and every folder of yours, by its kind and its main file (a ZIP package by the book inside it, never by its own size). The e-reader feed leaves out the tablet ones.
  • [reader] cache_gb: the reader's cache on the server's disk, of the pages it has drawn and the comics unpacked whole (10 GB, and the disk keeps a twentieth of it free: 2.1 GB at least, 21.5 GB at most); cache_folder: where that cache is, by its full path ("": Hylly's own cache folder, Where things are); draw_ahead: how many pages the server draws ahead at most for each reader (32, 0 to 200; 0 for none); book_fonts: whether the browser loads the font files books bring (Security); word_meanings: whether holding a word asks Wiktionary and Wikipedia for its meaning (true; false, and the word box has only Bookmark); memory_mb: pages the server keeps in its memory (128 MB, 16 to 16384), and however much you set, it also keeps to half of what's free, and hylly doctor says if that holds it back; pages_ahead, pages_ahead_fast, sharp_ahead and tiles_ahead: how far the browser reads ahead (5, 9, 2 and 6). A number past its limits is told in the server's log, and the nearest limit goes. [lookups]: the order the sources are asked in, and how sure a match must be. [tools] sevenzip: where 7-Zip is, by its full path on Windows; on Linux and macOS by default 7z or 7zz on the PATH.

A value of the wrong kind stops a command, or the server as it starts, as a mistake in a rules file does: in every section, [server], [bell], [ereader_feed] and [folders.NAME] too. True and false go without quotes (a number may have them): access_log = "false" in quotes is a text, and stops the server rather than keep the log it was meant to stop. A key a section doesn't have, a section there is none of (such as [Server]) and a name at the top that isn't a setting there are said once and left out, and so is a key Hylly no longer uses, with what took its place; hylly settings show lists every setting with its value and where it comes from, and what was left out, with the value of what's left out never shown; the alarms' ntfy address and token aren't in the file at all (Alarms). The file may be saved with a byte order mark or old Mac line ends, and so may the rules, tags and theme files. A command stops at the first mistake; hylly settings check lists them all, and hylly doctor says what it is without stopping.

The library page

  • hylly catalog updates the page, which the server sends (Opening the library): its last line says the page's address while the server runs, or else to run hylly serve. Only new or changed files are read, so it usually takes a few minutes. Reload the page afterwards (F5, or on a Mac ⌘R).
  • --lookup first asks the online sources about new titles without details, as hylly lookup does (see Looking up details online). Answers are remembered, so without it the catalog uses what was found before and needs no network.
  • --rebuild reads every file again: minutes for a few hundred books, hours for thousands on a network share. It's needed when a program change calls for it, and after a change to the rules read with each file: how authors are split, and what a ZIP holds ([packages]), as What the catalog goes by says. The covers and the caches of what was read are set aside first, not deleted, and only once the library's records and the rules can be read: they go once the new build is kept, and are put back if it's stopped or fails. After a power cut in the middle of one, the next hylly catalog reads what it hadn't, removes them, and says so. Meanwhile the library page shows the covers read again so far.
  • A build that would lose many titles stops first: when a source that had 10 titles or more has lost more than half of them since the last build, or the whole catalog more than a fifth, nothing is kept and the page stays as it was. It names the sources and the folders most of the missing titles were in. Most often a folder isn't there just now, a disk not mounted or a share gone away: once it's back, run hylly catalog again. If the titles are gone on purpose, say yes when it asks, or run hylly catalog --yes. With nobody there to ask, as in a scheduled run, it ends with exit code 8, sends a note saying so (see notes), and hylly jobs shows that run.
  • A folder that can't be read just then stops the build too, with nothing changed, and says which one: one of your folders, or a folder in it that had titles in the last build. Another one that can't be read is passed over with a line saying so, and the systems' own folders (System Volume Information, $RECYCLE.BIN, lost+found and the like) are never read for books, by a build or by hylly doctor. Neither are, at any depth of your folders, the folders that tools keep beside your books: version control's (.git, .svn, .hg), trash (.Trash, .Trash-1000 and the like for each user, .Trashes, Calibre's .caltrash), sync tools' (.stversions, .stfolder, .sync, .dropbox.cache) and macOS's (.AppleDouble, .Spotlight-V100, .fseventsd, .TemporaryItems). Titles an older Hylly found in any of these leave the catalog without counting as missing. Another folder whose name starts with a dot is read as any other. A file whose name isn't proper text, as on a Linux disk where an old program wrote names in another encoding, is passed over too, with a line naming it (its odd letters shown as \xe9 and the like); renamed, it comes in with the next build. So is a book file that is listed but can't then be looked at, with a line naming it and why: on Windows, one whose path is longer than Windows takes; anywhere, a link that leads nowhere, or one damaged file the disk can't answer for while its folder still answers (when the folder doesn't answer either, the build stops, as above). On Windows a folder whose name ends in a dot or a space, as Linux and macOS may write them, can't be read at all, and is a folder that can't be read, as above. hylly doctor names these files and folders too.
  • A book file that can't be read doesn't stop the build. One that can't be read just then (a share that stalls, a file another program holds, too little memory) keeps what was known of it, a line says how many there were and names up to three, and the next build reads it again. A damaged one gets the title and author its file name gives; hylly catalog --retry-covers reads those again, with the other files that have no cover. A file that trips up the build in some other way is named in a line of its own, and the next build tries it again.
  • The catalog\ folder only holds the catalog the server reads (data.js), covers and caches, so it is safe to delete. The next run rebuilds it, but making the covers again takes time: minutes for a few hundred books, hours for thousands on a network share. The page, and this help, come from the program itself.
  • Which browser: Safari, Chrome or Edge, and which versions, as Reading says.
  • The bars at the top stay in view as you scroll, except on a phone, where they'd cover too much. On an upright iPad they're two rows, and where there's room, one.
    • Where you are and who you are: Filters, the library's name, and the blue button with the shelf you're on, solid when it's a shelf and not everything. A phone leaves out the name. At the right end three buttons, just icons when room is short:
      • Help (?): this page, How to read, and in the home-screen app Refresh, which loads the page again in its latest version, as that app has no reload.
      • Manage, for those who may manage the library (below).
      • The account menu (your name, or Account): who you are, with Log in or Log out beside it; the colours and themes on one line; and, logged in, four tiles with their counts: Reading list, Your lists, Bookmarks and Your reviews. At its foot, Source and Licences (Licences and source).
      On a PC, pointing at a row or a tile in these menus says more of what it does.
    • The library's management, behind Manage, for those who may manage the library. Its button counts what someone waits on you for, the reported titles and the reviews to check, and each has its own count in the menu. Then Tag suggestions, Edit these… for all the titles showing, Recent changes and, for an owner, Server. A librarian's has Reported titles and Your recent changes.

A filter narrows it, as it does the list; a search hides it while it lasts. A title you've finished leaves it.

  • Your reading list, if you're logged in: tap the heart beside Read in a title's details, or in the reader's menu. It's filled when the title is on your list, and another tap takes it off, with an Undo. New ones go to the bottom. A title opened from a series' card has the series' name at the top of its details (‹ Lantern Wolf), and closing them, or coming back from reading it, goes back to the series, as far down as you were.

On a computer they open as a window in the middle of the page: ✕, Esc or a click beside it closes it. Your lists, bookmarks and reviews open the same way.

Each browser remembers its choice, and the title at the top stays at the top when you switch. On a PC the titles also move as under a finger: press the mouse's button on them and drag, the list up and down or a row such as Continue reading sideways, and let go while moving for them to glide on a little (unless the device asks for reduced motion); a click that hardly moves still opens a title.

The file comes over first, and the page shows how far. If the sheet doesn't open after a long wait, the page says so: tap the file again.

  • Colours: the account menu switches between Auto, Light and Dark. Auto looks as the device is set: on an iPhone or iPad set to Automatic appearance, light by day and dark at night. Each device and browser remembers its own choice, and this help page and the server page follow it. Beside them are the themes.
  • The search is the box with the magnifying glass at the top; on a PC, / jumps to it. The circled × at its right empties it. What it looks at, best first: titles and series, then authors, tags and games, then publisher, bundle, collection and genres, and last the file names. Every word you type must match somewhere; small typos are forgiven in words of four letters or more. Capitals, accents and punctuation don't count, and words in any script are found: Cyrillic, Greek, Hebrew, Arabic, Hindi, Japanese and the rest. Japanese and Chinese write no spaces between words, so there a title is found by how a run of its text starts. A title found only by its file name comes after those whose details match.

A group shows when it has something to pick: Reading and Lists for those logged in, Rating while stars are on, Reported for owners and librarians.

    • Phone sideways (and the iPad mini upright): a panel from the left over the titles, with Show … titles at its top. A tap beside it or Esc closes it.

Reading in the library page: HyllyReader

With HyllyReader, comics (CBZ and CBR), PDFs and books (EPUB, AZW3, MOBI and FB2) can be read right in the browser, on any device that reaches the library: Read in a title's details. A book opens its EPUB first, then AZW3, MOBI, FB2, and only then a PDF; anything else (a comic, an RPG book, a tech book, a manual) opens its CBZ, CBR or PDF first. A tech book's PDF comes first on purpose: its code and diagrams keep their layout there, which is why the rules call a tech book fine on an e-reader but better on a tablet. Which kinds open their e-book first is text_first in the rules' kinds (rules files).

Which browser: Hylly is made for Safari, Chrome and Edge, and tried in them. The library page needs Safari on iOS or iPadOS 16.2 or later, or a current Chrome or Edge, and reading e-books in it Safari 16.4. Others, such as a current Firefox, should work too, and what doesn't work in them is put right once it's reported. An older browser says what it needs, and a reading app can still use the library through its feed, at /opds.

A title that comes as a ZIP package (StoryBundle ships its books so) is read from inside it, by the same order: for each format the title's own files first, then those in the ZIP, and of two of a kind there, the smaller. A ZIP of nothing but pictures (scans, a comic not named .cbz) reads like a CBZ. The details say which file opens, as the EPUB in the ZIP. A PDF, or an EPUB over 12.6 MB, inside a ZIP is unpacked once into the server's page cache the first time it's opened, which for a big one takes a few seconds; after that it opens at once.

Opening a title

  • The guide: the first time you open a book, once its first page is there, a few pictures over the whole screen show where to tap and what the menu holds, as it is on that device. Swipe, tap the sides of the screen, use the buttons or the arrow keys; Skip or Esc ends it. It's said to be seen as soon as it shows, so it comes once: with a login for you, on all your devices, and without one in that browser. E-books differ from comics and PDFs, so the first of the other kind brings just its own page: holding a word, or zooming. How to read in the Help menu (?) shows all of it again.
  • A book that can't be opened: when it builds the catalog, Hylly looks once at how each EPUB, MOBI and AZW3 is put together. A file may be locked by the shop that sold it, so that only that shop's app can read it, or damaged, or not what its name says. If a title has another file that can be read, that one is read and offered, and the locked or damaged one is marked under Files. If it has none, its details say why where Read would be. Either way the file stays where it is and can still be downloaded, but the feeds don't offer it, as a device couldn't read it either. hylly doctor lists these files. To read a damaged one, the library needs another copy in its place, which the next hylly catalog sees. Comics, PDFs and what's inside a ZIP package aren't looked at like this, and neither is every chapter, so a book with one bad chapter still opens.
  • While it opens: Loading and a bar in the middle of the screen. For a book that comes over whole, the bar and the number say how much of it has come; then Opening while it is laid out. If its first page hasn't come after a minute, the reader says the book couldn't be opened and goes back to the library. A big EPUB, read a part at a time, counts the parts its first pages need: the list of what the file holds, its table of contents, then the chapter it opens at with that chapter's pictures, which are fetched side by side. A comic or a PDF counts its first page as it comes; before that, while the server draws the page, the bar slides back and forth. An opening that takes more than a second and a half grows vines in from the screen's edges, simple outlines in muted greens, leaving the middle clear; they stop when the book is there. They are light behind a book on a white or sepia page and dark behind a comic or a book on a grey or black one. They are drawn a few strokes at a time, which costs a device next to nothing, and not at all when it asks for reduced motion, saves data, or has two processor cores or less than 2 GB of memory; a device that can't keep up stops growing them and keeps what is drawn.
  • Any size opens at once: the server sends one page at a time, scaled for your screen, never the whole file. A 1.3 GB comic's first page takes about a second; pages ahead are fetched while you read. Pages come in a few set widths, each about a quarter wider than the one before, the next one up from your screen's: a window made a little larger or smaller, or full screen, uses the pages this browser has already.
  • When the connection goes: the page says Can't reach the library, tries again by itself, and goes back to normal when it can. What's already here goes on working: search and filters, a book that's open, comic pages already seen. A comic page that hasn't come waits on the screen, and comes when the connection is back. Opening or reloading the page itself with no connection still gives your browser's own error: the page isn't there yet to say anything.

The screen: full screen, the menu and the app

  • Full screen: on a phone or tablet the book opens full screen by itself, where the browser allows it. Android hides everything else. The iPad's Safari keeps its clock and battery bar and puts its own ✕ in the top left corner (it leaves full screen; the page can't remove it). The iPhone's Safari has no full screen for pages. On a PC the book opens in the window; Full screen in the menu, as you like.
  • Outside full screen (a PC's window, an iPhone, or after leaving full screen with Safari's ✕ or a swipe down) the menu stays at the top, the page below it, with Full screen to go back to nothing but the page. The tap at the top centre then brings just the page strip.
  • The cleanest way on an iPad or iPhone: the library as an app. In Safari, open the library, tap Share (the square with an arrow) and Add to Home Screen. Opened from its icon it has no browser bars and no ✕; the clock and battery bar stays (Apple lets no app page hide it) but in black, above the page. The app keeps its own login: log in once there. On Android, Add to Home screen or Install app in the browser's menu does the same.
  • Nothing but the page: in full screen, and in the home-screen app, the book shows no buttons. Tap the top centre for the menu, and again (or anywhere else) to hide it. At the top, on the left: ‹ Library (or the phone's Back, or Esc), which leaves the book for the library, its details open at your place; then the title, and on the right Search and Aa for a book, and Contents where there are any. Tapping past the last page brings the menu too.
  • Turning the screen keeps the page you're on, and the picture stays on the screen: a sharper one replaces it only if it's needed, once it has come.

Turning pages, and finding your way

  • Turning pages: drag the page sideways: it follows your finger, the next one beside it. Let go past a quarter of the screen, or flick, and it rolls on at your finger's speed, slowing into place; short of that it springs back. A tap towards the right rolls on the same way, towards the left back: the outer 30% of the screen on each side. A tap in the middle turns nothing, so a tap that misses, or picking a word, doesn't lose your page. While a page rolls nothing else reacts. If a comic's or a PDF's page hasn't come yet, it says Loading… and you stay there until it has; a page that is already here, as the one before usually is, can still be gone to. Two pages each way are kept loaded and ready, so turning stays smooth however quickly you go. On a PC: drag with the mouse, or the arrow keys, space, Page Up/Down, Home and End.
  • Page turn, for e-books: Slide moves both pages together, as above. With Lift, under Aa, the old page lifts off like a card with rounded corners and slides away over the new one: to the left going on, and to the right going back. Within a chapter the card follows your finger, and let go short it comes back. At a chapter's end it moves when you let go, as the next chapter has to come first. It's kept for each browser, like the rest of Aa. Lift needs Safari 18, or a current Chrome or Edge, and isn't offered otherwise, or when a device asks for reduced motion. Comics and PDFs slide, unless the device asks for reduced motion: then nothing slides, and the next page of a comic, a PDF or an e-book is there at once, as the page strip jumps to its place.
  • Keys, on a PC: arrows, Page Up and Page Down, and Space turn the page; Home and End go to the first and the last; M or a right-click on the page shows the menu (words you've picked, a link and the search field keep the browser's own menu); B a bookmark's reasons; Esc closes what's open, then the book. Space on a button presses it, as anywhere else. With the menu open, the page strip is one stop for Tab: the arrows go along it there, page by page, without turning the book, and Return or Space reads on from the one you've gone to. Contents, Aa and a bookmark's reasons take the keys as they open, and give them back to where they were as they close. In Contents, Aa, the search's list, a word's meaning and a bookmark's reasons, the arrows, Page Up and Down, Home and End move there, not the book, and while Contents is open the book behind it stays still. A button you've clicked keeps Space until you click the page.
  • Without a mouse or a finger: three things have no key yet. A word's meaning and a bookmark on an exact spot need a word held, or double-clicked; zooming a comic or a PDF needs a double tap or a double-click, the mouse wheel, or two fingers. For larger text all through the library page, use the browser's zoom (Ctrl and +, on a Mac ⌘ and +): the browser's own setting for text size doesn't change it. A book's text has its own size in Aa.
  • The page strip comes with the menu, at the bottom: every page small, the middle ones larger, and the middle one's number above Start and End. Drag it to look around; that moves only the strip, not your place. Tap a page to read on from there. When the strip is away from your page, back to … brings it back. A comic's or a PDF's pages show as pictures once the strip stops (blank ones meanwhile); a book's are its locations, shown as pictures of its pages, or as lines with the first of each chapter marked (Page strip in Aa). The pictures show about where in the book each is, as the server lays the book out on pages of its own, and only an EPUB, MOBI or FB2 has them.
  • Contents: a book's chapters, or a PDF's own outline, with the one you're in marked and where each begins. Tap one to go there. Comics have none. Your bookmarks are in a tab beside them.
  • Links in a book: a link to another part of the book goes there. A link to a website or an email address first says where it goes, at the bottom of the page: A link to example.org · Open. Open opens it in a new tab; turning the page lets it be. A note that was there before, such as Marked as finished, steps aside meanwhile and comes back. Any other kind of link does nothing (Security says why).

Your place, on every device

  • Your place follows you: a few seconds after a page settles, and at once when you leave the book, it goes to the server, and the next device that opens the title goes on from there. Without a network it waits, and goes when the network is back. The latest place wins, by when you were there, so a device that was offline for a day doesn't take you back. If that moved you from where you were on this device, a note says so, with a way back: Went to page 80 (read 22:10 on another device) · Back to page 12. It goes when you turn a page. Going back is then the latest place, on every device. Just opening a title and closing it changes nothing. A title left open while the catalog is built again, which gives a moved title a new name of its own, keeps its place and its pages all the same. See What's kept about you.
  • Your place goes with your login, to every device and every address you open the library at; each of these logs in once: the home address and an HTTPS one, and on an iPad or iPhone, Safari and the library as an app. Once you've started, Read in the details becomes Continue with how far you are, as Continue: 35%, and the button fills in as a progress bar: the darker green part read, the lighter part still to go. It opens where you stopped; beside it, the page (Page 7 of 12) or the chapter you're in.
  • Finished, if you're logged in: reading to the last page marks a title finished, and a note says so, with Not yet if that's wrong and Library for the way out. Going to the end from the page strip or the contents is only looking, and doesn't count. Many books have something after the story, such as a note about the author or ads for other books, and few say where that starts. So where a book's own marks or the last entries of its contents suggest the story is over, the reader just asks: Finished? · Mark as finished. Turning the page answers no. Comics and PDFs have nothing like that to go by, so they count from the last page alone.
  • In a title's details, if you're logged in: Mark as finished at any time, Start over to go back to the start on every device, and on a finished title, Read again and Not finished. A finished title leaves Continue reading, and the Reading filter finds it.
  • Next in the series: at the end of a title that's in a series, the note there also shows the next one, with a small cover, and a tap opens it right there, full screen and all. It's the next by number, or where there are no numbers, by title. One you've finished is passed over, and so is another copy of the same number. If none is left after this one, it offers an unread one from before it.

Bookmarks

If you're logged in: the pages you want to find again.

  • Marking a page: in the menu, tap the ribbon beside the page number, then a reason: Inspiring, Clever, Useful, Funny or Infuriating. The button then shows that reason. Tap it again to pick another, or to remove the bookmark. Undo is there for a moment after each. With two pages side by side, it asks which of them. It's always about the page you're on, even with the strip moved elsewhere. On a PC, B brings the reasons.
  • An exact spot, in an e-book: the ribbon marks a page by its first word, so a passage lower down may move to the next page at another text size. To mark the passage itself, hold a word (on a PC, double-click it), and Bookmark in the box with its meaning brings the same reasons. Pick more with the selection's handles, up to a whole stanza: the box then has only Bookmark. The words are underlined on the page, and the list picks a word out in its sentence. Hold it again to change or remove it. The ribbon shows it too, as the page then has a bookmark. A comic's or a PDF's text is part of its picture, so those go by the page.
  • While you read: nothing shows over the page but what you've underlined. An e-book's bottom line has the reason's sign, and with the menu open, so does the page's picture on the strip.
  • In a title: Contents gets a Bookmarks tab once the title has any, with the page and chapter of each and the first words of its page, or a small picture of it. A title with no contents gets a Bookmarks button instead. Tap one to go there, or ✕ to remove it.
  • All of them: Bookmarks in the account menu, by title, the latest marked first, with a filter for each reason you've used. A title that has left the library stays there with its name, for you to remove.
  • Looking doesn't move your place: going to a bookmark leaves your place as it was, here and on your other devices, and a note has the way back. Close the title and nothing has changed. Turn the page from there and you're reading there: that's your place from then on, and until you close the title, the way back stays under the page number in the menu.
  • Through any screen: an e-book's bookmark points at the words themselves, so it holds through a turned screen or another text size. One made with the ribbon may then start part of the way down a page. Opened in another format, it goes by how far through the book it is. They're yours alone, they follow you to your other devices, and without a network they wait as your place does. You can keep 2,000.

Books: the text, search and a word's meaning

  • Books are laid out in the page itself (by foliate-js, a free e-book engine), so their text flows to your screen: two pages side by side when it is wide, such as an iPad held sideways. Turning the screen lays the book out anew, and the page shown is the one with the words that began your page before, so nothing is skipped (as e-readers do); what fits on a page changes, so it may begin a little earlier. They turn like comics: drag, flick or tap. A thin line at the bottom names the chapter and says where you are, as 15 of 59 · 27%. The numbers are locations, stretches of the text that stay the same whatever the screen or the text size, so a place means the same on every device. A book of a few MB comes over whole when it opens; an EPUB over 12.6 MB is read where it lies, a part at a time, as its pages need them, so even an illustrated guide of hundreds of MB opens quickly. (AZW3, MOBI and FB2 always come whole, and open in the page up to 80.0 MB on a computer and 40.0 MB on a phone or tablet: a bigger one's details open instead, with its file to save and read in another app.) A copy-protected book can't be opened. A fixed-layout book (a picture book, comic or manga made as an EPUB or AZW3, each page drawn as it's meant to look) keeps its pages as they are, one or two side by side, scaled to the screen. They turn at once, with a tap, a swipe or a key, and the page strip has one for each of them, numbered as in the book. Its words are part of its pages: Aa has only the page colour around them, the bottom line and the page strip; a search finds the words and goes to their page, but doesn't mark them there; and a bookmark is the ribbon's, for the page, as words in it can't be marked or underlined.
  • Aa, the text settings (books only), the same for every book in that browser, in fixed steps:
    • Font: the book's own, Literata (made for reading on screens), Georgia, or Atkinson Hyperlegible (made by the Braille Institute for easy reading). The two free fonts come with the program.
    • Size in seven steps, line spacing and margins in three each.
    • Page: Theme is your theme's page, light or dark as the library is. White, Sepia, Grey and Black are for this book only, kept in this browser; Back to the theme's returns it, and Keep it in my theme makes that page your own theme's, for light mode (white, sepia) or dark (grey, black), on all your devices when you're logged in. On a dark page every text is light, whatever colours the book sets.
    • Bottom line: off, the chapter and where you are, or how many minutes are left in the chapter instead of its name.
  • Search (books only) looks through the whole book as you type, chapter by chapter, and lists each place with the words around it; each is also marked on its page. Tap one to go there. Search brings the list back; Done forgets it.
  • A word's meaning (books only): hold a word (on a PC, double-click it) and a box under it says what it means, with Bookmark to mark that spot, from Wiktionary, in the book's language; a plural or another form also shows the word it comes from. A capitalised word whose page has no entry in the book's language, such as a name's, is looked up in small letters too, and a sentence's first word in small letters first, so Will in Will you come? is the verb, not the name. Wikipedia in the box gives the encyclopedia's summary instead, and Open the whole entry the full page; beside it the box names where the answer came from and its text's licence, CC BY-SA, as a link to the licence. Translate, the third tab, gives an English word in another language, sense by sense, from the tables of translations in English Wiktionary: the first time it asks which language, and after that the tab is called by it, such as Finnish; tap it again to pick another. This browser remembers the language. The tab is there for English books only, as only English words have those tables; a plural or another form is translated as the word it comes from, and a word nobody has translated into that language yet says so. A word held may be part of a term: its neighbours in the sentence, two or three words with no punctuation between, are asked about in one small request, and when Wiktionary has one as an entry in the book's language, the box gives that instead, the longest one found, picked in the book; Only “…” under it goes back to the word alone, as does dragging the pick back to it. On the Wikipedia tab it's names only: a run of capitalised words with an article of its own, such as Ada Lovelace, not a page listing meanings. Up to four words can also be picked by hand; when together they aren't an entry, the box offers each word to look up on its own. On a touch screen the finger needn't be perfectly still: one that stays on a word for half a second, or creeps only a little, picks it, and the page settles back as you let go; a page drags as soon as the finger really moves. With words picked, a finger on either end of them moves that end, and dragging anywhere else lets them go and moves the page. The box always fits the screen, under the word or above it where there's more room; a long answer scrolls inside it. A tap anywhere closes it. With no answer within 8 seconds, or none at all (no connection, or the site turns the question down for a moment), the box says No answer, and the word is asked again the next time you hold it; a word Wiktionary or Wikipedia has nothing on is said so, and not asked again while the page is open. What goes to Wikimedia's servers (Wiktionary, Wikipedia) to look it up: the word or the words picked, the book's language, and for a word held the few words next to it, up to two on each side (on the Wikipedia tab only capitalised ones, as in a name). The browser sends the library's address along; nothing else of the book or the library goes. With word_meanings = false under [reader] in the settings, nothing goes: holding a word then brings only Bookmark, for those logged in.

Comics and PDFs

  • Two pages: a comic or a PDF shows two pages side by side on a screen wider than it is tall, at the same size as one would be. They turn one page at a time, so any two neighbours can be seen together: a fold-out shows whole wherever it falls. A page wider than it is tall, such as a spread scanned as one picture, shows alone. Two buttons in the menu choose one page or two, the one in use lit; they show only on such a screen, and each device remembers its own choice.
  • Zooming a comic or a PDF: a double tap in the middle of the page zooms in around that spot, and a double tap anywhere goes back to the whole page. The sides keep turning pages at once. Two fingers zoom in, up to six times the whole page. Zoomed in, one finger moves the page, up to its edges, gliding on a little as you let go, and the pages don't turn; a tap at the top centre brings the menu, and any other single tap does nothing, so it can't lose your place on the page. On a PC, the mouse wheel zooms around the pointer, up to six times too, a double-click does what a double tap does, a drag moves the page, and Esc goes back too. The page sharpens a moment after zooming: the server sends it at its full size.
  • Reading at the screen's width: with an upright page on a screen turned sideways, one page at a time, a double tap fits the page to the screen's width, from its top. One finger moves it up and down, and a sideways swipe turns the page and stays at that width.
  • PDFs are drawn page by page on the server, so a 4 GB PDF opens as quickly as a small one; a page takes about a second. Their text is part of the picture, so it can't be selected or searched in the reader (the file itself can, downloaded).
  • CBR comics are RAR archives (or ZIPs named .cbr, which is common). Some RARs are “solid”: all pages packed as one, so a page near the end means unpacking everything before it. The server unpacks such a comic once, in the background, while you read its first pages; after that every page is quick. The unpacked comic is kept in the reader's cache, with the pages drawn, and can be deleted at any time (Kept on the server's disk has the cache's size and place); one that comes to more than 2.1 GB unpacked is read a page at a time instead, and so is one that couldn't be unpacked just then (too little room on the disk, say), until it's tried again ten minutes later. 7-Zip must be installed for this: where it is, is sevenzip under [tools] in the settings, by its full path on Windows; on Linux and macOS, 7z or 7zz on the PATH will do. Most CBR comics also need its RAR part: without it, only a comic whose pages are stored uncompressed opens. The 7-Zip from 7-zip.org has it on every system (on Linux and macOS its 7zz); on Debian and Ubuntu, the package 7zip-rar adds it to 7zip (p7zip-rar to the older p7zip-full; on Debian from non-free); Homebrew's sevenzip is built without it. On macOS, unpack 7-zip.org's download for macOS (double-click it in Finder), and put its 7zz in a folder on the PATH, or give its full path as sevenzip under [tools], outside Hylly's own folders and the library. macOS may hold it back the first time it runs, as a program from the internet: allow it in System Settings, Privacy & Security (Open Anyway), or on an older macOS open it once from Finder with right-click, Open. hylly doctor says whether the 7-Zip it finds has it, and as a problem when the catalog lists CBR comics; a comic that needs it says so as it opens, with what to install.

Reading ahead, and the server's part

  • Reading ahead: once the pages around you have come, the next few are fetched, one at a time, so they're ready when you get there: more if you're turning fast, and the sharp ones if you're reading at the screen's width. A page you're waiting for always goes first. It stops when you close the book or jump elsewhere, with no connection, and with a data saver on.
  • Drawn ahead, on the server: drawing a page it hasn't drawn before takes the server a second or so, and reading one it has a thousandth of that. So with each turn it's told which pages are likely next, and it draws them before they're asked for: 4 when you open a book or jump, then twice as many each time you read halfway through those, up to 32 (draw_ahead under [reader] in the settings, 0 for none). A turn the other way starts again from 4, that way. So jumping about is slow at first, and catches up within a few turns. It draws only while nobody waits for a page, one at a time and at a low priority for the processor and the disk, and not while the server runs on a battery. Everyone's next page comes before anyone's page further on, so readers share the server fairly, and the more people read, the less it guesses.
  • Kept on the server's disk: every page it draws, read or drawn ahead, is kept as a file in {{cache_folder}}, up to cache_gb (10 GB), and the disk always keeps a twentieth of it free: at least 2.1 GB, and at most 21.5 GB. So a book read once opens and turns at once after that, on any device, by anyone, and after the server has restarted. cache_folder puts the cache somewhere else, by its full path: a folder of its own on another disk, say. Hylly makes its own folders inside it but never the folder itself, so a disk that isn't connected isn't filled in its place; on Linux, give a folder on the disk, not the place it's mounted at. Wherever the cache is, Hylly keeps it in two folders there, pages and drawn, and removes only what it made in them: a folder for each book, named by 20 letters and digits, and, as the server starts, a comic's unpacking that a stop left unfinished (such a name, then .part). Anything else in them is left as it is and never counted, and the server's log and hylly doctor name it. While the folder isn't there, can't be written or is inside the library, the pages drawn are kept in memory only, comics that must be unpacked to be read go to Hylly's own cache folder meanwhile, and the server page, its log and hylly doctor say why; it's looked at again every half minute. A cache already in Hylly's own cache folder stays where it was once cache_folder is set: remove it when you like. Hylly's own cache folder can move too, with HYLLY_CACHE_DIR (Where things are); cache_folder is for a folder that may be away, as a disk may, which Hylly never makes in its place. A server walled in by systemd needs a line for the folder in its service, BindPaths=-/mnt/fast/hylly-cache, as examples/hylly.service shows, and a restart. The books read longest ago go first; a page drawn ahead only takes room that's free, so it never pushes out a book someone has read. A file that changes gets new pages. Pages drawn at a width no longer used stay until their book's folder goes or the file changes. A page's address names its width and how it's drawn, so an update that changes either has each browser fetch each page once more. The server page shows how the pages came: from memory, from disk or drawn then, how many were drawn ahead and how many of those were read, and which widths were asked for.

Your lists

A list is like a playlist: titles you choose, in the order you choose, to read through. A shelf fills itself by its rows, and a list only holds what you've put on it. They're for those logged in, they're yours alone, and they follow you to your other devices. Without a network, changes wait as your place does.

  • Making one: Your lists in the account menu, then a name and Make it. Or from a title, below.
  • Putting a title on it: the button with the small list and plus, beside the heart in a title's details or in the reader's menu, shows every list with a tick for those it's on. In the reader it opens over the book, and Done or Esc takes you back to it. An e-book's menu on a phone held upright, or in a narrow window, has no room for the button: there it's in the title's details. A tick puts it on or takes it off at once, and a name there makes a new list with the title on it. The number on the button says how many of your own lists it's on. A title can be on as many as you like, once on each, and new ones go to the bottom.
  • Ordering it: tap a list for the same sheet as the reading list: drag a title by its handle, or use Move to top, ▲ and ▼. ✕ takes it off, with Undo. Each row says how far you've got. Rename and Delete are at the top, and deleting has Undo for a moment too.
  • Reading through it: Read next at the top of a list opens the first title you haven't finished. At that title's end the note there offers the next on the list, in place of the next in its series. This also works if you open a title from the list and tap Read. Closing it comes back to the list. Read next and the note pass over what you've finished and what can't be read in the page.
  • In the filters: Lists has your reading list and your own, so "comics on my tabletop list" works. With a list ticked, List order in the order menu sorts by that list. A shelf can go by a list too.
  • In the reading apps: an owner's list can go in everyone's feed (see Opening the library): Show in reading apps at the top of the list puts it on the feed's front page, in the list's own order. Featured makes it the first thing there, as Featured; one list is Featured at a time, and ticking another moves it. The e-reader feed has only the books on it that suit an e-reader, and leaves out a list with none. Both are off until ticked, and Your lists says which are in the apps. Anyone else's tick puts the list in their own feed only.
  • How many: 50 lists of up to 2,000 titles each, with names up to 60 characters.

Stars and reviews

A title's stars, 1 to 5, say what those who read it thought of it, and a few words can say why. In a family a number says little on its own, so a title's details show who gave what as well as the average: ★★★★ 4.0 from 4, then Ann 5 · Ben 4 · Cleo 3 · you 4 (made-up names). The words come below the details, the newest first.

  • Giving stars: Your stars in a title's details, below Read: tap the fourth for four. Tapping the one you gave takes them back, until you've written words with them. At a book's last page, and where its story seems to be over, the note there asks Rate it? until you have.
  • Writing a review: Write a review in a title's details, or Add a few words once you've given stars. Up to 1,000 characters, which show as you typed them, line breaks and all. Tick It tells how the book ends, and others see it blurred until they tap it. Edit on yours changes it; Delete your review, tapped twice, takes the stars and the words away, and they're gone from the server's files too, not only from the page.
  • When the owner looks first: with moderation on, your words wait until the owner has looked at them. Your review says Waiting for the owner, and only you see the words; your stars count at once. A change to words already out waits beside them, and the others see the earlier words meanwhile. Words the owner doesn't release stay yours to see, with the owner's note if there is one, and you can change them and try again.
  • Your ratings and reviews: Your reviews in the account menu, with how many, has every title you've given stars, the newest first, with where its words stand: All, With words or Stars only. A tap opens the title.
  • Finding by them: the filters' Rating has ★ 4 and up, ★ 3 and up, Rated by you, Finished, not rated by you and With reviews. The order menu has Best rated and Most rated, and while you sort by them each title's stars show under its cover. Best rated pulls a title with few ratings towards everyone's average, so one 5 doesn't go above ten that average 4.6.
  • Who sees them: everyone who may see the library, a borrower too, each with the name of the login that wrote them, so they're never anonymous.
  • Who gives them: those whose role the owner allows.
  • Without a network stars wait, as a place does, and go when it's back; of a few taps in a row only the last is sent. Words are sent when you tap Save: without a network the form says so, and keeps them for another try.
  • Words not saved yet stay: what you've typed in the form is kept in that browser tab until you tap Save or Cancel. Closed by Esc or a tap beside it, the form has it again the next time it opens, saying it isn't saved yet; open when the login ended (a Log out in another tab, say), it opens again with it once you've logged in. Cancel lets it go. A report's words and ticks are kept the same way.
  • For the owner: stars and reviews are off until you turn them on, in {{settings}}: [reviews] who = "reader" lets everyone but borrowers give them, "borrower" everyone logged in, and "librarian" or "owner" fewer. "off" hides them all and keeps what was given. moderation = "on" has the words wait for you, but your own; "borrowers" only a borrower's; "off", the default, lets them out at once. The server sees a change within seconds. They need users: hylly user add. A user removed takes theirs along.
  • Checking reviews: when words wait, the Manage button shows how many, and the phone alarm says so, by count only, never what they say or whose. Reviews to check in Manage shows them one at a time, the words shown now above a change: Release, Don't release… with a note only the writer and the owners see, or Skip for now. You release only what you saw: words changed while you looked come up again as they are now.
  • A year's best: hylly reviews export --year 2026 --out best.md writes the year's rated titles, the best first, with who gave what and the words everyone may read, as a text file to share or print. hylly reviews says who has given how many, and how many wait for you.

Reporting a bad file

A scan that's blurry, a page missing, a file that isn't the book its title says: anyone who notices can say so, and the owner can go through what's been said and look for better copies, a batch at a time.

  • Reporting: any role, Report a problem at the foot of a title's details, small so as not to invite it. Tick what's wrong, one or more: Bad quality, Low resolution, Pages missing or out of order, Wrong file, Questionable content, Something else (which wants a few words); and say more if you like, up to 500 characters. Until you send it or tap Cancel, it's kept as a review's words are (Stars and reviews). The line then says You reported this, with Change, and the box has Take it back.
  • Who sees it: the owners and the librarians, with your name, what you ticked and your words, always as plain text. Other readers don't see that a title was reported.
  • Going through them: owners and librarians get a count on the Manage button, Reported titles in that menu, Reported, waiting for you · Go through in the title's details, and a Reported filter under Housekeeping. In the list, each title has its reports and two choices: Better copy wanted keeps it marked, on the list's second tab, for a later batch of replacing or removing; Fine as it is clears it. A report that comes after either brings the title back to wait, with only the new report. A report that came while you looked isn't decided over: the list says so and shows it.
  • An alarm: with HyllyBell, a title newly waiting sends A title was reported, with how many wait, never which or whose.
  • Kept: in the database: each report with what's kept about its writer, so hylly people export has them and a removed user's go with them; each decision, with who made it and when, which goes into the nightly copy and backups. A title marked for a better copy stays marked when its reporter's account is removed. When a title's file is moved or renamed in one of your own folders, so that the catalog knows it by another id, its reports and the decision on them follow it, as your place in it does: a title found fine isn't asked about again, and a mark stays.
  • Better copies: hylly reports lists what waits and what's marked, with each title's files, and for a Humble title every format and size Humble offers, from the orders saved at the last download, marking the one you have. It asks no shop. Fetching a better copy and replacing the file is a step of its own, still to come.

Themes

A theme is how the library looks: its colours, the reader's bars, menus and loading screen, and the page of a book you read. Each has a light and a dark set, both made for it, so Auto, Light and Dark work with any theme.

  • Picking one: Theme in the account menu, beside Auto, Light and Dark, opens Look. There each theme has a card with its name, a line about it, and its light and dark side by side, and below them the one you wear is shown at real size in each place it colours: the library, a book's page and the loading screen, in light and in dark. A tap on a card puts it on at once. This browser keeps it, and logged in it follows you to your other devices. The help, login and server pages take it too.
  • The nine that come with Hylly, in two groups. Calm, for long reading: Hylly, warm paper, ink and a quiet harbour blue, as the library has always looked; Reading Room, sepia pages and a green banker's lamp, then walnut and brass at night; Birch, Nordic birch bark and lake blue, and a polar night; Clear, high contrast, at least 7:1, in Atkinson Hyperlegible, a typeface made to be easy to tell apart, with edges you can see. With colour of their own: Lake, clear water blue; Moss, forest greens; Lingonberry, berry red and dark wine; Cloudberry, amber and honey; Blue hour, violet dusk. Every theme's text is at least 4.5:1 on what it sits on.
  • A theme of your own: under each preview in Look, Customize opens that place bigger, with the colours that matter there: for the library its background, cards and menus, text and accent; for a book its page, text and links; for the loading screen its background, words and leaves. Each is one of nineteen named colours, such as Sepia, Sky, Lake or Plum, or the theme's own. The first colour you pick makes your own copy, such as Lake, yours, under Yours at the top; the theme you started from stays as it was, and Back to Lake's undoes a place. In light mode pages and backgrounds take a light colour, and text, links and the accent a dark one; in dark mode the other way round. Every light one reads on every dark one, so nothing you pick can make text hard to read. What goes with your colours, such as quieter text, lines and the reader's bars, is worked out from them, and the server checks the whole as it does a theme file. You have one theme of your own; making one from another theme starts afresh.
  • A book's page: the theme's, light or dark as the library is. In the reader's Aa, a page picked for one book stays with that book in this browser, and Keep it in my theme makes it your own theme's page: white and sepia for light mode, grey and black for dark. See Reading.
  • The reader's bars follow the page: over white and sepia paper they take the theme's light colours, over grey and black paper, comics and PDFs its dark ones, so that they never glare beside what you read. The guide to the reader stays dark, as it sits over the page.
  • For the owner: [look] in {{settings}} sets the library's own, which everyone sees until they pick another: theme = "clear". themes = ["hylly", "clear"] says which may be picked, and with just one the picker goes. The server sees a change within seconds.
  • A theme of your own is a small text file: copy one of Hylly's (hylly theme --json lists each theme with its file), give it an id and a name of its own, and change the colours, every one written as #rrggbb, both [light] and [dark]. A line beside each says what it colours. hylly theme check FILE says whether it can be used, and how well its text reads, on its own colours and on the tints the page lays over them, such as a ticked filter's row, and how well a star given or not stands out; text under 3:1 on its own colours is refused. A later Hylly may add colours to a theme: one of those your file lacks is worked out from its other colours, or else taken from Hylly's, so your theme keeps working, and the check names it, for you to set it yourself if you like. Any other colour it lacks is refused. Then copy it to the themes folder in {{settings_folder}}. A theme is colours and a name only, never code, so it can't bring anything else into the page.

Shelves

A shelf is a saved part of the library, which is then the library for now: a nice bookshelf without the odd games, a tabletop night, what one person cares about. Someone with no shelves yet gets a small note about this by the blue button, once in each browser.

  • Choosing one: the blue button at the top says what's showing, and it's solid when you're on a shelf, and Everything is always on its list. Choosing a shelf clears your filters and puts the titles in its order. The address then says the shelf too, so a link opens it.
  • On a shelf: the filters list and count only what's on it, and they narrow it further; Clear all comes back to the shelf. The rows above the titles keep to it too, and so does Next in the series. Your reading list and bookmarks in the account menu are yours, and show all of theirs.
  • Saving one: tick some filters, then Save as a shelf beside them, or Save what's showing as a shelf… in that button's menu. Your ticks become its Show only rows, and a name and Save are enough. It goes by the ticks, not the search, and leaves out Rating and Reported, which a shelf can't go by; the sheet says so. A shelf that's more than the library keeps, such as one more than your 50, or a row of over 50 values, is said before anything changes.
  • Show only and Never show: each row is a field with its values. Any value in a row will do, a title must suit every row, and then Never show takes out what's left and has the last word. So Kind: Comics with Tag: Adult under Never show is the comics without those tagged so. Rows go by kind, source, game, genre, tag, device, author, series, publisher, title, reading, list, e-reader feed or missing details. Typing offers what's in the library. An author, a series, a publisher or a title can also be just words: Moonwake finds any author with that name in theirs.
  • When a search finds little on a shelf, 4 more in Everything says what's outside it, and a tap goes there with your search.
  • Opening with one: Open with this shelf in the menu, for your login, on all your devices; a child's tablet with a login of its own opens with its own. Don't open with this shelf takes it back.
  • Yours, and for everyone: your shelves follow you to your other devices, and those a browser kept before you logged in there come along. A librarian or the owner can tick For everyone: anyone who opens the library can then use that shelf, and it can be changed by whoever made it and by the owner. The server keeps who made each one, and tells readers, librarians and the owner, but never a borrower, so a guest's account learns no one's account name from the shelves; the library page doesn't show it. The owner can also make one the shelf the library opens with, for those who haven't chosen.
  • In the reading apps: Show in reading apps in a shelf's sheet puts it on the feed's front page as a feed of its own: the same browsing, By kind, By genre, Series and the rest, and a search, with only what's on the shelf. Every feed is its reader's own: one for everyone is in everyone's, and one of yours in yours, where a shelf that goes by your reading or your lists follows yours. It's off until ticked.
  • It isn't a lock: a shelf is tidiness. Everything is a tap away, the reading apps' feeds list the whole library besides the shelves ticked for them, the file links know nothing of shelves, and a new title nobody has tagged Adult shows. For a child's shelf, Show only comics and crafts holds better than Never show.

What's kept about you

  • With your login: what's kept goes with the user you log in as, as every request logs in. On the server, the access log also has each device's address and each address it asked for, such as a book's, refused ones too, for 30 days, unless it's turned off. An alarm or the daily summary in {{bell_log}} may name that address too, for many downloads say, and that log has a limit of size but none of age.
  • What: where you've got to in each title you read, when, and on what kind of device, such as iPad · Safari, which you've finished, your reading list and your own lists, your bookmarks, each with the first words of its page if it's an e-book's, your shelves and the shelf you open with, which of the reader's guides you've had, how far you've been shown what's new, the theme you picked and your own theme's colours, and the browsers you've logged in on, until each login is cleared away after it has ended (when each began and ends, and whether it still works). The latest 20 places you reached in each title stay, and the latest 20 times you marked it finished or not; older ones go as new ones come. A list you delete is kept a day, for its Undo, and goes for good with your next change after that. The server takes up to 120 changes a minute from each person, all their devices together, far more than reading sends: past that, the page keeps a change and sends it again a little later by itself, and a review or a report says to try again in a moment.
  • On their way: a change the library can't take just now (no network, a login that has ended, the server busy or being updated) waits in the browser and goes later, in the order you made it; one the library refuses for good, such as a place in a title no longer in it, is let go, and for a shelf the page says so. A browser that can't keep them, its storage full or turned off, says so once, and sends them while the page stays open. Each goes with the login it was made by: a page left open for one person, with someone else logged in since in that browser, sends nothing as the other and starts afresh as theirs, and the first one's changes wait in that browser for their next login there.
  • Private from other users, who can't see any of it, but for your stars and reviews, which are there for everyone to see, with your name, and your reports of bad files, which the owners and librarians see. Words waiting for the owner, or not released, are seen by you and the owners only. It isn't hidden from the library's owner, who holds the files and whose access log already shows what each login opened in the last 30 days.
  • Any browser, not any app: an e-reader or a reading app takes the whole file and reads it offline, so nothing comes back from it.
  • The pages drawn are not about you: the server keeps the pages of comics and PDFs it has drawn on its disk, by book, with no word of who read them; that a book is there says only that someone read it lately. While you read, the page tells the server which pages are likely next, under a number made up for that book, not your name: the server's drawing queue keeps that in its memory only, until those pages are drawn, and then forgets it. Each of those requests is still in the access log, as every request is while it's on, with your login's name and the title's id.
  • Where: in the database, hylly.db in {{data_folder}}, on the server computer. Each change is on the disk before the page hears it went through.
  • A copy every night goes to state/db-backup on the library's disk. Each copy goes once seven newer ones are there, or with the first good copy made after it's 14 days old, so on a server that runs only now and then it doesn't stay for weeks. While no new copy is made, none goes, and the newest stays whatever its age. The server doesn't serve that folder, but anyone who can open the library's share can read it.
  • Words taken away are gone: a review's words you or an owner take away, or a review you delete, are overwritten in the database's file, not only hidden; the nightly copies made before still have them until they go, at the latest with the first good copy made after they're 14 days old, and so do the backup disk's zips, which stay unless keep under [backup] thins them (Backups), and the copy of the database taken before an update changed its tables (hylly.before-NNNN.db beside it).

A user removed: what's kept about them is kept aside in the database, in case that was a mistake. It's no longer theirs, nor in the library page or the feeds. hylly people list lists it apart, with when they were removed. hylly user restore NAME brings them back with it, while no user has that name (else it says what to do first); if the name was removed more than once, with the latest of what's kept aside, and the earlier ones stay as they are. Their password and role went with them, so it asks for a new password, and their role is the one --role gives, else reader, or owner when there are no users. hylly people erase NAME erases it for good, when the person has left and wants it gone: it says what goes and asks first, and never touches what's kept about a user of that name now. The nightly copies made before still have it until they go, and so do the backup disk's zips. The library's own records keep the name where they made a change, such as a tag or a shelf for everyone. hylly user rename changes the name there too, in one go with the rest, so the shelves they made, their changes and their word on reported titles stay theirs, and a later user given the old name has none of it. It refuses a name whose earlier user is kept aside, as that user's records would become the renamed one's: choose another name, or hylly people erase that name first. hylly user add refuses it too, for a new user: while what was kept of a removed user is kept aside, their name is no one else's until they're brought back or erased, and that holds for someone of whom only their name in those records was kept. A removed user of whom nothing was kept, and whom no record names, leaves the name free at once. hylly people erase NAME takes the name out of the records as well, which then say a former user, a name no user can have: a shelf for everyone they made stays, and only an owner may change it. After that the name is free for a new user, who has none of it.

hylly people list            # who has anything kept, and how much; then what's kept aside, with when
hylly people export NAME     # all the database keeps about one person, as JSON (not the logs)
hylly people forget NAME     # all their places
hylly user rename NAME NEW   # a new name, keeping the role, the password and all this
hylly user remove NAME       # what's kept about them is kept aside, in case that was a mistake
hylly user restore NAME      # brings them back with it, with a new password
hylly people erase NAME      # or erases it for good

Checking that the files are intact

hylly verify         # quick: every downloaded and copied file present, with the right size
hylly verify --hash  # full: re-reads every file and checks its MD5 (minutes for a few hundred books, hours for thousands on a share)

This covers what every shop downloaded (Humble, StoryBundle, DriveThruRPG and itch.io) and everything copied into your own folders. Worth running after any disk trouble, and now and then (say twice a year). A book you put in a folder of yours yourself, not with hylly add or through an Inbox, has no record to check it against, so it isn't checked: hylly verify says how many such files there are, once hylly catalog has listed them. A file you removed (To decide), in _Removed or emptied from it, or a shop's file you said you moved by hand, is no problem: it says how many.

When a file is downloaded, it's checked before it's kept: its length against the download server's, and its MD5 against the shop's checksum or else the server's. When the shop's checksum doesn't confirm it and the server's can't either (StoryBundle lists none, and not every server gives one to check), it's kept on its length and its first bytes. Unless the shop's checksum matches, the first bytes must be those of its kind (a PDF starts as PDFs do, an EPUB as a ZIP, a picture as a picture), the server mustn't call it a web page, and it mustn't be far smaller than the shop lists, unless the server's own checksum vouches for it and it's a megabyte or more: Humble now and then serves a newer, much lighter file than its listing says, and the run says when it keeps one. So a sign-in or error page, or an empty answer, is never kept as a book. Kinds with no fixed start, such as TXT, FB2 and Markdown, are only checked for not being a web page. A file that fails is listed in the shop's failures file, and the next run tries it again.

A backup on another disk

Your books, your edits and what people have read, on a second disk: the whole library is otherwise on one. The first backup copies the whole library, minutes for a few hundred books and hours for thousands, and can be left running. After that, only what's new goes over, usually in minutes.

hylly backup TARGET --dry-run      # the plan: how many files, how big, the room. Nothing is written
hylly backup TARGET                # back up. Stopped or not, the same command goes on from where it was
hylly backup                       # to target under [backup] in the settings, as a timer runs it
hylly backup check TARGET          # any time later: read every copy again, and compare
hylly restore BACKUP NEW_FOLDER    # get it all back (with --dry-run: the plan)
hylly jobs stop backup             # end a backup, a check or a restore running on this computer; what it has done is kept

On another disk, really: a target on the library's own disk is taken, as a copy there still helps against a book deleted by mistake, but the plan and the backup say plainly that it is no second copy: when that disk fails, both go.

It asks first before the first backup to a disk, the first of another library to a disk that has a backup already, and one that would copy more than all backed up there before, and over 1.1 GB, so a disk typed wrong gets nothing. --yes (-y) answers it, for a backup with nobody at the keyboard, once you've checked where it goes; without it, and with nobody there, it stops with exit code 8, and a note says so. A disk it has backed up to before goes on without asking.

On the backup's disk you'll find:

  • library, the books as plain files, and the catalog's covers. Any of them can be opened from there, with no program and no password. It's made by HyllyCopy, so all it promises holds here: each copy is read back and checked, stalls and drops are waited out, and a stop goes on from where it was. The zip and the note wait for the same mark: a disk that goes away after the books holds the backup until it's back, and nothing is written on the place it was mounted at.
  • No book is ever deleted. A book gone from the library stays in the backup. A book that changed gets its new copy, and the earlier one goes to changed, by the day: only once the new copy is whole and checked, and just before it takes the name. If the new one can't be read or written, as on a failing disk, the earlier copy stays where it was. So a mistake in the library can't take the backup with it. Each earlier copy's checksum, as it was copied, goes into changed\manifest.sha256, so hylly backup check reads it again too, and so does any sha256sum -c manifest.sha256 in that folder.
  • saved, one zip for each backup: the library's state and curation folders, the catalog's data, and this computer's settings: settings.toml, your rules (wherever rules = or HYLLY_RULES keeps them, by the files Hylly reads as rules) and your own themes. The plan says which, and from where. They change all the time, so they're taken whole, and an older one is there to go back to: every one stays, unless keep thins them (below). Each zip is whole by itself, so older ones may also be deleted by hand, as the disk fills: the plan says how many there are, and how big. state holds the database's newest nightly copy (your records, everyone's reading, and the users with their password hashes), the server's nightly copies of its settings, the shops' orders as last fetched (with Humble's order keys) and the lookups' answers. The jobs' locks in state\locks are left out: they're only for the moment. On Linux and macOS, on a disk that keeps rights, the folder and its zips are yours alone; Windows' own rights, as on a USB disk, are left as they are.
  • HYLLY-BACKUP.txt says how to get it all back, by command or by hand, where the settings folder is on each system, and what the zips hold, to keep private. A README.txt of yours there is left alone; one an older backup wrote, which starts as this note does, is replaced by it once. A restore brings back every book in the backup, also those you've since deleted from the library on purpose.

What's left out, on purpose: logins, cookies, API keys and sessions, so after a disaster you log in to the shops again. The phone's ntfy address and token, which are as good as a password for your alarms, are in the settings folder's secrets folder, which no backup takes, and settings.toml holds no secrets: after a disaster, put the address back in secrets\ntfy-url (the ntfy app on your phone shows the topic it's subscribed to), and a restore says where. Folders in the library whose names start with _ or a dot are left out too, such as _Removed, and so are files still being downloaded or copied in (a download's .part, a copy's .copying), which the backup lists as left out.

Keep the disk at home, or somewhere you trust: it isn't encrypted. Anyone with the disk can read your books, and the zips hold your settings, everyone's reading (where each person is in each title, their lists, bookmarks and reviews), your users' password hashes and your records of orders, with Humble's order keys, which open your Humble download pages. The library's own state folder holds the same, so keep it, and the share it's on, private too.

Where it goes, and how many zips stay: under [backup] in the settings, target = '/mnt/backup/hylly' (or 'E:\Hylly backup', a full path) lets a plain hylly backup and hylly backup check go there; a target typed on the command line wins. Each backup adds a zip, a few hundred megabytes, and as it comes every one stays; hylly backup check reads back the newest three, and with --all every one. keep = { daily = 7, weekly = 4, monthly = 12 } thins them as restic's forget does: going from the newest, the newest zip of each of the 7 latest days that have one stays, of the 4 latest weeks and of the 12 latest months, and so does the oldest zip while one of those counts has some left; the rest go. Only after a backup whose zip is whole, never the zip it has just made, and only the backups' own zips, by their names: any other file in saved stays. The backup lists which went and why, and so does saved\thinned.txt on the disk, with when; --dry-run says which would go, and removes nothing. It applies to every backup this computer makes, to the target typed too. hylly settings check names a key or a value that's wrong.

On a timer: with target set, a plain hylly backup runs nightly from the system's own scheduler. Make the first backup to the disk by hand, at a terminal: a backup asks before its first copy to a disk, and with nobody to answer it copies nothing, ends with exit code 8 and sends a note, as it does for one that would write more than all before. A disk that isn't mounted is refused too, and so is a backup with no target set, each with a note. Each names the hylly command installed as a tool (above) by its full path: the Linux units the tool's own, in uv's folder for tools, as examples/hylly.service does, and the others the one it put on the PATH (uv tool dir --bin says where). Run them on the computer that has the library: on one that reaches the server over ssh ([remote] ssh), a timer has no ssh-agent of yours, so a key with a passphrase can't be used, and a backup's records then come older every night.

  • Linux: examples/hylly-backup.service and hylly-backup.timer, with your user and where the program is filled in as the file says, then sudo cp hylly-backup.service hylly-backup.timer /etc/systemd/system/, sudo systemctl daemon-reload and sudo systemctl enable --now hylly-backup.timer. It runs around 04:30, or at the next start after a night the computer was off; journalctl -u hylly-backup shows what it said.
  • macOS: examples/hylly-backup.plist, with your user filled in, copied to ~/Library/LaunchAgents/io.github.janisc.hylly-backup.plist, then launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/io.github.janisc.hylly-backup.plist. It runs at 04:30 while you're logged in, or as the Mac wakes if it slept then, and writes what it said to ~/Library/Logs/hylly-backup.log. macOS may ask once whether Python may reach the backup's disk, or a network volume.
  • Windows: in Command Prompt, schtasks /Create /TN "Hylly backup" /SC DAILY /ST 04:30 /TR "cmd /c \"\"%USERPROFILE%\.local\bin\hylly.exe\" backup ^< NUL\"". Task Scheduler then saves the task to run as cmd /c ""C:\Users\you\.local\bin\hylly.exe" backup < NUL": the quotes keep a user folder with a space in one piece, the ^ keeps Command Prompt from taking < NUL for itself, and in the task < NUL makes a question end at once, with exit code 8 and a note, as nobody is there to answer it. It runs while you're logged in; Task Scheduler's own settings for the task can run it otherwise, and wake the computer for it.
  • Downloads and lookups the same way, at other hours: examples/hylly-download.service and hylly-download.timer run hylly download around 01:30, and examples/hylly-lookup.service and hylly-lookup.timer run hylly catalog --lookup around 03:30, which asks the lookup sources about the new titles and adds them to the library page. They need the shops' logins and the lookups' keys, so their walls don't hide those. On macOS and Windows, the backup's file or line with download, or catalog --lookup, in place of backup, and a name and an hour of its own: in the plist its Label (io.github.janisc.hylly-download, say), the file's name to match and Hour; in the Windows line /TN "Hylly download" and /ST 01:30. With the backup's name, launchd refuses it while the backup's is loaded, and Task Scheduler offers to replace the backup's task. A login that has expired ends the download with a note, to log in again by hand.

The library server's own nightly jobs (the database's nightly copy, the alarms, the Inbox, whose pass looks up only its own new books) run in the server, or from examples/hylly-jobs.timer with jobs = "external" (its periodic jobs): neither runs a backup, a download or a lookup of the shops' titles. Nothing above runs until you install it.

Your records, as they are: the library's records (your tags and corrections, the catalog, the accounts, what people have read, what was downloaded) are in the database. Just before the zip, the backup copies it again into state\db-backup, so the zip has them as they are at that moment. A copy there dated more than two days after this computer's day, made under a clock that was wrong, is never taken, by a backup or a restore, and they say so. A folder or file of the library that can't be read is listed at the end, and so is a copy of the records that couldn't be made fresh. Either way the backup isn't whole: a note goes to your phone, HYLLY-BACKUP.txt on the disk lists what's missing, and hylly doctor says so until a whole backup has been made.

When the server is on another computer: run the backup where the disk is: a backup always runs on the computer it's typed on. With the server named (-H HOST, HYLLY_REMOTE or [remote] ssh in this computer's settings, as in From another computer), the backup asks the server for that fresh copy. Without it, the zip has the server's last nightly copy, up to a day old, and the backup says so. The server's own settings are copied to state\settings-backup every night, without the phone's topic and token, and on Linux and macOS, on a disk that keeps rights, they can be read by the server's own user only, like the database's copies in state\db-backup. hylly doctor says when others can read them, when the last backup was, whether it was whole, and warns after 30 days.

Getting it all back: hylly restore BACKUP NEW_FOLDER copies the books from the backup into a new folder and unpacks the newest zip there (--saved picks an older one; --dry-run shows the plan first). The folder must be new or empty: one with files in it is refused, so that nothing of the backup is mixed with what's there, unless it's a restore of its own that was stopped before it was whole, which the same command goes on with: only from the same backup, and only while what it copied there is still as it was (a book removed since would come back). A new disk's own desktop.ini, .DS_Store, Thumbs.db and the like don't count as files. The zip is read back before anything is copied: a damaged one is said at once, with the older ones --saved can pick. If the new folder's disk goes away after the books, the restore waits for it before unpacking, and stops if it goes while the zip is unpacked: nothing lands on the place it was mounted at, and the same command goes on once it's back. Then, if this computer has no database yet, the copy of the records in the zip becomes its database. One it has is never written over: if it's the same library's, it's left as it is, as it's likely newer; if it's another library's, the restore says how to put the copy in place or give the restored library a data folder of its own, on this computer's own disk, with HYLLY_HOME naming a folder that holds all of that library's Hylly files, for its commands and server. The books' earlier copies in changed aren't restored: when there are some, the restore says so in its plan and at its end, and for which days, as a book's good copy may be among them. Last, it lists what's left: the backed-up settings, rules and themes, in NEW_FOLDER\_settings-from-backup, to copy to a new computer's settings folder; the library setting, to point at the new folder; the phone's ntfy address and token, to put back in secrets\ntfy-url and ntfy-token in the settings folder; and the shops' logins, to give again.

Copying a lot, and leaving it running: HyllyCopy

For moving a library to a bigger disk, onto a NAS and back, or to a new computer: hundreds of gigabytes, terabytes, or tens of thousands of small files. Explorer and Finder stop with a dialog when a share stalls, and a stop leaves you guessing what got copied. HyllyCopy isn't fast, but it finishes, and it tells you what it did. It works between any two folders, and needs no library.

hylly copy SOURCE TARGET --dry-run  # the plan: how many files, how big, the room, a rough time. Nothing is written
hylly copy SOURCE TARGET            # copy. Stopped or not, the same command goes on from where it was
hylly copy check TARGET             # any time later: read every copy again, and compare
hylly jobs stop copy                # end a copy or a check running on this computer; what it has done is kept

It asks first before the first copy to a target, the first there from another source, and one that would write more than all copied there before from this source, and over 1.1 GB, so a folder typed wrong gets nothing. --yes (-y) answers it once you've checked where it copies from and to; with nobody at the keyboard, it stops with exit code 8, and a note says so. A copy run again goes on without asking. It always runs on the computer it's typed on, with its disks, whatever From another computer names.

What you can count on:

  • The source is only read. Nothing is deleted, moved or overwritten anywhere. A file only the target has stays. A different file with the same name stays too, and the report lists it. Deleting the originals stays yours to do, once the report says it's safe.
  • Only whole files have their names. A file is written in .hyllycopy\parts on the target and gets its name when it's complete and checked, so a stop costs at most the time spent on one file. The next run compares what's there with the source, and goes on from it.
  • Every copy is checked: read back from the disk, past the computer's cache as far as the system allows, and compared with a SHA-256 made while the source was read. Lists of checksums the source already has (.sfv, .md5, .sha1, .sha256) are compared too, as each file is copied or compared, so a list added later has no say in what's already checked. If a file disagrees with such a list it's still copied as it is, and the report says so, as the original may be damaged.
  • Stalls and drops are waited out, on either side: longer and longer pauses, and it goes on from where it was: at most the last 134.2 MB of a file are written again. After 15 minutes with nothing moving, a note says it's on hold, and another when it goes on. It holds as long as it takes. A disk that gets full holds it too, until there is room. report.txt says "not finished" for as long as a run hasn't ended, so an earlier "done" can't mislead you. If it can't be changed at the start, as something has it locked, the copy says so.
  • An unmounted disk doesn't count as being there: on Linux and macOS it leaves an empty folder, which would take the files gladly. A target has a mark of its own in .hyllycopy. If the mark goes during a copy, the copy holds until it's back. A target this computer has copied to before is refused if its mark is gone or another, and so is a source that doesn't look like the one copied from before; --new-disk says it really is another disk, or a folder you emptied. Two kinds of place are watched besides. On Linux, at every copy, a target at or below a place /etc/fstab mounts a disk at, wherever it is (/srv/books, say), is refused while no disk is mounted there, empty or not; a disk mounted deeper on the way, as one mounted by hand at /mnt/usb, is the disk. And before a target has a mark, an empty folder where disks are usually mounted (/mnt, /media, /run/media, /Volumes) that isn't a disk is refused, on Linux and macOS. Anywhere else, as with a disk you mount by hand at a place of your own, check the plan's free space when it's your first copy to a disk.
  • One file that can't be read is noted, and the rest goes on. The same goes for a file or folder where the disk fails or goes away at the same place every time. If five files in a row keep failing that way, it goes on hold with a note: one file every half hour, so as not to wear out a disk that may be in trouble, and back at full speed as soon as one goes through.
  • "Done" means done: the source is listed again at the end, and every file on it has to check out. A file added meanwhile gets another round, and one changing while it's copied is copied again, up to three times. One changed after its copy was made is listed, as nothing is written over. A listing gone short isn't believed: a file that dropped out of it is asked about by itself, a file that failed and then left the source isn't forgotten, and if the source has lost more than half of its files during the copy, it isn't done. A file that left the source before it could be copied is listed.
  • The computer stays awake while it runs, and only then. Closing a laptop's lid may still put it to sleep, depending on its settings. If it does, the copy goes on after it wakes.
  • One at a time, on this computer and on a target another computer is copying to. The target can't be the source by another name either: a mapped drive, a link or a junction to it is refused.

What's kept and what isn't: the contents, the file's time, empty folders, and on Linux and macOS the permissions, which each copy is given as it's made, as far as your umask allows; a read-only file's copy is writable by you, so that a copy cut short goes on from where it was. Not the owner, Windows' own permissions and attributes, or the folders' times. Left out, and listed in the report:

  • Links and junctions: never followed, as they may lead anywhere, even back to where they are. If what they point to matters, copy that too.
  • The systems' own files and folders: .DS_Store, ._ files, Thumbs.db, desktop.ini, $RECYCLE.BIN, System Volume Information and the like. --everything takes them along too.
  • Names the target's disk can't hold, such as one with a colon on Windows, or two that differ only in capitals. They're reported, never renamed behind your back. Nothing is written through a link on the target either: a file that would go that way is reported.

Running it again copies what is new on the source and skips what checks out, and is quick about it. A file changed on the source since it was copied isn't written over: the report lists it, and it's yours to decide. There is no "mirror": nothing is ever deleted from the target for being gone from the source.

Notes: they go where HyllyBell sends things. A copy that takes more than a couple of minutes says it started, with an estimate, and says when it's done; --progress 6h adds how far it has come, this often. A failure or a hold always gets a note. The phone gets counts, never names or paths. If the phone can't be reached, as the way to the internet may be down too, the note goes again later, and for up to an hour after the copy has ended. hylly jobs shows how far it has come.

What it leaves in the target, in .hyllycopy, travelling with the disk:

  • report.txt: how the last run went, with every file that isn't there and why, and what was left out.
  • manifest.sha256: every copy's checksum, which needs no Hylly to check: in the target folder, sha256sum -c .hyllycopy/manifest.sha256.
  • record.jsonl: what was copied and checked, which tells a new run what it can skip, and what hylly copy check goes by. Losing it costs only reading the files again. A file gone from both the source and the target leaves it at the next copy, and until then hylly copy check says it's missing.
  • checked.txt: how the last hylly copy check went.

Copying a folder that was a copy's target leaves its own .hyllycopy, at its top, behind, as the new copy has one of its own. One deeper in, as a backup's library\.hyllycopy, is copied like any folder, so a backup disk moved to a bigger one keeps its record and checksums, and can be checked there.

After the copy, when it's a library you're moving. Stop its server before the copy (hylly server stop), and what runs hylly server jobs every minute, if you set that up (its periodic jobs): on Linux its timer, sudo systemctl stop hylly-jobs.timer; on Windows its task, disabled in Task Scheduler; on macOS, or with cron anywhere, its line, made a comment with #. So nothing in the library changes meanwhile: a file that changes after its copy was made can't be brought along, as nothing on the target is written over, and a move while the server runs may end not done for it. If it does, the report names the file: delete that one on the target, and run the copy again. Once the report says it's done:

  • On the same computer, as to a bigger disk or a NAS: set library in {{settings}} to the new folder. Where the old folder is named outside the settings, name the new one there too: HYLLY_LIBRARY, which a start at logon on Linux and macOS keeps from when it was made, and the walls made from examples/hylly.service and hylly-jobs.service, on every line that names it (its parent too), then sudo systemctl daemon-reload. Then start the server again (hylly serve --background; a system service: sudo systemctl start hylly), and the jobs where you stopped them: sudo systemctl start hylly-jobs.timer, the task enabled again, or the # taken away. The records stay in this computer's database, which takes the library on at its new place, as the copy brought state\database.json along.
  • On a new computer, the books are half of it. The records (your tags and corrections, the catalog, the users, what people have read) are in the old computer's database, hylly.db in {{data_folder}}, and the new computer refuses the library until its own database has them. Either back up on the old computer with its server stopped, hylly backup TARGET, which makes a fresh copy of the records for its zip, and get it all back on the new one, hylly restore BACKUP NEW_FOLDER, which copies the books, unpacks the zip, makes the records that computer's database if it has none yet, and says what's left to do (A backup on another disk). Or, after hylly copy, copy hylly.db from the old computer's data folder into the new one's (hylly settings places says where each is), with hylly.db-wal and hylly.db-shm beside it if they're there: a stopped server may leave its last changes in hylly.db-wal (on Windows, hylly server stop ends it at once). Do it with no server running on either, where the new one has no database yet (move aside one Hylly made there, with any hylly.db-wal and hylly.db-shm of its own), and copy settings.toml with it if you like, but never records-token, which is the old install's; then set library there, take the records over with hylly server take-over, which asks first, and start the server. Either way, leave the old computer's server and jobs stopped, as the records are the new one's from then on, and set the jobs up on the new one if you had them.

Read back on a share: the share's own computer may answer from its memory, which no client can get past. For the most certain check, run hylly copy check TARGET after it has been restarted, or after a good while. And the checks say the copy equals the source: they can't say the source was right to begin with, other than by its own lists of checksums.

How things stand, scripts and AI assistants

  • Is all well? hylly doctor lists the settings, rules, the library, the catalog, e-books that can't be opened, files of the catalog the server refuses, the logins saved, the server, who can log in, how safely it's all set up (rights, where it listens and the address people use, walls), jobs running, alarms, whether 7-Zip can open the CBR comics, and whether anything is too old, with the next step for whatever is wrong. It only looks: it's offline, writes nothing and shows no logins or keys. It does show your folders, so look before you paste it anywhere. It ends with exit code 1 when something needs putting right, though not for something merely old. With --json, each check has an id that stays the same between versions (catalog, settings-rights), beside what, its state, what it says and the next step in words; for a script or an AI assistant, run is the one command to run, where the step is one command that needs no sudo, password, login or yes, and owner: true marks a step that is yours alone: sudo, a password, a choice of yours, or someone at the server computer.
  • What's running? hylly jobs lists the jobs running on this computer, with how far they have come for downloads and lookups, how to end one that has hung, and how each one's last run ended, or that it didn't end (stopped or killed): hylly jobs stop, a closed window or a power cut ends a job before it can say how it went.
  • Where are the logs? hylly logs lists them, and hylly logs lookup --tail 100 shows the end of one: download, lookup, inbox, server, bell or access.
  • To try something: hylly demo makes a small library of made-up books in hylly-demo in your home folder, or the empty folder you name, with its own settings and users, and serves it on port 8779 until Ctrl-C. It needs no shop's login, books or network, and doesn't touch your own library or server. hylly demo --background serves it on its own instead, with no browser, says its address and ends, for a script or an AI assistant that mustn't wait on a server; hylly demo --stop stops that server, the one of the demo's own settings folder, and never yours. --no-serve only makes it, and every run says what to set for other commands on it: HYLLY_HOME and HYLLY_LIBRARY, HYLLY_NO_NOTIFY=1, and HYLLY_SETTINGS, HYLLY_RULES and HYLLY_REMOTE left unset, as they would lead them to your own settings, rules or server computer, and so are your logins and the alarms' secrets: the demo's own run, and its server, leave all of these out. Its owner is demo, with a password nobody is told: at a terminal, its server shows a one-time link that logs a browser in as demo, and opens it on Windows and macOS, or where there is a desktop (DISPLAY or WAYLAND_DISPLAY set). Delete the folder when you're done with it.
  • From a script: a command's exit code says how it ended (the table): 1 is partly done, run it again, and 70 a bug in Hylly, which a run again is likely to meet too: report it, with what it wrote on standard error. Standard output has the command's result only; progress, notes, warnings and questions go to standard error, so a pipe or a file gets the result. --json gives what these say as JSON: (lookup with --dry-run). These give one object, however they end, even one refused before it starts (not a mistyped option, which argparse refuses with exit code 2 and its usage on standard error, and no object), with exit_code, its meaning and the message, and what they found: . A command alone that is one of its actions takes it too: hylly jobs --json is hylly jobs list --json. --library FOLDER goes before the command or after it. A reader that stops reading, such as head at the end of a pipe, gets no more, on standard error too (2>&1 | head): the command goes on with its work and ends with its own exit code, without a word of the pipe. Without a terminal, progress comes as a line each tenth of the way, not as one line rewritten.
  • What each command may do: hylly commands lists which sites it talks to, what it may write, which job it holds, whether it changes your account at a shop (only claiming at itch.io does), what needs a person, where it runs, and whether its --dry-run is offline or reads the site. Either way a dry run changes nothing: it downloads nothing, changes nothing at the shop, and writes no file, database, lock, log or note. One that reads a shop's site still waits its turn: while that shop's download runs, it is refused with exit code 4, as a second download would be.
  • An option a command doesn't take is refused, with exit code 2, and so is one shortened: each action takes only its own, so hylly humble seed FOLDER --limit 5 is refused rather than copying in every file it finds, and hylly backup TARGET --dry rather than backing up.
  • What needs you: logins and passwords are typed at the keyboard, or for a login copied to the clipboard by you; your own script may give them on standard input (hylly login SITE --stdin, hylly user add NAME --password-stdin), or a login in a cookies.txt (--cookies FILE). A login is checked with the site before it's saved, so a wrong one never replaces one that works. These need you at the keyboard: . These ask first, each when its line under Commands that ask first says, and --yes (-y) says yes for you: . With nobody at the keyboard, these end at once with exit code 8 and say what's needed, rather than wait.
  • With an AI assistant: you can let one run these commands for you. It doesn't need your logins: when one has expired, it asks you to run hylly login yourself. On Windows, an assistant in a packaged app has its own copy of the settings folder (more). It starts from AGENTS.md in Hylly's source, with the rules it keeps, and its playbooks are in docs\playbooks.md there, from setting Hylly up to a backup and its restore.
  • A Hylly apart from your own: with HYLLY_HOME set to another folder, on any system, a command keeps its settings, database, users, logins, logs and locks in that folder itself, every kind of Hylly's own files there over their own variables, as long as HYLLY_SETTINGS, HYLLY_RULES and HYLLY_REMOTE are unset: set, they still lead it to your own settings, rules or server computer (hylly --here before a command keeps it on this computer). Such a one can't change the start at logon, which is one for the whole user, so a test or an assistant trying things can't replace yours.

If something goes wrong

  • Writing to a network share fails (“Invalid argument”): as a workaround, if the disk can be attached to this computer directly (a USB disk plugged into a router or a NAS, say), attach it to this computer, then point the commands at it in that terminal: 
    $env:HYLLY_LIBRARY = "E:\Library"    # on Linux or macOS: export HYLLY_LIBRARY=/media/you/Library
    Replace E:\Library with the disk's drive letter and folder, or the place it's mounted at. Close that terminal when done, so later commands use the share again. If writes keep failing, check the disk's health: on a NAS, with its own disk check; else from the disk's SMART data, with CrystalDiskInfo on Windows, or smartctl -a (smartmontools) on Linux and macOS.
  • A tablet or e-reader can't connect:
    • Check that the server runs: hylly server status shows its addresses. A device with Tailscale uses the HTTPS one, In a browser, with Tailscale on there, in the same account. A device without Tailscale needs the server to listen beyond this computer (listen = "0.0.0.0" under [server], with hylly settings edit, then hylly server restart): only then does it show its plain address, as In a browser, or with address set as Home network.
    • At the plain home address, check that both devices are on the home Wi-Fi.
    • Check that the address in the app matches the one hylly server status shows, in full: http:// for the plain home address, https:// for Tailscale's. A “TLS error” at a plain address means the app tried https://.
  • A reading app keeps asking for the password: check the name with hylly user list, or set a new password with hylly user add NAME. After 10 wrong tries, wait 15 minutes. The access log shows each refused request with result 401 (wrong or missing login) or 429 (too many tries).
  • The server doesn't start (“Port {{port}} is taken by another program”): another program uses that port. Choose another with port = … under [server] in your settings, then change the address in the reading apps, and in Tailscale Serve or Funnel, to match. In a walled-in service, the port is in its SocketBindAllow too. Other messages say what else kept it from listening: an address in listen that isn't this computer's, say. Other reasons, such as a mistake in a rules file or in the settings, are at the end of {{server_log}}.
  • A page says “Something went wrong in the server”: the end of {{server_log}} says what; a failure that goes on is said there again each hour, with how often it came. Just after the start at logon, it may be that your rules folder's share isn't there yet: the server reads the rules as soon as it is.
  • A download failed: run the same command again. Failures are listed in the state folder, in each shop's own folder there: state\humble\failures.csv, state\storybundle\failures.csv, state\drivethrurpg\failures.csv, state\itchio\failures.csv. A book is listed there only when none of its formats could be downloaded; a failed extra is listed as itself.

Rules that keep it healthy

  • Don't rename, move or remove files in humble\, storybundle\, drivethrurpg\ or itchio\. They are recorded by path: a shop's file that isn't at its path counts as not downloaded, so the next download from that shop (hylly download) fetches it again, and until then hylly verify reports it as missing. There's no way yet to tell Hylly that you don't want a shop's title.
  • A link that leads out of the library is never read: a book file, or a folder on its way, that's a link to somewhere outside the library gets no details or cover in the catalog. Put the books themselves in the library.
  • Back up state\ and curation\ with the books, best with hylly backup. Your tags, your own work, which no command can make again, are in the database with the record of what was downloaded: hylly.db in {{data_folder}}, on the computer that keeps the library's records, not in the library. The server copies it into state\db-backup once a day, at night if it's running then, so that copy may be a day old, or older if the server hasn't run; hylly backup makes a fresh one each time, and says so when it can't. curation\ holds the words that suggest tags.
  • Keep state\ private. It holds your order keys, which open your Humble download pages, and the nightly copies of the database, with everyone's reading and your users' password hashes, and of the settings. A backup's zips hold all of it too (Backups). On Linux and macOS, on a disk that keeps rights, Hylly makes those copies yours alone, and hylly doctor says when others can read them; on Windows, the folder's own rights decide. The library page and the feeds never show it.
  • To remove something from your own folders: move it into {{library}}\_Removed first, at the same place below it as below the library (ebooks\Science Fiction\Lantern Wolf.epub into _Removed\ebooks\Science Fiction): the Server page's Removed lists it there and puts it back (To decide has how), and empties _Removed once you're sure. A book hylly add copied in isn't copied again while it is there, or once it is emptied from there; moved anywhere else, the next hylly add copies it again while its original is still there to copy from. With a list, take its line out too: once the original is gone as well, hylly add passes it over and says so at every run, until its line is out of the list, and more than half of a list's books gone at once stop it, as a folder moved would. And hylly verify doesn't count it as missing, in _Removed or emptied from it, as it would anywhere else. A shop's file comes back at the next download, as above.
  • Don't rename or remove the network share while the library is on it: the library's address would lead nowhere.

How to stop using Hylly, and what to removeStopping using Hylly

Which folder is the library: state\library.json says so, written once by hylly init. Without it, what writes to the library refuses the folder, and asks whether the disk or the share is there: an unmounted disk leaves an empty folder behind on Linux and macOS, and a download would fill the wrong disk. So when a library that was there is refused, mount the disk or connect the share, and don't mark the folder. hylly init says what it writes, and asks first when the folder is empty or new (--yes answers it). Given the folder, it writes a settings.toml with the library's line, so that every command finds the library, when there is none yet in your usual settings folder or the one HYLLY_HOME or HYLLY_CONFIG_DIR names, and HYLLY_SETTINGS isn't set; one there already it never changes, and otherwise it says the line to add; it refuses an empty folder that this computer's database knows as the library, with titles, unless that library is gone for good and you give --new. To undo it, delete the file. Keep the file with the library.

Using an AI assistant? On Windows, a packaged app, such as the Claude desktop app, gets its own private copy of the settings folder, so what an assistant writes there doesn't reach yours, and the other way round. Run hylly login, hylly user and hylly serve in your own terminal. hylly doctor and hylly user mention it when they find such a copy.

catalog\ can be deleted: hylly catalog makes it again. state\ can't, so back it up with the books: it holds what you bought, the lookups' answers, days of them, and the nightly copies of the database, with the record of what was downloaded, and of the settings. Hylly writes these so that a power cut or a share dropping out costs at most the last line, and a file with a damaged line still reads. The database itself, hylly.db, isn't in the library but in {{data_folder}} on the computer that keeps the library's records: the server copies it into state\db-backup once a day, so that copy may be a day old, or older if the server hasn't run, and hylly backup makes a fresh one each time.
